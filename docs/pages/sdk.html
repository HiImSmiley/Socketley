C++ SDK

Socketley ships a modular C++ SDK in include/linux/socketley/ with a three-tier architecture. Each tier targets a different use case, from zero-dependency daemon control to embedding the full io_uring engine in your own binary.

Three Tiers

TierHeaderUse CaseDependencies
Tier 1socketley/control.hControl a running daemonNone (POSIX only)
Tier 2socketley/server.h
socketley/client.h
socketley/proxy.h
socketley/cache.h		Embed the full enginelibsocketley_sdk.a + io_uring + OpenSSL
Tier 3socketley/attach.hRegister with a daemonNone (builds on Tier 1)
Tiers 1 and 3 are fully self-contained. Copy the header anywhere, compile with g++ -std=c++17, and you're done — no library to link, no repo needed. Tier 2 requires building from source.

Installation

Requirements (same as the daemon build): Linux 5.19+ (io_uring multishot accept), GCC 12+ (C++23 for Tier 2; Tiers 1 and 3 need only C++17), liburing 2.7 or newer to build (Ubuntu 24.04's liburing-dev is 2.5 — use bash scripts/install-liburing.sh; a built binary needs 2.6+ at run time), and libssl-dev.

Tier 1 & 3 (header-only)

Copy the header files from the SDK directory. No build step required:

# Copy headers to your project
cp -r include/linux/socketley/ /your/project/include/

Tier 2 (requires library)

Build the SDK static library from the socketley source tree:

./bin/premake5 gmake2
cd make && make config=release_x64 -j$(nproc)
# Library: bin/Release/libsocketley_sdk.a

Quick Start

Tier 1 — Control a running daemon:

#include <socketley/control.h>

int main() {
    socketley::ctl::create("server", "myapp", "-p 9000 -s");
    socketley::ctl::send("myapp", "Hello!");
    socketley::ctl::stop("myapp");
    socketley::ctl::remove("myapp");
}
// g++ -std=c++17 app.cpp -Iinclude/linux -o app

Tier 2 — Embed the engine:

#include <socketley/server.h>

int main() {
    socketley::server srv(9000);
    srv.on_message([&](int fd, std::string_view msg) {
        srv.send(fd, "echo: " + std::string(msg));
    });
    srv.start();
}
// g++ -std=c++23 app.cpp -I. -Iinclude/linux -Ithirdparty/sol2 -Ithirdparty/luajit \\
//     -Lbin/Release -Lthirdparty/luajit -lsocketley_sdk -luring -lssl -lcrypto -lluajit

Tier 3 — Register with daemon:

#include <socketley/attach.h>

int main() {
    // Your own server setup here...
    socketley::daemon_attach("myservice", "server", 8080);
    // Now visible in: socketley ls
    // Auto-detach on exit()
}
// g++ -std=c++17 app.cpp -Iinclude/linux -o app

Tier 1: Daemon Control

#include <socketley/control.h> — header-only, zero dependencies. Full programmatic control over a running socketley daemon through the same Unix socket IPC that the CLI uses.

Result Type

Every socketley::ctl function returns this struct:

socketley::result 
struct result {
    int         exit_code;  // 0 = success, 1 = bad input, 2 = fatal, -1 = connect failed
    std::string data;       // response body from daemon

    bool ok() const;        // exit_code == 0
};

Deliberately not operator bool: a result with exit_code 1 is a response — the daemon's refusal, with the reason in data. ok() asks the narrower question.

Runtime Management

All functions live in the socketley::ctl namespace.

create Tier 1

result create(const std::string& type, const std::string& name, const std::string& flags = "")

Create a new runtime. Does not start it unless -s is in flags.

ParameterDescription
type"server", "client", "proxy", or "cache"
nameUnique runtime name
flagsCLI flags string (e.g. "-p 9000 -s --mode admin")

Returns: result with exit_code 0 on success

start Tier 1

result start(const std::string& name)

Start a created runtime. Transitions from created/stopped to running.

Returns: result — exit_code 1 if runtime not found or already running

stop Tier 1

result stop(const std::string& name)

Stop a running runtime. Gracefully tears down connections.

remove Tier 1

result remove(const std::string& name)

Remove a stopped runtime permanently. Deletes its persisted state.

ls Tier 1

result ls()

List all runtimes with their type, port, state, and connection count.

Returns: result with tabular listing in data

ps Tier 1

result ps()

Show running runtimes with PIDs and uptime.

stats Tier 1

result stats(const std::string& name)

Get detailed statistics for a runtime: connections, messages, bytes in/out, uptime.

show Tier 1

result show(const std::string& name)

Show the current configuration of a runtime (port, mode, flags, Lua script path, etc.).

reload Tier 1

result reload(const std::string& name)

Reload a runtime (stop + start). Connections are dropped and re-established.

reload_lua Tier 1

result reload_lua(const std::string& name)

Hot-reload the Lua script without restarting the runtime. Existing connections stay alive.

edit Tier 1

result edit(const std::string& name, const std::string& flags)

Edit runtime flags on a stopped runtime. Takes the same flags as create.

restart Tier 1

result restart(const std::string& name)

Stop, then start — two IPC round trips, exactly what the CLI's restart does. The stop's answer is read before the start goes out, so restarting a name the daemon does not hold reports runtime not found once, from the stop.

import_runtime Tier 1

result import_runtime(const std::string& name, const std::string& json)

Create a runtime from a JSON document — the inverse of show(), whose output is accepted unchanged. (Not named import: that is a context-sensitive keyword in C++20 modules.)

Send Behavior

The send method behaves differently depending on the runtime type:

send Tier 1

result send(const std::string& name, const std::string& message)

Send a text message to a runtime. Behavior depends on the runtime type:

RuntimeBehavior
Server (mode != in)Broadcasts to all connected clients
Client (mode != in)Sends to the connected remote server
CacheNot supported — returns error
ProxyNot supported — returns error
 
// Server: broadcasts "hello" to all connected clients
socketley::ctl::send("my_server", "hello");

// Client: sends "hello" to the remote server
socketley::ctl::send("my_client", "hello");

// Cache/Proxy: returns error (exit_code != 0)
auto r = socketley::ctl::send("my_cache", "hello");
// r.exit_code == 1

Daemon & Cluster

ping Tier 1

result ping()

Who is serving this socket: socketley-daemon <version> <pid> <dev:inode> <path>, the executable path read fresh from /proc on the daemon side. The path goes last because a path may contain spaces; the inode is what distinguishes two builds carrying the same version string.

version Tier 1

result version()

The daemon's version string, extracted from ping(). There is no version IPC command — the CLI's socketley version prints the CLI's compile-time version, and a header-only client has none, so the daemon's answer is the only honest one available.

daemon_name / cluster_dir / dashboard Tier 1

result daemon_name()  ·  result cluster_dir()  ·  result dashboard()

The daemon's --name, its cluster directory, and the dashboard URL (an error when no metrics endpoint is configured).

cluster_status / cluster_ls / cluster_show Tier 1

result cluster_status()  ·  result cluster_ls()  ·  result cluster_show(const std::string& name)

A daemon in cluster mode publishes itself into the cluster directory as <name>.json — host, heartbeat, pid, and its runtime table — and discovers peers by reading the same directory. The roster is files, not IPC. cluster_status() is the one real daemon command (cluster:on|off, name:, dir:, host:, and error: when cluster mode was refused). cluster_ls() lists the publishing daemons, one name per line, stale ones included — a heartbeat more than 10 s old is stale, and the timestamp is in the JSON. cluster_show(name) returns that daemon's published JSON raw, deliberately: the format belongs to the publisher, and a second parser in the header would be a second thing that drifts.

auto peers = socketley::ctl::cluster_ls();
// "edge-1\nedge-2\nstore-1"
auto one = socketley::ctl::cluster_show("edge-1");
// {"daemon":"edge-1","host":"...","heartbeat":1787829747,"runtimes":[...]}

cluster_ps(), cluster_group(), cluster_stats() and cluster_watch() exist but refuse immediately with a recipe: they are CLI renderings over the same files (a cross-daemon table, a group filter, a live terminal view), and a library has no terminal to render into. Aggregate cluster_show()'s runtimes arrays instead.

Raw Command

command Tier 1

Send any raw command string to the daemon. Supports glob patterns. The two-argument form lets you target a specific socket path.

Socket Path Resolution

The SDK automatically finds the daemon socket in this order:

  1. SOCKETLEY_SOCKET environment variable
  2. /run/socketley/socketley.sock
  3. /tmp/socketley.sock

Tier 2: Embed Engine

Tier 2 embeds the full socketley engine — io_uring event loop, runtime manager, and all four runtime types — directly in your own binary. Maximum performance (no IPC overhead), full control over the event loop.

Build & Link

Build requirement: Tier 2 requires the socketley source tree and libsocketley_sdk.a (build it with ./bin/premake5 gmake2 && cd make && make config=release_x64 socketley_sdk).
g++ -std=c++23 app.cpp -I. -Iinclude/linux -Ithirdparty/sol2 -Ithirdparty/luajit -Lbin/Release -Lthirdparty/luajit -lsocketley_sdk -luring -lssl -lcrypto -lluajit
The sol2/LuaJIT include paths and -lluajit are not optional extras: core.h pulls the Lua context in by default. To build without Lua, define SOCKETLEY_NO_LUA and link libsocketley_sdk_nolua.a instead.

High-Level Wrapper Classes

The recommended way to use Tier 2. Each wrapper manages its own event loop, runtime manager, and signal handlers internally. All config methods return *this for chaining. start() blocks until SIGINT/SIGTERM — and returns bool: false when the runtime never started (a taken port, a refused TLS or listener configuration), in which case the event loop is not entered at all.

One start() per process — the signal handler points to one event loop. For multi-runtime in a single process, use the raw API below.

Every wrapper constructor takes an optional runtime name (server(9000, "web")), which appears in logs and stats — and on a proxy is load-bearing: see the proxy card. Three wrappers also take an AF_UNIX listener path instead of a port (server("unix:/run/app.sock"), with or without the unix: prefix) — the --listen unix: feature. Port and path are alternatives, never both, which is why the path is a constructor and not a setter. tls() does not combine with a unix listener: the socket node's permissions are what restrict it.

All four wrappers share:

MethodDescription
cpus(spec)Pin the wrapper's I/O thread: "max", "0-3", "0,2,5" — the --cpus spellings. A spec that does not parse is logged and ignored.
sqpoll(bool)Ask for (or decline) an SQPOLL submission poller on the wrapper's ring. A request — the kernel may refuse, and start() logs one line if it does. Must be called before start().
owner(name) / child_policy(p)Ownership hierarchy, as in the daemon
start() → boolRun the loop; blocks. false = runtime never reached running, loop not entered
stop()Request the event loop to stop (callable from any thread or callback)
instance() / manager() / loop()Escape hatches to the raw API
state(), name(), port(), stats(), connection_count(), get_listen_path(), …Introspection; each config setter has a matching getter
No shards(), deliberately. A shard is a worker process forked by the daemon; an embedded wrapper is in-process by construction, and shards_config_refusal refuses any in-process runtime claiming more than one. Sharding an SDK service means running N processes of your binary; on a TCP port they can share it via SO_REUSEPORT.

The default mode makes the server a hub. In mode_inout every inbound line is relayed raw to every other connected client, on top of whatever on_message does with it — two clients on an "echo server" each see the other's traffic. A Lua script that defines a message handler suppresses the relay; a C++ on_message callback does not. A server whose on_message IS the protocol wants mode(mode_in).

Callbacks, Actions & Lifecycle

Callbacks as on the server, minus the connection-table ones: on_start, on_stop, on_connect(int), on_disconnect(int), on_message(string_view), on_tick(double). Action: send(msg). No idle_timeout(): it reaps idle inbound connections, and a client's own connection is redialled the moment it drops.

cli.reconnect(0);  // infinite reconnect

    printf("%.*s\n", (int)msg.size(), msg.data());

return cli.start() ? 0 : 2;
socketley::proxy Tier 2 Proxy

proxy(std::string_view unix_path, std::string_view name = "_sdk_proxy")

High-level TCP/HTTP reverse proxy with load balancing, health checks, circuit breaker and retries.

The name is the URL space. In protocol_http mode the runtime routes by path prefix /<name>/ — a request that does not start with it is answered 404 before any backend is consulted, exactly as the daemon's named proxies behave. proxy(8443, "gw") serves /gw/…; the default name serves /_sdk_proxy/…. The prefix is stripped before the backend sees the path. protocol_tcp has no prefix (and no per-request anything).

Hooks & Callbacks

on_start, on_stop, on_connect(int), on_disconnect(int), on_tick(double) as elsewhere — plus the byte-path hooks:

The hook return contract is not the obvious one. on_proxy_request(cb) / on_proxy_response(cb) take std::optional<std::string>(int fd, std::string_view data):
return std::nullopt; — DROP: the bytes are not forwarded.
return std::string{}; — pass through unmodified (empty = "no edit").
return std::string("…"); — forward this instead of the original.
A hook that returns nullopt meaning "no change" forwards nothing: on HTTP every request then dies at backend_timeout as a 504, and with backend_timeout(0) the client hangs. On protocol_http the request hook runs on the head and again on body chunks; on protocol_tcp on every read.

Actions

peer_ip(fd), close_client(fd), clients(), backends(), backend_health() (vector of {status, address}).

socketley::proxy gw(8443, "gw");
gw.tls("cert.pem", "key.pem")
  .protocol(protocol_http)
  .backend("unix:/tmp/edge-app.sock")
  .sidecar();
return gw.start() ? 0 : 2;

Raw Engine API

For multi-runtime in a single process or custom event loop control, use the raw types (event_loop, runtime_manager, server_instance, etc.) documented below. The wrapper classes use this API internally — access it via the instance(), manager(), and loop() escape hatches.

event_loop

The io_uring event loop drives all I/O. One per process, shared by all runtimes.

event_loop::init Tier 2

bool init()

Initialize the io_uring ring. Must be called before any other event_loop method. Returns false if io_uring setup fails (missing kernel support). SQPOLL is opt-in: set_sqpoll(true) before init(), or SOCKETLEY_SQPOLL=1 in the environment — and a request, not a guarantee: the kernel may refuse, in which case the loop runs without a poller (sqpoll_enabled() says what the ring actually got, sqpoll_requested() what was asked). A ring's polling mode is fixed at creation and cannot change afterwards.

event_loop::set_sqpoll / set_cpus Tier 2

void set_sqpoll(bool on)  ·  void set_cpus(const cpu_set_spec& cpus)

Ring configuration; both must be called before init(). set_cpus bounds the loop thread's CPU set (parse a spec string with parse_cpu_set("0-3", online_cpu_count(), out, err)); under SQPOLL the poller thread is pinned to the set's lowest member, because io_uring takes a CPU number for the poller, not a mask. The wrapper classes expose both as cpus(spec) and sqpoll(bool).

event_loop::run Tier 2

void run()

Enter the main event loop. Blocks until request_stop() is called (typically from a signal handler). Processes io_uring completions and dispatches them to runtime handlers.

event_loop::request_stop Tier 2

void request_stop()

Signal the event loop to stop. Safe to call from signal handlers. The loop exits after the current batch of completions is processed.

Tier 3: Daemon Attach

#include <socketley/attach.h> — header-only, zero dependencies. Register your own process as a runtime in a running daemon.

API

daemon_attach Tier 3

bool socketley::daemon_attach(const std::string& name, const std::string& type, uint16_t port, const std::string& owner = "")

Register the current process with the daemon. After calling, your process appears in socketley ls, socketley stats, and socketley ps. Automatically deregisters on exit() via atexit().

ParameterDescription
nameName to register under
type"server", "client", "proxy", or "cache"
portPort your service is listening on
ownerOptional: parent this entry under an existing runtime, as attach … --owner does. socketley ls shows the hierarchy, and the owner's child policy decides what happens to this entry when the owner goes.

Returns: true if daemon accepted the registration, false if daemon not running (service works standalone) or if it refused — socketley::attach_error() holds the refusal verbatim (empty after a success).

attach_error Tier 3

const std::string& socketley::attach_error()

Why the last daemon_attach() returned false: the daemon's refusal verbatim, or the connect failure. daemon_attach() returns bool because registering is usually best-effort ("run anyway, just unlisted") — this is for the cases where it is not.

daemon_detach Tier 3

void socketley::daemon_detach(const std::string& name)

void socketley::daemon_detach()

Explicitly deregister a runtime. The no-argument form deregisters the name from the last daemon_attach() call.

Lifecycle

The typical Tier 3 pattern:

  1. Start your own server (any framework, any language with C++ FFI)
  2. Call daemon_attach() — registers with daemon
  3. Run your accept loop / event loop
  4. On shutdown: daemon_detach() is called automatically via atexit()
Graceful degradation: If the daemon isn't running, daemon_attach() returns false and your service continues working in standalone mode. This makes Tier 3 safe to use unconditionally.

Managed Mode

When a binary is registered via socketley add, the daemon fork+exec's it with two environment variables:

VariableValue
SOCKETLEY_MANAGED=1Always "1" for managed binaries
SOCKETLEY_NAME=<name>The runtime name assigned by --name or derived from the binary path

daemon_attach() detects these automatically:

  • Uses SOCKETLEY_NAME as the runtime name (overriding the name parameter)
  • Sends --managed flag in the attach IPC command so the daemon updates the existing entry instead of creating a new one
  • Skips the atexit() self-removal — the daemon owns the lifecycle

No code changes are needed in the binary — the same daemon_attach() call works both standalone and managed.

Managed vs Attached: attach gives the daemon visibility only. add gives full lifecycle management: auto-restart on crash (~2s), re-launch on daemon boot, and proper stop/start cycling. See the socketley add command in the CLI reference.

Patterns & Best Practices

Mixed: Tier 2 + Tier 3

Embed the full engine for maximum performance, then register with the daemon for fleet visibility:

#include <socketley/server.h>
#include <socketley/attach.h>

socketley::server srv(9000);
srv.on_message([&](int fd, std::string_view msg) {
    srv.send(fd, msg);
});

// Register with daemon (Tier 3)
socketley::daemon_attach("app_srv", "server", 9000);

srv.start();  // daemon sees the runtime
// daemon_detach() called automatically via atexit()
Multiple runtimes: daemon_attach() can only auto-detach one name via atexit(). For additional runtimes, use socketley::ctl::command("attach ...") and manually detach on shutdown.

Signal Handling

// Always ignore SIGPIPE — io_uring writes CAN trigger it
signal(SIGPIPE, SIG_IGN);

// Use a global event_loop pointer for signal handlers
static event_loop* g_loop = nullptr;
// ... after init ...
g_loop = &loop;

// Graceful shutdown on Ctrl-C / kill
signal(SIGINT,  [](int) { if (g_loop) g_loop->request_stop(); });
signal(SIGTERM, [](int) { if (g_loop) g_loop->request_stop(); });
SIGPIPE is critical. Without signal(SIGPIPE, SIG_IGN), a disconnected client can kill your entire process when io_uring delivers a write to a closed socket.
Wrapper classes handle all of this automatically. socketley::server, socketley::client, socketley::proxy, and socketley::cache install SIGPIPE, SIGINT, and SIGTERM handlers internally. Manual signal setup is only needed with the raw API.

Lua Integration

Tier 2 runtimes can load Lua scripts just like daemon-managed runtimes. The Lua callbacks and C++ callbacks work together — C++ callbacks fire first, then Lua callbacks (if both are set).

auto* srv = static_cast<server_instance*>(mgr.get("chat"));

// Try loading Lua script
bool lua_ok = srv->load_lua_script("chat.lua");
if (!lua_ok) {
    // Fallback to C++ callbacks
    srv->set_on_client_message([srv](int, std::string_view msg) {
        srv->lua_broadcast(msg);
    });
}
Build with -lluajit to enable Lua support, or define SOCKETLEY_NO_LUA to compile without it.
