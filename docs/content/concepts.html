The daemon and the CLI

One binary is both. socketley daemon holds the runtimes; every other invocation sends it one command and prints the answer. Exit status: 0, 1 for bad input, 2 for a fatal error.

A runtime

A runtime has a type (one of the registered types) and a name unique on the daemon. create checks the flags and keeps them; start runs it and loads its script. A failed runtime shows the reason in ls.

Each runtime is its own process, a supervised worker with one io_uring loop on one thread. A crash or runaway script takes down that runtime, not the daemon, and it is restarted.

State that survives

Each runtime's configuration is a JSON file. When the daemon starts, it brings back every runtime and starts those that were running.

Names, ports and addresses

  • Runtimes reach each other by name: --backend api, --cache store.
  • --domain names are served by the entrance, the one proxy on 80 and 443, with certificates it gets itself.
  • --bind keeps a port to one address; --listen unix:/path uses a unix socket instead.

TLS

On a server, cache, proxy or mqtt listener, --tls --cert --key terminates TLS and --ca verifies clients; --acme gets Let's Encrypt certificates. A client or a proxy's https:// backend always verifies the server. Not supported: TLS under limitations.

Several cores

--shards N runs N workers sharing the port; --cpus pins them. On a cache each key has one owning shard. Read sharding before choosing N: the gain depends on the workload.

Scripts

Most types take --lua file, loaded at start and replaced with reload-lua. A runaway callback is ended by a deadline. See Lua scripting.

More than one machine

Daemons sharing a directory see each other's runtimes, and @group backends span machines. See Cluster.

Watching it

socketley stats and daemon stats print live counters. The daemon serves a dashboard and a Prometheus /metrics; a metrics runtime keeps history and sends alerts.
