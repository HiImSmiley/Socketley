A db keeps JSON documents for applications, a game's characters, a shop's orders, a user's settings, each owned by an account of an idp runtime, which reaches its own documents and nobody else's. An application in the browser or on a phone talks to it directly over HTTP with the user's access token; there is no backend to write in between.

socketley create db data -p 9500 --domain data --idp auth \
    --schema /etc/socketley/db.schema --keys /etc/socketley/db.keys -s
socketley data query characters '{"where":{"level":{"gte":5}},"limit":10}'

What it does

  • Documents at /c/collection/id: GET, PUT, PATCH with set/unset/inc/push/pull on dotted paths, DELETE, and POST to make one; every document carries _id, _v (its version and ETag) and _owner, and If-Match writes only at a version.
  • Queries: POST /c/collection/_query with eq ne gt gte lt lte in prefix exists, sorting, paging and counting, answered from the indexes --schema declares.
  • Access per collection: private, owner, shared, public or catalog, set in the schema; server-side keys from --keys for trusted services.
  • Transactions and a change stream, an in-memory --cache, a size bound with --max-bytes.
  • Copies: --replicate follows another db read-only; --backup-dir, --backup-every and --backup-keep take scheduled backups, and socketley <db> backup|restore takes one now.
