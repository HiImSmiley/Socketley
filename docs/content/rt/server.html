A server listens on one port and speaks whatever arrives on it: line-delimited TCP, UDP datagrams, WebSocket and HTTP are told apart per connection from the first bytes, so a browser, a game client and nc can share a port. Without a script it relays: what one client says reaches the others, as --mode and --send-to decide. With a Lua script it is whatever the script makes of it: an API, a chat room, a game loop, a bridge to a cache.

socketley create server chat -p 9000 -s                    # every line reaches every other client
socketley create server echo -p 9001 --send-to sender -s   # answers whoever spoke
socketley create server site -p 8080 --http /srv/site --http-cache -s
socketley create server api -p 9002 --lua api.lua --cache store -s

What it does

  • One port, several protocols. Auto-detection classifies each connection as plain TCP, WebSocket, HTTP or RESP by its first message, and request framing decides how a stream is cut into messages.
  • Static files with --http, from memory with --http-cache, compressed copies with --compress, ETags and range requests. HTML pages get a WebSocket script injected, as the flag's entry says.
  • Lua handlers per message, connection, HTTP request and WebSocket upgrade (Lua scripting), with streaming responses that pace against the client's queue.
  • Relaying: --mode inout|in|out|master and --send-to sender,others,master; master mode lets one password-holding client broadcast.
  • Upstreams with -u host:port: the server dials other servers itself and its script hears them through on_upstream.
  • A cache beside it with --cache name: scripts and clients reach a cache runtime through the server, see cache access via server.
  • Several cores with --shards N: N worker processes share the port through SO_REUSEPORT; see sharding.

Works with

A proxy in front of it for names, TLS and load balancing; a cache behind it for state; a client runtime or another server's -u to chain servers. Its counters reach the metrics runtime and the dashboard without configuration.
