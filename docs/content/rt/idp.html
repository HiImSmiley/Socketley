An idp is an OpenID Connect provider that keeps its own accounts: a user signs in once, and every application that asks it, every route a proxy puts behind --auth idp:, a storage's web interface, the db, the mail server and the dashboard know who they are.

socketley create idp auth -p 9400 --domain auth.example.com \
    --clients /etc/socketley/idp.clients --cookie-domain example.com -s
socketley auth user add smiley --password - --groups admins

What it does

  • OpenID Connect: the authorization code flow with PKCE, refresh tokens, discovery at /.well-known/openid-configuration, keys at /jwks, /userinfo and /logout.
  • Accounts: a fixed random id and fields without a schema; the provider reads name, e-mail, groups, password (scrypt) and a few more, and keeps every other field for the applications. Each change is synced to a journal before it is answered.
  • Sign-in: passwords, a second step, app passwords, and /account where a user changes their own details and signs out everywhere.
  • Applications are listed in --clients: an id, a secret or - for a public client, and its redirect addresses.
  • Tokens for other servers: --resources names resource servers, such as an mcp runtime's https://mcp.example.com/mcp, that an application may ask a token for (RFC 8707). With it set, an MCP client such as Claude Code may also sign in by its client metadata document, after the person allows it on a page that names it, its host and the resource.
  • SSH: with --ssh-ca hours it signs short-lived SSH certificates for signed-in users (socketley ssh-cert) and host certificates.
