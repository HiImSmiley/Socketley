How these numbers are made

  • One machine, one run, interleaved. Every arm, socketley and each reference, is up at the same time on the same pinned core, each with its own port. A pass runs every arm once, in an order that rotates and reverses from pass to pass, and the first pass is thrown away as a warm-up. A clock change on the host therefore moves every arm alike, and a comparison is never made between two runs.
  • The ratio is the median of the per-pass ratios, not the ratio of two medians, and the range across passes is printed beside it. Where that range contains 1.00× the row is not a difference, whatever its median says.
  • CPU beside every rate. Each server's cores are read from /proc around the measured operations; a server at 1.00 core is saturated, so its rate is one core divided by its cost per operation. Client cores are recorded too, and a load generator that reaches a full core is the ceiling being measured, so such a run is not published.
  • The answer is checked. Every HTTP arm is asked for the same path and its body size compared before a pass is timed; a 404 is fast and is never what is measured.
  • The box is quiet. A pass begins only when no build, test suite or foreign server runs on the machine, and one that another workload started during is thrown away and run again.
  • The machine is a virtual one, and that has a direction. It halts an idle vCPU, so every time a server wakes a client that sleeps, the host takes a VM exit, and how many find their client asleep is chance. A server that answers each message with its own write and wakeup (Redis at depth 1, nginx, Mosquitto's fan-out) pays that more often than one that batches, as socketley does: its rates swing between passes, and on hardware without the exit the gap in those rows is smaller. Keeping the vCPUs awake with spinners was tried and refused, because a spinner on a client's core delays that client's own wakeups to the next tick.
  • Same work for each. References run as a production install would: persistence off where socketley's is off, one worker or thread where socketley has one core, the configuration written in each set's notes.

The harness is not part of the repository; the numbers, with the commit, the versions and the date of every set, are in data/bench.json.
