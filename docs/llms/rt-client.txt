# client runtime

Dials a server and holds the connection: TCP, UDP or a unix socket, over TLS, reconnecting

A **client** dials a TCP or UDP peer and keeps the connection. What arrives is printed, saved or handled in Lua.

```
socketley create client feed -t 10.0.0.5:9000 --reconnect 0 -b -s   # print what arrives, reconnect for ever
socketley send feed "subscribe prices"
socketley create client probe -t unix:/run/app.sock --lua probe.lua -s
```

## What it does

- **Any target**: `-t host:port` or `-t unix:/path`; `--udp` for datagrams.
- **Verified TLS**: `--tls`, checked against `--ca` or the system store; no way to skip it.
- **Reconnects**: `--reconnect [n]` backs off up to 16 seconds; `0` retries for ever.
- **Output**: `-b` prints messages (`-bpt` adds name and time); `-w file` saves them.
- **Lua**: `on_connect`, `on_message`, `on_disconnect`; `on_writable` paces sending.

## Works with

Any [server](rt-server.txt) or TCP service. `socketley send` writes through it from the shell.

## Flags

Every flag a client runtime takes, by group.

**Basics**

| flag | value | what it does |
|---|---|---|
| `-p` | int | Port: The port it listens on (a client: the port of its target). |
| `-s` |  | Start now: Start it as soon as it is made. |
| `-g` (--group) | text | Group: Puts it in a group; a proxy with --backend @group reaches every member. |
| `--lua` | path | Lua script: A script with the runtime's callbacks, run at start. |

**Network**

| flag | value | what it does |
|---|---|---|
| `--cpus` | text | CPUs: The CPUs its I/O may run on, as 0-3,6. |

**TLS**

| flag | value | what it does |
|---|---|---|
| `--tls` |  | TLS: Encrypt its transport: terminate TLS on its port, or dial over it. |
| `--cert` | path | Certificate: The PEM certificate (chain allowed) a listener presents. |
| `--key` | path | Key: The PEM key of the certificate. |
| `--ca` | path | CA: On a listener: require client certificates from this CA (mutual TLS). On a client or proxy: the CA its servers are checked against. |

**Limits**

| flag | value | what it does |
|---|---|---|
| `--read-buffer` | size | Read buffer: How much data may pile up from one connection before it is refused; 1M unless given. |
| `--write-buffer` | size | Write buffer: How much unsent data may queue up for one connection before it is dropped; 8M unless given. |
| `--reconnect` | int | Reconnect: Reconnect with backoff when the connection drops: the most attempts, 0 for no limit. |

**Output**

| flag | value | what it does |
|---|---|---|
| `--log` | path | State log: A file it appends each state change to. |
| `-w` | path | Message file: A file every received message is written to. |
| `-b` |  | Print messages: Print every received message. |
| `-bp` |  | …with name: Print them with the runtime's name before each. |
| `-bt` |  | …with time: Print them with the time before each. |
| `-bpt` (-btp) |  | …with time and name: Print them with the time and the name before each. |

**Server**

| flag | value | what it does |
|---|---|---|
| `--udp` |  | UDP: Datagrams instead of a stream. |

**Client**

| flag | value | what it does |
|---|---|---|
| `-t` | text | Target: The server it connects to, host:port. |
| `--mode` | one of inout, in, out | Mode: Both ways, receive only or send only. |
| `--connections` | int | Connections: How many connections it holds to the target, each with its own id; changing it opens or closes them. |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; every client arm on one core, the Go target (clientgen) on four others. Every client on the same one core, the target (a Go program) on four others with headroom: every row records the target's cores, and none used all four. socketley is one client runtime holding every connection (--connections N) with its Lua on_message as the handler; the others are one process with the same logic. Every count is taken at the target: a consumer's count must equal the lines sent, every request's size is checked, and a round trip is the interval between one connection's requests as the target sees them. The firehose rows are bound by the client's core, and every line differs (each carries its index). socketley's script reads them with on_read, walking a view of the read buffer with view:lines(), which makes no string, as Go's ReadSlice hands out a slice of its buffer; Node and Python make a string or a bytes object per line. Written with on_message instead, a Lua string per line, the 64 B row makes about 12.7 million lines a second, and with on_messages, one string per read, about 52 million. Over TLS the 64 B row is bound by the target, whose one goroutine encrypting the stream uses a whole core while socketley's runtime decrypts at about four fifths of its own; the target's cores beside the row say so. Connecting is that one runtime dialling all of them, as the others dial from one process; the memory row is socketley's daemon and the runtime's process together, by proportional set size, divided by the connections, so at 200 it is mostly the two processes' fixed cost. One runtime per connection instead, each made with socketley create ... -s from a shell loop, is a process each: 386 created and connected a second, 243 with TLS, and 1,546 KiB each held.

### Generating load: lines as fast as the connection takes them

tcpkali 1.1.1, Go 1.24.6, 3 passes, 2026-11-10, socketley 81ffa51e.

| case | socketley | tcpkali | Go | socketley vs tcpkali | socketley vs Go |
|---|---|---|---|---|---|
| send: 64 B lines as fast as the connection takes them, TCP | 118.78 M lines/s (1.00 cores) | 103.80 M lines/s (1.00 cores) | 68.00 M lines/s (1.00 cores) | 1.12× (1.09–1.14) | 1.68× (1.60–1.77) |
| send: 4 KiB lines, TCP | 2.45 M lines/s (1.00 cores) | 1.64 M lines/s (1.00 cores) | 1.43 M lines/s (1.00 cores) | 1.50× (1.25–1.58) | 1.69× (1.66–1.79) |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; every sender on one core, the Go sink on four others. Sending as fast as the connection takes it, counted at a sink on other cores. socketley paces with self.pending() and on_writable and sends one line per self.send call; tcpkali repeats its message into large writes; Go makes one buffered write call per line. All are bound by the client's core.

Go 1.24.6, 3 passes, 2026-11-10, socketley 81ffa51e.

### Driving a Redis-protocol server

redis-benchmark 8.0.5, 3 passes, 2026-11-10, socketley 81ffa51e.

| case | socketley | redis-benchmark | socketley vs redis-benchmark |
|---|---|---|---|
| pipelined INCR to a socketley cache, depth 32, 1 connection | 961 K /s (0.56 cores) | 916 K /s (0.62 cores) | 1.06× (1.04–1.06) |
| pipelined INCR to a socketley cache, depth 32, 4 connections | 5.89 M /s (0.85 cores) | 7.34 M /s (0.99 cores) | 0.80× (0.79–0.82) |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; each client on one core, the socketley cache on another. A socketley client runtime sending 32 INCR commands as one message and the next 32 on the 32nd reply, the replies counted with on_read and view:lines() as redis-benchmark counts them in C, against redis-benchmark -P 32 with one thread, both to the same socketley cache on its own core, counted by the cache's own counter. At one connection both wait on the round trip; at four, socketley's runtime holds four connections, as redis-benchmark's one thread does, and the cache is the bound under socketley's client at a whole core, where redis-benchmark is at its own.

### A line from a shell script

socketley, socat 1.8.1.1, bash /dev/tcp, 3 passes, 2026-11-10, socketley 81ffa51e.

| case | socketley, bash builtin | socketley | socat | bash /dev/tcp | socketley vs socketley | socketley vs socat | socketley vs bash /dev/tcp |
|---|---|---|---|---|---|---|---|
| one line from the shell, 1,000 in a row | 27 K lines/s (0.99 cores) | 1.4 K lines/s (1.00 cores) | 1.2 K lines/s (1.00 cores) | 33 K lines/s (0.98 cores) | 19.61× (19.18–19.85) | 23.18× (22.84–23.50) | 0.83× (0.76–0.93) |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; the shell loop on one core, the Go sink on four others. One line per command from a shell loop, until the sink has the last one. socketley send writes onto the connection a client runtime holds, a program started a line; with the bash builtin (enable -f socketley-bash.so socketley) the same command is a request to the daemon from the shell itself over one connection it keeps; socat opens a connection per line (nodelay); bash's /dev/tcp is a builtin with no process to start, bound by the connection set-up alone.
