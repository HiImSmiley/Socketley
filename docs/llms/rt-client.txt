# client runtime

Dials a server and holds the connection: TCP, UDP or a unix socket, over TLS, reconnecting

A **client** dials a TCP or UDP peer and keeps the connection. What arrives is printed, saved or handled in Lua.

```
socketley create client feed -t 10.0.0.5:9000 --reconnect 0 -b -s   # print what arrives, reconnect for ever
socketley send feed "subscribe prices"
socketley create client probe -t unix:/run/app.sock --lua probe.lua -s
```

## What it does

- **Any target**: `-t host:port` or `-t unix:/path`; `--udp` for datagrams.
- **Verified TLS**: `--tls`, checked against `--ca` or the system store; no way to skip it.
- **Reconnects**: `--reconnect [n]` backs off up to 16 seconds; `0` retries for ever.
- **Output**: `-b` prints messages (`-bpt` adds name and time); `-w file` saves them.
- **Lua**: `on_connect`, `on_message`, `on_disconnect`; `on_writable` paces sending.

## Works with

Any [server](rt-server.txt) or TCP service. `socketley send` writes through it from the shell.

## Flags

Every flag a client runtime takes, by group.

**Basics**

| flag | value | what it does |
|---|---|---|
| `-p` | int | Port: The port it listens on (a client: the port of its target). |
| `-s` |  | Start now: Start it as soon as it is made. |
| `-g` (--group) | text | Group: Puts it in a group; a proxy with --backend @group reaches every member. |
| `--lua` | path | Lua script: A script with the runtime's callbacks, run at start. |

**Network**

| flag | value | what it does |
|---|---|---|
| `--cpus` | text | CPUs: The CPUs its I/O may run on, as 0-3,6. |

**TLS**

| flag | value | what it does |
|---|---|---|
| `--tls` |  | TLS: Encrypt its transport: terminate TLS on its port, or dial over it. |
| `--cert` | path | Certificate: The PEM certificate (chain allowed) a listener presents. |
| `--key` | path | Key: The PEM key of the certificate. |
| `--ca` | path | CA: On a listener: require client certificates from this CA (mutual TLS). On a client or proxy: the CA its servers are checked against. |

**Limits**

| flag | value | what it does |
|---|---|---|
| `--read-buffer` | size | Read buffer: How much data may pile up from one connection before it is refused; 1M unless given. |
| `--write-buffer` | size | Write buffer: How much unsent data may queue up for one connection before it is dropped; 8M unless given. |
| `--reconnect` | int | Reconnect: Reconnect with backoff when the connection drops: the most attempts, 0 for no limit. |

**Output**

| flag | value | what it does |
|---|---|---|
| `--log` | path | State log: A file it appends each state change to. |
| `-w` | path | Message file: A file every received message is written to. |
| `-b` |  | Print messages: Print every received message. |
| `-bp` |  | …with name: Print them with the runtime's name before each. |
| `-bt` |  | …with time: Print them with the time before each. |
| `-bpt` (-btp) |  | …with time and name: Print them with the time and the name before each. |

**Server**

| flag | value | what it does |
|---|---|---|
| `--udp` |  | UDP: Datagrams instead of a stream. |

**Client**

| flag | value | what it does |
|---|---|---|
| `-t` | text | Target: The server it connects to, host:port. |
| `--mode` | one of inout, in, out | Mode: Both ways, receive only or send only. |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; every client arm on one core, the Go target (clientgen) on four others. Every client on the same one core, the target (a Go program) on four others with headroom: every row records the target's cores, and none used all four. socketley is one client runtime per connection with its Lua on_message as the handler; the others are one process with the same logic. Every count is taken at the target: a consumer's count must equal the lines sent, every request's size is checked, and a round trip is the interval between one connection's requests as the target sees them. The firehose rows are bound by the client's core, where socketley calls Lua once per line. With 64 connections socketley is 64 processes on one core, so a request costs a context switch, and a connection holds a process's memory. Connecting is creating a runtime each (socketley create ... -s from a shell loop), where the others dial from one process.

### Generating load: lines as fast as the connection takes them

tcpkali 1.1.1, Go 1.24.6, 3 passes, 2026-11-09, socketley 7171898a.

| case | socketley | tcpkali | Go | socketley vs tcpkali | socketley vs Go |
|---|---|---|---|---|---|
| send: 64 B lines as fast as the connection takes them, TCP | 23.77 M lines/s (1.00 cores) | 98.66 M lines/s (1.00 cores) | 68.27 M lines/s (1.00 cores) | 0.24× (0.22–0.27) | 0.35× (0.34–0.35) |
| send: 4 KiB lines, TCP | 2.35 M lines/s (1.00 cores) | 1.56 M lines/s (1.00 cores) | 1.39 M lines/s (1.00 cores) | 1.50× (1.47–1.85) | 1.74× (1.66–2.07) |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; every sender on one core, the Go sink on four others. Sending as fast as the connection takes it, counted at a sink on other cores. socketley paces with self.pending() and on_writable and sends one line per self.send call; tcpkali repeats its message into large writes; Go makes one buffered write call per line. All are bound by the client's core.

### Generating load over a unix socket and TLS

Go 1.24.6, 3 passes, 2026-11-09, socketley 7171898a.

| case | socketley | Go | socketley vs Go |
|---|---|---|---|
| send: 64 B lines, unix socket | 24.24 M lines/s (1.00 cores) | 162.00 M lines/s (1.00 cores) | 0.15× (0.14–0.18) |
| send: 64 B lines, TLS 1.3 | 21.77 M lines/s (1.00 cores) | 33.08 M lines/s (1.00 cores) | 0.67× (0.65–0.69) |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; every sender on one core, the Go sink on four others. The same over a unix socket and over TLS 1.3, which tcpkali does not speak. Over TLS Go's rate takes one of two levels from pass to pass in every run, about 21 or 33-37 million lines a second, while socketley's stays at 20-22 million; the median falls on whichever level most passes took.

### Driving a Redis-protocol server

redis-benchmark 8.0.5, 3 passes, 2026-11-09, socketley 7171898a.

| case | socketley | redis-benchmark | socketley vs redis-benchmark |
|---|---|---|---|
| pipelined INCR to a socketley cache, depth 32, 1 connection | 904 K /s (0.60 cores) | 919 K /s (0.62 cores) | 0.98× (0.98–0.98) |
| pipelined INCR to a socketley cache, depth 32, 4 connections | 2.02 M /s (1.00 cores) | 7.28 M /s (0.99 cores) | 0.28× (0.27–0.28) |

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; each client on one core, the socketley cache on another. A socketley client runtime sending 32 INCR commands as one message and the next 32 on the 32nd reply, against redis-benchmark -P 32 with one thread, both to the same socketley cache on its own core, counted by the cache's own counter. At one connection both wait on the round trip; at four, socketley is four processes on one core.
