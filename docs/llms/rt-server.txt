# server runtime

TCP, UDP, WebSocket and HTTP on one port, answered by Lua or by a built-in path

A **server** is one port for long-lived connections: TCP lines, WebSocket, HTTP and RESP on the same port, or UDP datagrams. Without a script it relays messages between clients; with Lua it answers them, as a chat room, a game server, a line protocol or an API.

```
socketley create server chat -p 9000 -s                    # every line reaches every other client
socketley create server echo -p 9001 --send-to sender -s   # answers whoever spoke
socketley create server room -p 9003 --lua room.lua -s     # the script decides who hears what
socketley create server site -p 8080 --http /srv/site --http-cache -s
socketley create server api -p 9002 --lua api.lua --cache store -s
```

```
-- room.lua: whoever sends "join" hears everything said in the room
function on_client_message(id, msg)
  if msg == "join" then self.join_group(id, "room") else self.group_send("room", msg) end
  return true   -- handled, so nothing is relayed on its own
end
```

> Warning: `--cache` also stores every ordinary message in the cache, under keys `1`, `2`, `3`… And `--http` injects a WebSocket script into every HTML page.

## What it does

- **One port, four protocols**: TCP lines, WebSocket, HTTP and RESP, [told apart by their first bytes](man-server-flags.txt); `--udp` for datagrams, where `on_client_message` names the peer and `self.send` answers it.
- **Lua per message**: `on_client_message` answers with `self.send` and returns `true` to keep the relay out; connects, disconnects, requests and upgrades have callbacks too. See [Lua](lua.txt).
- **Broadcast and rooms**: `self.broadcast` reaches everyone, `self.multicast` a list, `self.join_group` and `self.group_send` a room.
- **Relaying without code**: `--mode` and `--send-to` decide who hears a message; `--send-to sender` is an echo server.
- **HTTP on the same port**: `on_http_request` answers requests; `--http` serves a directory, `--http-cache` holds it in memory.
- **TLS and unix sockets**: `--tls --cert --key` encrypt the port, `--ca` asks for client certificates; `--listen unix:/path` serves a local socket.
- **Upstreams and a cache**: `-u host:port` dials other servers for `on_upstream`; with `--cache name`, clients send `cache <command>` ([cache access](man-server-flags.txt)).
- **Several cores**: `--shards N` runs N processes on one port, and a broadcast reaches every shard's clients; see [sharding](man-server-flags.txt).

## Works with

A [proxy](rt-proxy.txt) in front for names and TLS, a [cache](rt-cache.txt) behind for state, a [client](rt-client.txt) to chain servers. Its counters reach [metrics](rt-metrics.txt) without setup.

## Flags

Every flag a server runtime takes, by group.

**Basics**

| flag | value | what it does |
|---|---|---|
| `-p` | int | Port: The port it listens on (a client: the port of its target). |
| `-s` |  | Start now: Start it as soon as it is made. |
| `-g` (--group) | text | Group: Puts it in a group; a proxy with --backend @group reaches every member. |
| `--lua` | path | Lua script: A script with the runtime's callbacks, run at start. |
| `--lua-ffi` |  | Lua FFI: Let the script require("ffi"): LuaJIT's calls into C and raw memory, where a wrong pointer ends the runtime's process. |

**Network**

| flag | value | what it does |
|---|---|---|
| `--bind` | text | Bind address: Bind the port to this address only, such as 127.0.0.1 when only a proxy on this machine should reach it. |
| `--listen` | text | Unix socket: Listen on a unix socket instead of a port. |
| `--shards` | int | Shards: Worker processes sharing the port: the way one runtime uses more than one core. |
| `--domain` | list | Names: The names it is reached by through the entrance; empty for its own name. |
| `--cpus` | text | CPUs: The CPUs its I/O may run on, as 0-3,6. |

**TLS**

| flag | value | what it does |
|---|---|---|
| `--tls` |  | TLS: Encrypt its transport: terminate TLS on its port, or dial over it. |
| `--cert` | path | Certificate: The PEM certificate (chain allowed) a listener presents. |
| `--key` | path | Key: The PEM key of the certificate. |
| `--ca` | path | CA: On a listener: require client certificates from this CA (mutual TLS). On a client or proxy: the CA its servers are checked against. |
| `--acme` | list | ACME names: Names to get a Let's Encrypt certificate for, renewed by itself. |
| `--acme-email` | text | ACME e-mail: The address the CA writes to about the certificate. |

**Limits**

| flag | value | what it does |
|---|---|---|
| `--max-connections` (--max-conn) | int | Max connections: The most clients at once. |
| `--rate-limit` | int | Rate limit: Messages a second per connection. |
| `--global-rate-limit` | int | Global rate limit: Messages a second over all connections. |
| `--congestion` | text | Congestion control: The kernel's congestion control for its connections, such as bbr, which keeps its rate up under packet loss. |
| `--idle-timeout` | duration | Idle timeout: Close a connection that has received nothing for this long; off unless given. |
| `--read-buffer` | size | Read buffer: How much data may pile up from one connection before it is refused; 1M unless given. |
| `--write-buffer` | size | Write buffer: How much unsent data may queue up for one connection before it is dropped; 8M unless given. |
| `--drain` |  | Drain on stop: Finish what is in flight before stopping. |

**Output**

| flag | value | what it does |
|---|---|---|
| `--log` | path | State log: A file it appends each state change to. |
| `-w` | path | Message file: A file every received message is written to. |
| `-b` |  | Print messages: Print every received message. |
| `-bp` |  | …with name: Print them with the runtime's name before each. |
| `-bt` |  | …with time: Print them with the time before each. |
| `-bpt` (-btp) |  | …with time and name: Print them with the time and the name before each. |

**Server**

| flag | value | what it does |
|---|---|---|
| `--mode` | one of inout, in, out, master | Mode: Who talks: both ways, in only, out only, or one master broadcasting. |
| `--send-to` | list | Answer to: Who the built-in path answers: sender, others, master. |
| `--udp` |  | UDP: Datagrams instead of a stream. |
| `--http` | path | Static files: Serve this directory over HTTP. |
| `--http-cache` |  | Files in memory: Read the static files into memory at start. |
| `--compress` |  | Compressed copies: Serve a file's .br or .gz copy next to it to clients that accept it, unless the copy is older than the file. |
| `--no-inject` |  | Pages as they are: Serve each page exactly as the file holds it, without the WebSocket script. |
| `--master-pw` | text | Master password: The password that claims master mode. |
| `--no-master-pw` |  | No master password: Take the master password away, which ends master mode. |
| `--cache` | text | Cache: A cache runtime its scripts and clients use. |
| `--origins` | list | Web origins: Other web origins whose pages may open a WebSocket to it; * for any. |
| `-u` (--upstream) | list | Upstreams: Servers it relays to, host:port each. |

## Benchmarks

A ratio (×) is how many times better socketley did: more per second, or less time, memory or CPU; above 1× socketley is ahead. The range in brackets is the lowest and highest ratio across the passes.

### WebSocket: echo and a chat room's fan-out

socketley, Lua script, ws 8.22.0 (Node 24.22.1), uWebSockets.js 20.71.0 (Node 24.22.1), 3 passes, 2026-11-10, socketley 81ffa51e.

| case | socketley | socketley, Lua script | ws 8.22.0 (Node 24.22.1) | uWebSockets.js 20.71.0 (Node 24.22.1) | socketley vs socketley, Lua script | socketley vs ws 8.22.0 (Node 24.22.1) | socketley vs uWebSockets.js 20.71.0 (Node 24.22.1) |
|---|---|---|---|---|---|---|---|
| echo, 64 B messages, 256 connections, one in flight each | 320 K msg/s (1.00 cores) | 303 K msg/s (1.00 cores) | 151 K msg/s (1.00 cores) | 232 K msg/s (1.00 cores) | 1.05× (1.05–1.07) | 2.09× (2.08–2.17) | 1.38× (1.34–1.41) |
| room fan-out: 1 sender to 100 receivers, 64 B | 6.15 M msg/s (1.00 cores) | 6.13 M msg/s (1.00 cores) | 305 K msg/s (1.00 cores) | 5.40 M msg/s (1.00 cores) | 1.01× (1.00–1.01) | 20.27× (20.10–20.44) | 1.14× (1.13–1.15) |
| room fan-out: 1 sender to 1,000 receivers, 64 B | 6.25 M msg/s (1.00 cores) | 6.26 M msg/s (1.00 cores) | 293 K msg/s (1.00 cores) | 5.73 M msg/s (1.00 cores) | 1.00× (0.97–1.01) | 21.28× (21.19–22.75) | 1.09× (1.09–1.10) |

How it was measured: srvgen (Go), 4 s a run, every answer checked; each server on one core (ws and uWebSockets.js under Node 24), srvgen on 20 others. The same logic in each: an echo, and a room that a receiver enters by sending "join", with one sender's messages counted at every receiver. socketley runs it on its built-in relay, and as "socketley, Lua script" in Lua (join_group/group_send); ws loops over the room with send(), uWebSockets.js publishes to a topic. Both socketley and uWebSockets.js build a room's frame once; socketley writes each receiver's share of a turn in one send, and uWebSockets.js corks its writes.

### TCP line protocol, answered by a handler

socketley, Lua script, Node 24.22.1 net, Go 1.24.6 net, 3 passes, 2026-11-10, socketley 81ffa51e.

| case | socketley | socketley, Lua script | Node 24.22.1 net | Go 1.24.6 net | socketley vs socketley, Lua script | socketley vs Node 24.22.1 net | socketley vs Go 1.24.6 net |
|---|---|---|---|---|---|---|---|
| line echo, 64 B, 256 connections, one in flight each | 329 K msg/s (1.00 cores) | 313 K msg/s (1.00 cores) | 199 K msg/s (1.00 cores) | 227 K msg/s (1.00 cores) | 1.05× (1.05–1.05) | 1.65× (1.64–1.68) | 1.46× (1.44–1.46) |
| line echo, 64 B, 64 connections, 16 pipelined each | 4.63 M msg/s (1.00 cores) | 4.48 M msg/s (1.00 cores) | 2.32 M msg/s (1.00 cores) | 3.24 M msg/s (1.00 cores) | 1.04× (1.03–1.05) | 2.00× (1.99–2.05) | 1.43× (1.42–1.46) |

How it was measured: srvgen (Go), 4 s a run, every answer checked; each server on one core, srvgen on 20 others. Every line is answered with itself by a handler: socketley's built-in echo, and as "socketley, Lua script" a Lua on_client_messages, handed a read's lines in one call and answering them with one self.send; on Node's net a function over the read's lines, written with one write a read; in Go a goroutine with bufio. With one line in flight the kernel's per-message cost dominates; 16 pipelined lines show each server's own per-line work, where a script with on_client_message, a call and a string a line, makes about 3.2 million a second.

### HTTP: static files and a fixed answer

nginx 1.28.3, 3 passes, 2026-11-10, socketley 0174a7a1.

| case | socketley | nginx | socketley vs nginx |
|---|---|---|---|
| 1 KiB file, keep-alive, 256 connections | 271 K req/s (1.00 cores) | 50 K req/s (0.99 cores) | 5.46× (5.42–5.51) |
| 64 KiB file, keep-alive, 256 connections | 93 K req/s (1.00 cores) | 47 K req/s (0.99 cores) | 2.00× (1.98–2.16) |
| 1 KiB file, a connection per request, 64 at once | 83 K req/s (0.99 cores) | 35 K req/s (1.00 cores) | 2.36× (2.33–2.48) |
| fixed answer (Lua handler / nginx return), keep-alive | 246 K req/s (1.00 cores) | 77 K req/s (0.99 cores) | 3.22× (3.08–3.54) |

How it was measured: wrk 8 threads, 4 s a run; each server on one core, wrk on 20 others. socketley --http dir --http-cache against nginx with one worker, sendfile, open_file_cache and access logs off. Files are .txt: socketley adds a WebSocket script to every .html it serves, by design. The fixed answer is a Lua on_http_request on socketley and a return 200 on nginx, which runs no script at all. Read the 1 KiB keep-alive row with this machine in mind: nginx answers each request with its own write and wakeup, and on this VM waking a halted vCPU costs an exit, which costs a server that does that more than one that batches. A single unpublished pass on another VM (16 cores) read 1.85× for the same row. The kernel keeps at most 2,048 connections in TIME-WAIT for every arm (net.ipv4.tcp_max_tw_buckets, 131,072 by default), so a pass with a connection per request does not wait out the closed connections of the one before.

### HTTP on four cores

nginx 1.28.3, 3 passes, 2026-11-10, socketley 0174a7a1.

| case | socketley | nginx | socketley vs nginx |
|---|---|---|---|
| 1 KiB file, keep-alive, 256 connections | 500 K req/s (3.99 cores) | 230 K req/s (3.99 cores) | 2.17× (2.15–2.25) |
| 64 KiB file, keep-alive, 256 connections | 229 K req/s (3.98 cores) | 166 K req/s (3.99 cores) | 1.38× (1.36–1.40) |
| 1 KiB file, a connection per request, 64 at once | 158 K req/s (3.94 cores) | 131 K req/s (3.90 cores) | 1.21× (1.21–1.21) |
| fixed answer (Lua handler / nginx return), keep-alive | 451 K req/s (3.99 cores) | 297 K req/s (3.98 cores) | 1.52× (1.46–1.54) |

How it was measured: wrk 16 threads, 4 s a run; socketley as four shards and nginx with four workers, each pinned to one of the same four cores; wrk (16 threads) on 20 others. The same rows as the one-core set, the same wrk for both. socketley spends about twice the CPU a request here that it does on one core, and most of that is the client, not the shards: wrk's threads each hold connections on all four shards, and waking a thread from another core is an interrupt the server's core pays for on loopback, a VM exit on this VM. With one wrk per quarter of the connections, four shards cost about 15% more a request than four separate one-core servers. A client on another machine costs neither. The kernel keeps at most 2,048 connections in TIME-WAIT for every arm (net.ipv4.tcp_max_tw_buckets, 131,072 by default), so a pass with a connection per request does not wait out the closed connections of the one before.
