# server runtime

TCP, UDP, WebSocket and HTTP on one port, answered by Lua or by a built-in path

A **server** listens on one port and talks to whoever connects. Without a script it relays messages between clients; with Lua it becomes an API, a chat room or a game loop.

```
socketley create server chat -p 9000 -s                    # every line reaches every other client
socketley create server echo -p 9001 --send-to sender -s   # answers whoever spoke
socketley create server site -p 8080 --http /srv/site --http-cache -s
socketley create server api -p 9002 --lua api.lua --cache store -s
```

> Warning: `--cache` also stores every ordinary message in the cache, under keys `1`, `2`, `3`… And `--http` injects a WebSocket script into every HTML page.

## What it does

- **One port, several protocols**: TCP, WebSocket, HTTP and RESP, [told apart by their first bytes](man-server-flags.txt); `--udp` for datagrams.
- **Static files**: `--http` serves a directory; `--http-cache` holds it in memory.
- **Lua handlers**: Per message, connection, HTTP request and WebSocket upgrade; see [Lua](lua.txt).
- **Relaying without code**: `--mode` and `--send-to` decide who hears a message.
- **Upstreams**: `-u host:port` dials other servers; the script hears them in `on_upstream`.
- **A cache beside it**: With `--cache name`, clients send `cache <command>`; see [cache access](man-server-flags.txt).
- **Several cores**: `--shards N` runs N processes on one port; see [sharding](man-server-flags.txt).

## Works with

A [proxy](rt-proxy.txt) in front for names and TLS, a [cache](rt-cache.txt) behind for state, a [client](rt-client.txt) to chain servers. Its counters reach [metrics](rt-metrics.txt) without setup.

## Benchmarks

A ratio (×) is how many times better socketley did: more per second, or less time, memory or CPU; above 1× socketley is ahead. The range in brackets is the lowest and highest ratio across the passes.

### HTTP: static files and a fixed answer

nginx 1.28.3, 9 passes, 2026-11-03, socketley c7d4c42b.

| case | socketley | nginx | socketley vs nginx |
|---|---|---|---|
| 1 KiB file, keep-alive, 256 connections | 281 K req/s (1.00 cores) | 52 K req/s (1.00 cores) | 5.31× (4.95–5.82) |
| 64 KiB file, keep-alive, 256 connections | 93 K req/s (1.00 cores) | 45 K req/s (1.00 cores) | 2.08× (1.98–2.13) |
| 1 KiB file, a connection per request, 64 at once | 87 K req/s (1.00 cores) | 33 K req/s (1.00 cores) | 2.64× (2.56–2.86) |
| fixed answer (Lua handler / nginx return), keep-alive | 225 K req/s (1.00 cores) | 76 K req/s (1.00 cores) | 2.88× (2.82–3.08) |

Caveat: likely higher on this VM than on hardware; see the notes.

How it was measured: wrk 8 threads, 8 s a run; each server on one core, wrk on 20 others. socketley --http dir --http-cache against nginx with one worker, sendfile, open_file_cache and access logs off. Files are .txt: socketley adds a WebSocket script to every .html it serves, by design. The fixed answer is a Lua on_http_request on socketley and a return 200 on nginx, which runs no script at all. Read the 1 KiB keep-alive row with this machine in mind: nginx answers each request with its own write and wakeup, and on this VM waking a halted vCPU costs an exit, which costs a server that does that more than one that batches. A single unpublished pass on another VM (16 cores) read 1.85× for the same row.

## The manual on server

#### `--mode mode`

Sets the direction messages flow: **inout** (bidirectional, default), **in** (receive only), **out** (send only), or **master** (one client claims master, and only the master's messages are broadcast).

The mode alone does not decide who receives a message. In **inout** with no script, every message is repeated to the other connections but not to the one that sent it. So a single client talking to itself hears nothing, and a second client hears everything. See **--send-to**.

The server holds relayed messages for a connection until it knows which protocol the connection speaks. It then delivers them in that protocol's framing, so a WebSocket client receives them as frames rather than as raw text. A connection is classified by its first message. Without the hold, a client whose first move is an HTTP request or a WebSocket upgrade would receive relay bytes ahead of the response it is waiting for, which corrupts the handshake.

A client that connects and sends nothing is served anyway, after a delay of at most 250 ms. From then on it is treated as a plain line-delimited TCP client. Such a client has nothing outstanding for the relayed bytes to arrive ahead of, so there is no handshake to protect. The delay is paid once per connection, not once per message: everything relayed after the first delivery goes out immediately. A client that has sent part of a request is not covered by this. It is held until its request completes, however long that takes, because it is waiting for an answer, and the answer must come first.

The hold is capped at 64 KB per connection. Past that, the oldest held messages are dropped to make room. So a client that stays silent through more than 64 KB of relay traffic in under 250 ms receives the most recent messages, not the whole backlog. The cap applies only before classification. Once a connection is classified, relay traffic goes straight to its write queue, and the ordinary **--max-connections** and write-queue limits apply instead.

A connection that speaks HTTP is not in the relay set. It receives no relayed messages at all, starting from the request that identifies it as HTTP. HTTP has no framing for a message the server sends on its own. Before a response, such a message replaces the status line the client is parsing for. Between two keep-alive requests, it is read as the status line of the next response. It would never be well formed, so it is not sent at all rather than delayed. A WebSocket connection is unaffected: it starts over HTTP, but once upgraded it has framing for server-initiated messages and receives everything. That is the supported way for a browser client to receive relay traffic.

A connection that speaks RESP is excluded for the same reasons, starting from the command that identifies it as RESP. RESP2 matches replies to commands only by their order on the stream, so a relayed message would be read as the reply to the client's next command. Also, the relay writes the message text, not a RESP value, so a Redis client reads a plain letter where a type byte belongs and answers with a protocol error. Encoding the message as a value would not help. The only channel RESP2 has for a server-initiated value is pub/sub, which the client enters with SUBSCRIBE, and a server runtime does not implement it. A RESP client on a relaying server still receives its own replies, anything a script addresses to it by client id, and the answers to **cache <command>** messages. What it no longer receives is other clients' traffic.

#### `--send-to who[,who...]`

Sets who receives a message on the built-in path when no script handles it. The value is a comma separated set of recipients: **sender** (the connection the message came from), **others** (every other connection except the master), and **master** (the master connection, which only **--mode master** has).

The recipients do not overlap, so they combine: **--send-to sender,others** reaches everyone including the sender, and **--send-to sender,master** answers the sender and sends the master a copy. That is why there is no **all** recipient: **sender,others** already says it, and the flag avoids one behaviour under two spellings.

When the flag is not set, each mode keeps its usual behaviour: **inout** sends to **others**, and **master** drops what a non-master says.

In **--mode master**, the flag decides what happens to a NON-master's message. The master's own message still reaches everyone else, which is what the mode means. **--send-to master** forwards the message with a prefix: the sender's descriptor stays in front of the line, so the master can tell two clients apart. **--send-to others,master** makes a moderated room that the master reads along with.

Invalid recipients are refused rather than accepted and ignored. Modes **in** and **out** answer nobody at all, so they refuse the flag. The **master** recipient names a connection that no other mode has, so only master mode accepts it.

In **inout**, and for the master's own messages in **master**, a script's **on_message** takes precedence over every recipient. When it is defined, nothing is sent automatically, and **self.send** or **self.broadcast** decides. A non-master's message in **master** mode never reaches **on_message** at all, only **on_client_message**, which does not suppress anything. So there the recipients apply whether or not a script is loaded.

Unset, UDP and TCP both send to **others**. Before this flag existed, a UDP sender also received its own datagram back, while a TCP sender did not. **--send-to sender,others** gives that old UDP behaviour.

#### `--udp`

Uses UDP instead of TCP. The server binds a single SOCK_DGRAM socket. A peer is registered automatically on its first datagram. Each datagram is one message, with no line parsing. Broadcast sends to all known peers with sendto(). Not available for cache or proxy.

**An exposed UDP server can reflect traffic.** With no Lua handler, every datagram is relayed to every other peer that has sent one. A peer is learned from a source address, which a sender can forge. Keep such a server on a trusted network, or give it a Lua handler that decides.

Refused with **--mode master**. Master mode claims a connection as the master, and a datagram is not a connection, so the pair is worse than useless. Without the refusal, a datagram beginning with **master** would reach that code with no sender and take the worker down.

#### `--master-pw password`

A static password for master mode authentication. A client sends "master <password>" to claim the master role. Only one master exists at a time, and the role is released on disconnect. For dynamic authentication, use the **on_master_auth(client_id, password)** Lua callback instead.

Failed attempts are counted per source address. Once an address has failed ten attempts within sixty seconds, its connections are refused at accept, before a byte is read. The count decays after sixty seconds of quiet. This is a property of master mode, not of this flag, so it applies to whichever of the two authenticators is in use.

Requires **--mode master**, and is refused without it. The **master** prefix is read in only one place. In any other mode the password is not a credential but an ordinary message, and a client that sends it has its password relayed verbatim to every other connection.

#### `--no-master-pw`

Removes the password from a server that has one. Only **edit** accepts it. This is what makes leaving master mode possible: **--master-pw** and **--mode master** are checked as a pair, so a mode change alone is refused while the password remains. It needs a flag of its own because an empty string passed to **--master-pw** cannot express it. The daemon receives one line and splits it on whitespace, so an empty argument does not survive the wire. It arrives as the flag with nothing after it.

#### `--origins list`

Lists the web origins, besides the server's own, whose pages may open a WebSocket to this server. The list is comma-separated, such as **https://app.example.com**. * admits any origin.

The server refuses a handshake whose **Origin** is not in the list and is not the **Host** the handshake was sent to (or the **X-Forwarded-Host** set by a proxy in front). It answers **403 Forbidden** and closes the connection. This stops a page on another site from driving the server, or the cache linked to it, through the browser of someone who can reach them. A client that sends no **Origin** is not affected, and only browsers send one.

#### `--http directory`

Serve static files from the given directory over HTTP. When a browser sends a plain HTTP GET request (one without a WebSocket upgrade header), the server answers with the requested file. GET / serves index.html. The server injects a WebSocket connection script before </head> in every HTML file (.html, .htm).

**Note that this modifies the HTML it serves.** Every .html and .htm response is rewritten as it is sent. Documents this server did not author, such as uploads, a generated report or a third-party page, are therefore delivered altered: they carry a script that opens a WebSocket back to this runtime. No flag turns this off. If you do not want it, serve those files with something else.

Content-Type is detected from the file extension. Every file response carries an **ETag** built from the file's inode, modification time and size. A request whose **If-None-Match** names that ETag is answered **304** with no body. The server sends no **Last-Modified**, so a browser asks again on every load instead of trusting a copy it guessed was fresh. A changed or replaced file is therefore always sent anew. WebSocket upgrades still work on the same port. Only GET requests are served; other HTTP methods fall through to raw TCP handling.

**Range requests.** Every whole-file response carries **Accept-Ranges: bytes**. A request with a **Range** field is answered **206 Partial Content**. Its **Content-Range** states the file's whole length, and its **Content-Length** states the length of the slice. This lets a media player seek and an interrupted download resume. Without it, a player scrubs by downloading from the beginning, and Safari does not play **<video>** at all. The server accepts all three forms:

```
Range: bytes=0-499      the first 500 bytes
Range: bytes=500-       from 500 to the end
Range: bytes=-500       the last 500 bytes
```

An end past the file is clamped to the last byte. A range that starts at or past the end is answered **416 Range Not Satisfiable** with **Content-Range: bytes */<length>**. This is how a client that was not told the length learns it.

Two kinds of request are deliberately answered with the whole file instead. A multi-range request (**bytes=0-9,20-29**) would need a **multipart/byteranges** body, which the server does not produce. RFC 9110 14.2 permits ignoring the field, and the whole file is more useful than a wrong slice. A range on **.html** or **.htm** is also ignored, because the injected script described above changes the body's length. A byte offset into the file is therefore not an offset into the response. Those responses do not send **Accept-Ranges** either, so no client is invited to make a seek the server cannot honour.

**Concurrency of the zero-copy path.** The server sends a file with **sendfile**(2) from the event loop. The socket is made non-blocking for that call only, so no pipe is held and nothing limits how many files are sent at once. Compared with the io_uring splice it replaced, a 2 MiB file costs 85 us of CPU instead of 158, and 64 slow readers hold no kernel threads instead of 64. When a window of the file is not in the page cache, the server splices that window through a pipe instead, so the event loop never waits on the disk. The rest of this section is about that pipe.

In the table below, the before column is the earlier design. It sent every file with **splice**(2) through a pipe, which keeps the bytes out of user space entirely. It had one pipe per runtime, so only one connection at a time could use the splice path. Every other connection fell back to a read into memory followed by a write. Measured on 4 MiB files, seven interleaved passes of each build:

```
concurrent   before      after     factor
1            2.9 ms      2.9 ms     0.98
2           11.9 ms      4.2 ms     2.80
4           26.1 ms      5.3 ms     4.97
8           55.8 ms     10.5 ms     5.33
```

Each connection now makes its own pipe. The number of pipes is limited by a budget in bytes, not by a count: 64 MB of kernel pipe, divided by the pipe size. The pipe size follows **--write-buffer**, capped at 1 MB. So the default allows 64 pipes. A runtime configured with a small buffer because it serves many streams gets MORE pipes out of the same budget, not fewer. Past that count, the remaining connections use the read path.

A file takes this path from 64 KiB upward on a plaintext connection. Only a window that is not in the page cache needs a pipe, so a server of warm images never reaches this budget. A server that does reach it falls back to the read path.

This boundary is worth knowing, because the fallback is not merely slower. Worker throughput and RSS on 4 MiB files:

```
                     at/below the count      past it
default (64)         12.7-14.2 GB/s          1.20 GB/s
                     RSS 35 MB               RSS 234 MB
--write-buffer 512K  12.3-14.0 GB/s at 128 concurrent, RSS 36 MB
```

The read path allocates the WHOLE file for each request, so its memory grows with concurrency times file size. The pipes do not grow that way, because the kernel fills a pipe's buffer only as it is used. That is also why the count is 64 and not 8. The pipes cost less than the fallback they avoid, and a count of 8 put the boundary at about ten concurrent requests.

**On a TLS listener there is no zero-copy path at all.** Know this limit before serving large files over TLS. Splicing would hand the peer plaintext in the middle of an encrypted stream, so every request takes the read path, whatever the pipe budget allows. Measured worker RSS on a 256 MB file:

```
plaintext, one request        +2 MB          (splice)
TLS, one request            505 MB          about twice the file
TLS, three concurrent     1,250 MB
```

The memory is twice the file because the file is read into memory and the response is then assembled around it. The same doubling was recorded for a 400 MiB .html, where it came to 1219 MiB. The memory is held for the whole request, and the client decides how many such requests there are. Ten concurrent 256 MB requests would take about 5 GB.

**--http-cache** limits the multiplication but not the size. It holds each file once and shares it, so concurrency stops mattering. The cost is that it holds the file permanently from startup. A 64 MB file was measured at 154 MB, which is the file plus the two prebuilt responses. Otherwise, keep the files a TLS listener serves small, or put a plaintext listener behind something else that terminates TLS.

The fix would be a read path that works in bounded pieces, as the request side does with **on_http_body**, instead of one allocation the size of whatever was requested. That change touches the most intricate function in this path and has not been made.

A slice is never stored in the revalidation map and never answered from it. The map is keyed by path and holds the whole file's response. A stored 206 would answer every later request for that path with one reader's slice and that reader's **Content-Range**.

The client's **Connection** request header decides whether the connection is reused. The HTTP version supplies only the default: keep-alive for 1.1, close for 1.0. A request carrying **Connection: close** is answered with **Connection: close**, and the server then shuts down its own write side first. The 60-second TIME-WAIT that follows is therefore held on the server's fixed listening port, not on one of the client's ephemeral ports. The header is parsed token by token and case-insensitively, so **Connection: close, TE** counts as close.

Without **--http-cache**, this is the development mode: the next request picks up a file edited on disk. The server does this without re-reading the file every time. It keeps the response in memory, and one **statx**(2) per request decides whether that response still matches the file. The check compares the device, the inode number, the size and the modification time together. The inode number is included because of how files are usually replaced. **mv**, **cp**, **git checkout** and most editors write a new file and rename it over the old one. That can leave the size unchanged and can restore the old timestamp exactly.

The memory this uses is bounded, unlike **--http-cache**'s. The reason is that it fills from whatever is requested, not from a directory whose size the operator can see before starting. Once the kept responses reach 64 MiB in total, no further file is added. The cap per file depends on whether the requesting connection has a faster path available at all:

```
plaintext, not .html    64 KiB   anything larger goes by sendfile instead
TLS, or an .html         1 MiB   neither has a sendfile arm
```

That split comes from measurement, not from tidiness. A kept response is sent by copying it into the socket. sendfile sends the page cache by reference and copies nothing, but it costs a system call and a descriptor of its own. Measured on one core, interleaved, in us of CPU per request, kept response against sendfile: 4.7 against 7.9 at 8 KiB, 10.4 against 11.4 at 64 KiB, 15.6 against 14.3 at 128 KiB, and 27.8 against 23.9 at 256 KiB. So above 64 KiB, keeping a file makes serving it more expensive, and it also costs the map twice the file's size.

A TLS connection cannot use sendfile at all, because that would hand the peer plaintext in the middle of an encrypted stream. An .html file has a script injected into it. For those two cases the larger cap applies. There the map is what keeps a file from being read, and allocated, once per request.

Outside those two cases, a file that is not kept is not read either: it goes from the page cache to the socket without passing through this process. To switch the whole mechanism off, see **SOCKETLEY_HTTP_REVALIDATE**. Switching it off also puts every file size back on the copying path.

#### `--http-cache`

With --http, read all files into memory at startup instead of checking the filesystem on each request. This is faster for production; the difference from plain **--http** is one **statx**(2) per request. The cache is rebuilt on **reload-lua** and at no other time. A file edited on disk is therefore **not** picked up. That is both the reason to use this flag and the reason not to.

#### `--compress`

With --http, send a file's precompressed copy, made by the site's build, to clients that accept it. For example, **app.css.br** or **app.css.gz** is sent for **app.css** to a client whose **Accept-Encoding** accepts that coding. br is preferred over gzip. The response carries **Content-Encoding** and the copy's own ETag. With this flag, every file response also carries **Vary: Accept-Encoding**.

A copy is never sent when it is older than its file, or for a range request. Nor is one sent for a page, because the copy lacks the injected script. Nor is one sent for an image, a video, a woff font, a zip or a pdf. A copy requested by its own name is sent as itself. With **--http-cache**, the copies are loaded at startup along with the files and compared with them at that time. In the same measurement as the proxy's, a page's 3.8 MB of scripts loaded over 10 Mbit and 50 ms in 0.97 s instead of 3.51 s. The server itself never compresses or decompresses anything.

Each file is held twice: once with a **Connection: keep-alive** response header and once with **Connection: close**. A cache hit therefore stays a reference-count increment and still answers with the header the client asked for.

#### `-u host:port` / `--upstream host:port`

Add an outbound connection to an upstream. The server connects to the given host:port on startup. If the connection drops, the server reconnects automatically with exponential backoff (1s–16s). To add several upstreams, give -u several times, or give several addresses separated by semicolons (e.g. -u "feed:9000;cache:6379"). Each upstream gets a stable 1-based conn_id for use in Lua callbacks.

Upstream Lua callbacks:

#### `on_upstream(conn_id, data)`

Called for each newline-delimited message received from an upstream.

#### `on_upstream_connect(conn_id)`

Called when an upstream connects (including reconnects).

#### `on_upstream_disconnect(conn_id)`

Called when an upstream disconnects.

Upstream Lua actions:

#### `self.upstream_send(conn_id, msg)`

Send a message to a specific upstream.

#### `self.upstream_broadcast(msg)`

Send a message to all connected upstreams.

#### `self.upstreams()`

Returns a table of currently connected upstream conn_ids.

#### `--cache name`

Link this server to an existing cache runtime. Clients can then send "cache <command>" messages, such as "cache set foo bar" or "cache get foo". The server runs them against the linked cache and returns the response to the sender only. The server's mode still handles normal messages.

**The link also archives: every ordinary message is written to that cache.** Every message that is not a **cache** command is stored under an auto-incrementing integer key (**1**, **2**, **3** and so on). The server's mode also handles it as usual. For example, if two clients send **hello** and **world** to a linked server, **get 1** then answers **hello** and **get 2** answers **world**. The counter is per server and starts again when the server restarts. A **--persistent** cache therefore keeps growing across restarts, while keys from **1** upward are overwritten. Link a cache to a server only when you want that archive. A server that only wants its clients to reach a cache pays for one write per message.

The server does not execute the command on the connection that asked for it. It hands the command to the daemon and answers when the reply comes back, one turn of the event loop later. A **cache** command sent this way therefore costs a round trip that the same command sent to the cache's own port does not. See **Cache Access via Server** below for what this guarantees and what it costs.

### Sharding

##### `--shards N`

Serve this server from *N* worker processes instead of one, sharing the listening socket through **SO_REUSEPORT**. The kernel gives each incoming connection to one of them. *N* is 1 to 64; the default is 1.

A runtime is one process, and therefore one event loop on one core. This flag is the only way to give a single server more than that.

**With or without --lua.** A server may be sharded whether or not it runs a script. The three things a script can ask about its clients cover the whole runtime, across shard boundaries:

- **self.connections()** sums the figure each shard publishes in a shared mapping, with no round trip.
- **self.broadcast** and **socketley.send** addressed to this runtime reach the clients of every shard, once each.
- **self.clients()** lists the whole runtime: this shard's descriptors, plus a stable handle for each client that a sibling shard holds. **self.send** on one of those handles reaches the shard that owns the client.

**Per-connection state is per shard, and that is what sharding means.** A connection belongs to exactly one shard, so every callback about it runs on that shard and nowhere else. For a client that a sibling accepted, **on_connect** fired in that sibling, and **on_message** will fire there too. A script therefore holds no state for the ids that **self.clients()** returns from another shard. It can name them, count them and send to them, but it never saw them arrive. Design the script for that. Keep cross-connection state in a **cache** runtime, which every shard can reach. Do not keep it in a Lua table at file scope, because each shard has its own copy of that table.

**self.route works from a shard.** Routing hands a live client to another runtime. The target runtime answers the client, while this shard keeps the socket and relays the bytes. The target is reached across the process boundary, as from any worker, so **--shards** changes nothing about routing. A routed client belongs to the shard that accepted it, like every other connection. **unroute**, **get_route** and **owner_send** read this shard's own tables.

**What it bought, measured.** One server runtime in **--http** mode with **--http-cache**, driven by **socketley_bench proxy http-keepalive** over 64 keep-alive connections. Seven interleaved passes; the figures are the median of the per-pass ratios. The cores are those of the SERVER processes only (daemon plus workers, from */proc/<pid>/stat*), not the whole machine's. A machine-wide figure would include the benchmark client, which at this concurrency is the larger half of it.

| shards | throughput | cores | per core |
|---|---|---|---|
| 1 | 126,497 req/s | 0.99 | 127,775 req/s |
| 8 | 451,097 req/s | 4.78 | 94,372 req/s |

Eight shards give 3.57x the throughput of one, with the per-pass ratios spread from 3.18x to 4.26x.

**That figure is a server's, and does not transfer to a cache.** A server's shards are interchangeable, so any shard can answer any request. A cache's shards are not. The shard a connection lands on relays every key it does not own, and behind one address that is (*N*-1)/*N* of the keys. At four shards a cache measured 1.75x, against a server's 3.57x. At two shards it measured 1.05x for 1.91 cores. See **CACHE FLAGS** for the table.

**One shard is exactly one core.** One shard used 0.99 of a core at every concurrency tried, while the machine had fifteen more cores sitting idle. That measurement is the whole case for this flag. A server does not run out of machine; it runs out of the single event loop it is allowed.

**Per-core efficiency falls by about a quarter, and that is the price.** Throughput per core was 127,775 req/s at one shard against 94,372 at eight. Sharding buys throughput with cores, not with efficiency. If the machine has cores that are otherwise idle, that is a good trade. If it does not, this flag makes things worse rather than better. Do not set more shards than the machine has cores to give them.

**Measure with enough connections to feed the shards, or the flag looks worse than it is.** The same eight shards driven by only *16* connections reached 294,917 req/s and 2.54x. They were not slower; they were starved. That run used 4.12 cores, where the 64-connection run used 4.78. **SO_REUSEPORT** hands out whole connections, so sixteen connections over eight shards is two each with an uneven tail, and the slowest shard limits the pass. A shard count above the client's concurrency measures the client.

**The load is balanced per connection, not per request.** **SO_REUSEPORT** picks a shard when it accepts a connection and never changes that choice. One heavy long-lived connection therefore makes one shard hot while the others idle. Over a small number of connections the spread is uneven: eight connections over four shards were measured landing 3/2/2/1. Sharding helps a server carrying many comparable connections; it does nothing for a server carrying one big one.

**The surface still answers about the runtime, not the shard.**

- **ls** shows one entry.
- **stats** reports the connection count summed across the shards, and labels each shard's detail text.
- **stop** and **remove** take all the shards down.
- The count is persisted, so a daemon restart brings back the number that was asked for.

The count can be changed with **edit** only while the runtime is stopped, for the same reason as **-p**.

**--shards gives each shard a node of its own.** On a unix socket the path is not shared, because **SO_REUSEPORT** does not work that way there. *N* processes binding one path would unlink each other's node, and only the last would be reachable. A base of */run/app.sock* therefore becomes */run/app#0.sock*, */run/app#1.sock*, and so on, one per shard, and a caller can pick any of them. A base that does not end in **.sock** gets the index appended instead.

The combination is refused only when the longest of those names would not fit. The kernel's limit applies to the node, and a shard whose name is truncated is a shard nothing can reach. The refusal names that longest member.

See **Sharding** under **PROXY FLAGS** for the fuller treatment of the flag.

### Multi-Protocol Auto-Detection

Server connections detect the protocol automatically from the first bytes received. No flags are needed; all four protocols coexist on the same port:

##### `TCP (newline-delimited text)`

The default. Lines terminated by **\en** are delivered as messages.

##### `HTTP`

Detected when the first bytes are a valid HTTP method (GET, POST, etc.). The **on_http_request** Lua callback handles requests if it is defined. Otherwise the static file server handles them if **--http** is set, and the server responds with 404 if it is not. HTTP/1.1 keep-alive is supported. An explicit **Connection** request header overrides the version's default; see **--http** for what the server does with it.

##### `WebSocket`

Detected when an HTTP request contains **Upgrade: websocket**. The server completes the RFC 6455 handshake and frames and deframes messages transparently. The **on_websocket** callback fires after the upgrade. A browser page from another origin is refused with 403 unless **--origins** lists it.

A text message that is not valid UTF-8 fails its connection with close code 1007 and never reaches a script. A fragmented message is checked once it is complete. A message the server relays without a script (to other clients, back to its sender, or to the master) goes out as the same kind of frame it arrived in, text or binary. A message a script sends goes out as text when it is valid UTF-8 and as binary otherwise. A line relayed from a TCP client is sent the same way.

##### `RESP (Redis protocol)`

Detected when the first byte is *. Useful for cache-linked servers or custom RESP-based protocols. Like an HTTP connection, and for the same reason, a RESP connection is not in the relay set. The server answers it, but does not send it other clients' messages. See **--mode** under **SERVER FLAGS**.

**How much it waits for before deciding.** The tests above read four bytes. Every HTTP method is matched on four characters, and the RESP markers on two. So a connection that has sent fewer than four bytes is normally left to send more.

A completed line is the exception, and it has to be. A client that writes **hi\en** and waits for an answer will not send a fourth byte until it gets one. Waiting for that byte would mean waiting for something that only arrives after the answer. A line that ends within four bytes cannot be an HTTP method, because each method is four characters and none contains a newline. So the server decides the protocol there and then: RESP if the first two bytes say so, and TCP otherwise. Short lines are ordinary input on a line protocol and are delivered like any other.

This applies to the *first* line only. Once a connection's protocol is known, lines of any length are delivered as they arrive.

Browser example, from a page the server serves itself or one that **--origins** lists:

```
const ws = new WebSocket("ws://localhost:9000");
ws.onmessage = e => console.log(e.data);
ws.send("hello");
```

### Request Framing

The server frames an HTTP request by exactly the same rules as the proxy, because both use the same code. If a request's header block gives no answer, or two answers, to "how long is the body", the server answers **400 Bad Request** and closes the connection. That happens when the header block contains any of:

- a bare LF or a bare CR — every line must end with CRLF
- whitespace between a field name and its colon (**Content-Length : 6**)
- a continuation (obs-fold) line, i.e. one starting with a space or tab
- a field line with no colon, or with an empty field name
- more than one **Content-Length** field, or a **Content-Length** together with a **Transfer-Encoding**
- a **Content-Length** that is not a whole decimal number (**Content-Length: 6x**)

A tab is legal optional whitespace around a field value. A **Content-Length** value separated from the colon by a tab instead of a space is an ordinary request and is served, as is a value with trailing whitespace. Values reach **on_http_request** with that whitespace removed from both ends.

How the server handles **Transfer-Encoding** depends on the coding and on whether the script reads bodies:

- **chunked** alone, with a script that defines **on_http_body**: the server decodes the body and delivers it in pieces like any other. There is no length to bound it by, which is what chunked is for.
- **chunked** alone, without that callback: **501 Not Implemented**. Nothing is going to read the body incrementally. A body whose end the server cannot find is refused rather than treated as though it had none.
- **gzip, chunked**: **501** even with the callback. Chunked is the final coding, so the chunk sizes do delimit the body, but the bytes inside are still compressed. Removing the framing and handing those bytes on would pass gzip data off as the body.
- A coding that is not chunked at all, such as **gzip** by itself: **400 Bad Request**, because nothing can say where the body ends.

So a chunked request sent through a socketley proxy to a socketley server is served when the server's script takes bodies, and answered 501 when it does not. Either way, the proxy forwards the framing verbatim and relays whatever comes back. **Content-Length** remains the simpler form, and a client that knows its body's length should send it.

A server is the last recipient, so it may seem to have nobody to disagree with. Usually it does. As soon as anything sits in front of it, whether this proxy or any other, two parsers read one byte stream. A header that a strict parser ignores and a lenient one honours moves the boundary between one request and the next. The server serves pipelined requests without waiting for another read. So a body it wrongly measured as empty is read as the next request: one message goes in, two are answered, and the client chooses what the second one says. Compliant clients send none of these shapes.

A request whose header block is still arriving is held until the terminating blank line. The server applies a 16 KiB header limit (**431 Request Header Fields Too Large**) and a 10 second header deadline (**408 Request Timeout**). The server answers a missed deadline with that status instead of closing silently, as the proxy does in the same case. A client that gets a bare close cannot tell a deadline from a crash, a firewall or the wrong port.

The deadline is the same one the proxy applies, for the reason given there. It is fixed, not configurable, and deliberately independent of **--idle-timeout**. That timeout defaults to 0, so it cannot end a half-sent request. A client that sends a request line and then stops sends no further bytes for the 16 KiB limit to count. The deadline starts at the first read that left the header block incomplete, and later bytes do not renew it. It applies neither to an idle keep-alive connection between requests nor to a slow request body.

The server checks the deadline on a sweep that runs every 30 seconds. A connection is therefore closed between 10 and 40 seconds after it stops sending. A proxy has a timer chain of its own and closes between 10 and 20 seconds. The deadline itself is the same in both.

### Cache Access via Server

When a server is linked to a cache with **--cache**, clients can send "cache <command>" messages to run commands directly against the linked cache. The response goes back to the sender only and is never broadcast. The server's mode still handles normal messages.

```
socketley create cache store -p 9001 -s
socketley create server api -p 9000 --cache store -s
# Client sends: "cache set foo bar" -> receives "ok"
# Client sends: "cache get foo" -> receives "bar"
# Client sends: "hello"            -> handled by the server's mode, AND
#                                     stored in `store` under the key "1"
```

The last line is the part that surprises people. The server archives an ordinary message in the linked cache under an auto-incrementing integer key, as well as handling it normally; see **--cache** under **SERVER FLAGS**.

The request is asynchronous. The server does not run the cache's command interpreter itself. It posts the command and answers the client when the reply arrives, on the next turn of the daemon's event loop. That costs a round trip, on the order of tens of microseconds on loopback. In return, the cache can later become a different process without any change on the client's side. Nothing else waits on the reply: the server keeps serving every other connection while it is outstanding.

What holds:

- Replies on one connection come back in request order, so a client may pipeline **cache** commands and match answers to questions by position.
- A command addressed to a cache that is not running is answered with an **error:** line, not with silence.
- A client that shuts down its write side after asking still receives its answer: the server holds the connection open until it has written every reply the client is owed.

What does not hold: nothing is promised about the order of a **cache** reply relative to other traffic on the same connection. A broadcast goes to every client except the sender, and a cache reply goes to the sender alone, so there is no interleaving to define.

A connection may have at most 4096 unanswered **cache** commands outstanding, and the daemon at most 32768 across all connections. A client that pipelines past its share is disconnected rather than sent a refusal. A refusal written at that point would arrive ahead of the answers already queued in front of it. A client that cannot tell which answer belongs to which question has no protocol left.

Default port: 8000
