# Benchmarks

Each runtime against what people run instead, on one machine, in one run.

Each table below sets socketley beside reference servers doing the same work on one machine. A row gives a ratio, its range across passes, and the CPU spent. The data, with commit, versions and date of every set, is in [data/bench.json](data/bench.json); the harness is not in the repository.

## How these numbers are made

- **Interleaved on the same cores.** All arms run at once on the same pinned core, in a rotating order; the first pass is a discarded warm-up.
- **Median of per-pass ratios.** The range is shown beside it; a range that contains 1.00× is no difference.
- **CPU beside every rate.** A server at 1.00 core is saturated; a run whose load generator hits a full core is not published.
- **Checked answers.** HTTP body sizes are compared first, so a fast 404 is never measured.
- **A quiet machine.** No build, test or foreign server runs during a pass; a disturbed pass is run again.
- **Same work.** References run as a production install would, as each set's notes say.
- **The VM penalises wakeups.** It halts idle vCPUs, so a server that wakes a client per message (Redis at depth 1, nginx, Mosquitto's fan-out) takes VM exits more often than one that batches, as socketley does. Those rows swing, and the gap is smaller on hardware without the exit. Keeping vCPUs awake with spinners was refused: it delays clients' own wakeups.

A ratio (×) is how many times better socketley did: more per second, or less time, memory or CPU; above 1× socketley is ahead. The range in brackets is the lowest and highest ratio across the passes.

## HTTP: static files and a fixed answer

nginx 1.28.3, 3 passes, 2026-11-10, socketley 0174a7a1.

| case | socketley | nginx | socketley vs nginx |
|---|---|---|---|
| 1 KiB file, keep-alive, 256 connections | 271 K req/s (1.00 cores) | 50 K req/s (0.99 cores) | 5.46× (5.42–5.51) |
| 64 KiB file, keep-alive, 256 connections | 93 K req/s (1.00 cores) | 47 K req/s (0.99 cores) | 2.00× (1.98–2.16) |
| 1 KiB file, a connection per request, 64 at once | 83 K req/s (0.99 cores) | 35 K req/s (1.00 cores) | 2.36× (2.33–2.48) |
| fixed answer (Lua handler / nginx return), keep-alive | 246 K req/s (1.00 cores) | 77 K req/s (0.99 cores) | 3.22× (3.08–3.54) |

How it was measured: wrk 8 threads, 4 s a run; each server on one core, wrk on 20 others. socketley --http dir --http-cache against nginx with one worker, sendfile, open_file_cache and access logs off. Files are .txt: socketley adds a WebSocket script to every .html it serves, by design. The fixed answer is a Lua on_http_request on socketley and a return 200 on nginx, which runs no script at all. Read the 1 KiB keep-alive row with this machine in mind: nginx answers each request with its own write and wakeup, and on this VM waking a halted vCPU costs an exit, which costs a server that does that more than one that batches. A single unpublished pass on another VM (16 cores) read 1.85× for the same row. The kernel keeps at most 2,048 connections in TIME-WAIT for every arm (net.ipv4.tcp_max_tw_buckets, 131,072 by default), so a pass with a connection per request does not wait out the closed connections of the one before.

How it was measured: clientgen target (Go) on 2-5, every client arm on core 8, 3 s windows; every client arm on one core, the Go target (clientgen) on four others. Every client on the same one core, the target (a Go program) on four others with headroom: every row records the target's cores, and none used all four. socketley is one client runtime holding every connection (--connections N) with its Lua on_message as the handler; the others are one process with the same logic. Every count is taken at the target: a consumer's count must equal the lines sent, every request's size is checked, and a round trip is the interval between one connection's requests as the target sees them. The firehose rows are bound by the client's core, and every line differs (each carries its index). socketley's script reads them with on_read, walking a view of the read buffer with view:lines(), which makes no string, as Go's ReadSlice hands out a slice of its buffer; Node and Python make a string or a bytes object per line. Written with on_message instead, a Lua string per line, the 64 B row makes about 12.7 million lines a second, and with on_messages, one string per read, about 52 million. Over TLS the 64 B row is bound by the target, whose one goroutine encrypting the stream uses a whole core while socketley's runtime decrypts at about four fifths of its own; the target's cores beside the row say so. Connecting is that one runtime dialling all of them, as the others dial from one process; the memory row is socketley's daemon and the runtime's process together, by proportional set size, divided by the connections, so at 200 it is mostly the two processes' fixed cost. One runtime per connection instead, each made with socketley create ... -s from a shell loop, is a process each: 386 created and connected a second, 243 with TLS, and 1,546 KiB each held.
