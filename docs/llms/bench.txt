# Benchmarks

Each runtime against what people run instead, on one machine, in one run.

Each table below sets socketley beside reference servers doing the same work on one machine. A row gives a ratio, its range across passes, and the CPU spent. The data, with commit, versions and date of every set, is in [data/bench.json](data/bench.json); the harness is not in the repository.

## How these numbers are made

- **Interleaved on the same cores.** All arms run at once on the same pinned core, in a rotating order; the first pass is a discarded warm-up.
- **Median of per-pass ratios.** The range is shown beside it; a range that contains 1.00× is no difference.
- **CPU beside every rate.** A server at 1.00 core is saturated; a run whose load generator hits a full core is not published.
- **Checked answers.** HTTP body sizes are compared first, so a fast 404 is never measured.
- **A quiet machine.** No build, test or foreign server runs during a pass; a disturbed pass is run again.
- **Same work.** References run as a production install would, as each set's notes say.
- **The VM penalises wakeups.** It halts idle vCPUs, so a server that wakes a client per message (Redis at depth 1, nginx, Mosquitto's fan-out) takes VM exits more often than one that batches, as socketley does. Those rows swing, and the gap is smaller on hardware without the exit. Keeping vCPUs awake with spinners was refused: it delays clients' own wakeups.

A ratio (×) is how many times better socketley did: more per second, or less time, memory or CPU; above 1× socketley is ahead. The range in brackets is the lowest and highest ratio across the passes.

| LPOP | 237 K /s (1.00 cores) | 234 K /s (1.00 cores) | 241 K /s (1.00 cores) | 1.03× (0.92–1.75) | 1.01× (0.94–1.57) |
| SADD | 237 K /s (1.00 cores) | 188 K /s (1.00 cores) | 180 K /s (1.00 cores) | 1.25× (0.87–2.02) | 1.35× (1.05–2.13) |
| HSET | 229 K /s (1.00 cores) | 203 K /s (1.00 cores) | 228 K /s (1.00 cores) | 1.10× (0.84–1.69) | 0.99× (0.92–2.07) |

How it was measured: 6 redis-benchmark processes × 50 connections; servers on one core, clients on 20 others. Each server on one pinned core, every row at a full core: the rate is one core divided by the cost of an operation. At depth 1 that cost is mostly the kernel's per-message price, which all three pay alike, so the differences are small and the ranges wide; this VM halts idle vCPUs and every wakeup of a client costs the server a VM exit, which moves a server that answers each command with its own write more than one that batches.

## HTTP: static files and a fixed answer

nginx 1.28.3, 9 passes, 2026-11-03, socketley c7d4c42b.

| case | socketley | nginx | socketley vs nginx |
|---|---|---|---|
| 1 KiB file, keep-alive, 256 connections | 281 K req/s (1.00 cores) | 52 K req/s (1.00 cores) | 5.31× (4.95–5.82) |
| 64 KiB file, keep-alive, 256 connections | 93 K req/s (1.00 cores) | 45 K req/s (1.00 cores) | 2.08× (1.98–2.13) |
| 1 KiB file, a connection per request, 64 at once | 87 K req/s (1.00 cores) | 33 K req/s (1.00 cores) | 2.64× (2.56–2.86) |
| fixed answer (Lua handler / nginx return), keep-alive | 225 K req/s (1.00 cores) | 76 K req/s (1.00 cores) | 2.88× (2.82–3.08) |

Caveat: likely higher on this VM than on hardware; see the notes.

How it was measured: wrk 8 threads, 8 s a run; each server on one core, wrk on 20 others. socketley --http dir --http-cache against nginx with one worker, sendfile, open_file_cache and access logs off. Files are .txt: socketley adds a WebSocket script to every .html it serves, by design. The fixed answer is a Lua on_http_request on socketley and a return 200 on nginx, which runs no script at all. Read the 1 KiB keep-alive row with this machine in mind: nginx answers each request with its own write and wakeup, and on this VM waking a halted vCPU costs an exit, which costs a server that does that more than one that batches. A single unpublished pass on another VM (16 cores) read 1.85× for the same row.

## Authoritative DNS, one zone of 10,000 names

NSD 4.14.0, Knot 3.5.3, 9 passes, 2026-11-03, socketley c7d4c42b.

| case | socketley | NSD | Knot | socketley vs NSD | socketley vs Knot |
|---|---|---|---|---|---|
| A queries over UDP | 446 K q per core·s (1.00 cores) | 351 K q per core·s (0.90 cores) | 295 K q per core·s (0.91 cores) | 1.28× (1.24–1.31) | 1.53× (1.49–1.58) |
| A queries over TCP, 128 connections | 191 K q per core·s (0.99 cores) | 55 K q per core·s (0.94 cores) | 61 K q per core·s (0.99 cores) | 3.53× (3.29–3.64) | 3.10× (2.92–3.34) |

How it was measured: dnsperf 8 threads, 32 sockets, 8 s a run, zone of 10000 names; each server one worker on one core, dnsperf on 20 others. Queries answered per second of server CPU (rate ÷ cores), because no server saturates its core at a window of 500 outstanding queries, and with more NSD and Knot drop UDP from their default socket buffers and dnsperf waits out each loss. socketley runs with --rrl 0 --proxy none: its response rate limit, on by default, would throttle one client host, and NSD and Knot have none by default. 90% of queries find a name, 10% are NXDOMAIN.

## MQTT broker, deliveries per second

Mosquitto 2.0.22, 9 passes, 2026-11-03, socketley c7d4c42b.

| case | socketley | Mosquitto | socketley vs Mosquitto |
|---|---|---|---|
| fan-in: 16 publishers to 1 subscriber, QoS 0, 64 B | 8.00 M msg/s (0.97 cores) | 793 K msg/s (0.99 cores) | 10.11× (9.96–10.28) |
| fan-out: 1 publisher to 100 subscribers, QoS 0, 64 B | 11.98 M msg/s (1.00 cores) | 502 K msg/s (0.99 cores) | 23.02× (20.48–30.99) |
| fan-out: 1 publisher to 50 subscribers, QoS 1, 64 B | 1.46 M msg/s (1.00 cores) | 69 K msg/s (1.00 cores) | 21.20× (21.02–21.42) |
| round trip, QoS 1 publish to own delivery | 26.6 µs (0.91 cores) | 42.7 µs (0.68 cores) | 1.61× (1.60–1.62) |

How it was measured: mqbench (MQTT 3.1.1), 6 s a run; each broker on one core, mqbench on 20 others. A fan-out delivery costs Mosquitto about 4 µs of CPU, one write each; socketley coalesces the writes to a subscriber, which is the whole of the fan-out difference. The round trip is a QoS 1 publish to the publisher's own subscription.

| case | socketley | MinIO | socketley vs MinIO |
|---|---|---|---|
| GET 4 KiB, 1 connection | 8.3 K obj/s (0.18 cores) | 2.7 K obj/s (0.84 cores) | 3.12× (3.11–3.14) |

## OpenID Connect provider

Keycloak 26.8.1, 7 passes, 2026-11-03, socketley 396cc846.

| case | socketley | Keycloak | socketley vs Keycloak |
|---|---|---|---|
| sign-in: authorization code with a password, 16 clients | 260.0 req/s (3.99 cores) | 188.0 req/s (3.92 cores) | 1.35× (1.32–1.72) |
| refresh token, 64 clients | 48 K req/s (2.48 cores) | 2.4 K req/s (3.88 cores) | 19.94× (19.13–20.38) |
| userinfo, 64 clients | 168 K req/s (2.44 cores) | 20 K req/s (3.91 cores) | 8.33× (8.27–8.97) |
| JWKS, 64 clients | 172 K req/s (2.21 cores) | 28 K req/s (3.90 cores) | 6.05× (5.98–6.43) |

Caveat: a floor: the load generator ran out before socketley did.

How it was measured: idpgen, 8s a run, 200 accounts; both on the same four cores (socketley as four shards; Keycloak with its PostgreSQL), idpgen on 20 others. 200 accounts. A sign-in is the authorization code flow with PKCE and a password, so it also compares the password hashes each uses by default: scrypt here, PBKDF2 in Keycloak. Keycloak's CPU includes PostgreSQL's. On refresh, userinfo and JWKS socketley uses two and a half of its four cores while idpgen takes up to eleven, so those ratios are floors. Sign-ins come four at a time from each of four addresses: socketley refuses a fifth from one address while four are being checked, and four connections alone may land on two of its four shards, which would measure where the kernel put them. Keycloak's sign-ins still warm up across the passes (145 to 199 a second), so the top of that row's range is its first passes.
