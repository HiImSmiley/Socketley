# db runtime

JSON documents owned by accounts, over HTTP, with indexes, queries, replicas and backups

A **db** keeps JSON documents for applications, such as a game's characters or a shop's orders. Each document belongs to an [idp](rt-idp.txt) account. Nobody writes another account's documents; who may read them is set per collection.

```
socketley create db data -p 9500 --domain data --idp auth \
    --schema /etc/socketley/db.schema --keys /etc/socketley/db.keys -s
socketley data query characters '{"where":{"level":{"gte":5}},"limit":10}'
```

## What it does

- **Documents over HTTP**: GET, PUT, PATCH, DELETE at `/c/collection/id`, each versioned for safe writes.
- **Queries**: `POST /c/collection/_query` filters, sorts and pages on the indexes in `--schema`.
- **Access per collection**: `private`, `owner`, `shared`, `public` or `catalog`; services use `--keys`.
- **Transactions and changes**: Several writes as one, and a live stream of changes.
- **Replicas**: `--replicate` keeps a read-only copy of another db.
- **Backups**: Scheduled with `--backup-dir`, or now with `socketley <db> backup|restore`.

## Works with

Users sign in through an [idp](rt-idp.txt). Pictures and other large files belong in a [storage](rt-storage.txt).

## Flags

Every flag a db runtime takes, by group.

**Basics**

| flag | value | what it does |
|---|---|---|
| `-p` | int | Port: The port it listens on (a client: the port of its target). |
| `-s` |  | Start now: Start it as soon as it is made. |

**Network**

| flag | value | what it does |
|---|---|---|
| `--bind` | text | Bind address: Bind the port to this address only, such as 127.0.0.1 when only a proxy on this machine should reach it. |
| `--shards` | int | Shards: Worker processes sharing the port: the way one runtime uses more than one core. |
| `--domain` | list | Names: The names it is reached by through the entrance; empty for its own name. |
| `--cpus` | text | CPUs: The CPUs its I/O may run on, as 0-3,6. |

**Limits**

| flag | value | what it does |
|---|---|---|
| `--max-connections` (--max-conn) | int | Max connections: The most clients at once. |

**Database**

| flag | value | what it does |
|---|---|---|
| `--schema` | path | Schema: The collections, a line each: name, access (private, owner, shared, public, catalog) and indexed fields. |
| `--keys` | path | Keys: Service keys a backend sends as Authorization: Bearer, one name and secret per line. |
| `--idp` | text | Identity provider: The idp runtime whose accounts own documents and sign in by its cookie or access tokens. |
| `--idp-audience` | list | Token clients: The idp's clients whose access tokens it takes; a token of any other is refused. |
| `--origins` | list | Web origins: Web origins whose pages may call it with the user's sign-in; * lets any page call it, without the sign-in. |
| `--max-bytes` | size | Quota: The most bytes the documents hold. |
| `--cache` | size | Cache: Memory for the documents read most recently; the rest are read from disk. |

**Replication**

| flag | value | what it does |
|---|---|---|
| `--replicate` | text | Copy of: The http or https address of the database this one follows; a copy answers reads. |
| `--replicate-key` | path | Its key: A file holding a key of that database. |

**Backups**

| flag | value | what it does |
|---|---|---|
| `--backup-dir` | path | Backups: The directory backups are written into. |
| `--backup-every` | duration | Back up every: How often a backup is taken. |
| `--backup-keep` | int | Keep: How many backups are kept. |

## Benchmarks

A ratio (×) is how many times better socketley did: more per second, or less time, memory or CPU; above 1× socketley is ahead. The range in brackets is the lowest and highest ratio across the passes.

### JSON documents over HTTP

MongoDB 9.0.4, PocketBase 0.40.5, 3 passes, 2026-11-08, socketley bce3e552.

| case | socketley | MongoDB | PocketBase | socketley vs MongoDB | socketley vs PocketBase |
|---|---|---|---|---|---|
| read one document by id, 64 clients | 704 K req/s (3.49 cores) | 155 K req/s (3.86 cores) | 35 K req/s (3.86 cores) | 4.61× (4.37–12.17) | 20.45× (19.53–20.54) |
| replace one document, 64 clients | 125 K req/s (3.10 cores) | 106 K req/s (3.94 cores) | 12 K req/s (2.74 cores) | 1.18× (1.17–1.34) | 10.82× (10.72–11.02) |
| query on an indexed field, 64 clients | 485 K req/s (3.57 cores) | 82 K req/s (3.89 cores) | 22 K req/s (3.78 cores) | 5.94× (5.88–6.01) | 22.44× (22.21–22.80) |
| mixed: 90% reads, 10% writes, 64 clients | 334 K req/s (3.59 cores) | 135 K req/s (3.90 cores) | 38 K req/s (3.59 cores) | 2.40× (2.28–2.60) | 8.77× (8.70–8.82) |

How it was measured: loadgen, 4s a run, 100,000 documents, data on tmpfs; all three on the same four cores (socketley as four shards), loadgen on 20 others. 100,000 documents, data on tmpfs. MongoDB through its wire protocol with journaled writes, PocketBase over its REST API with request logs off, socketley over its HTTP API with a key. A sharded socketley db hands every write to shard 0, so its writes are at most what one shard takes, at more cores; reads and queries spread over all four.
