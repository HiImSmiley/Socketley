# Storage flags

From the manual page socketley(1).

A **storage** runtime serves the S3 API over one directory. Unmodified S3 clients (boto3, the AWS CLI, rclone, SDKs) can then put, get, list and delete objects on this machine's disk:

```
socketley create storage media -p 9000 --dir /srv/objects \
    --access-key AKIAEXAMPLE --secret-key wJalrXUtnFEMI -s
```

Like every other runtime, it runs in a worker process of its own. It speaks HTTP/1.1 with path-style addressing (**/bucket/key**). Given **--domain**, it also accepts virtual-hosted style (**bucket.domain/key**). It answers errors as S3 XML (**<Error><Code>**...) and stamps every reply with an **x-amz-request-id**. The flags below are the runtime's own. **-p**, **--listen**, **--tls**, **--cert**, **--key**, **--ca**, **--cpus**, **--max-connections**, **--idle-timeout** and the common flags apply as documented under **COMMON FLAGS**.

### `--dir path`

Sets the directory that holds the buckets. It is required, is created if it does not exist, and is made absolute against the caller's directory. A runtime is one process on one directory or, with **--shards**, several processes that share it. Two runtimes on one path would append to each other's journals.

### `--access-key key` / `--secret-key secret`

Sets the one pair of credentials that requests are signed with (AWS Signature Version 4). The two flags go together: one without the other is refused. The pair is kept in the state file and printed by **show**; prefer **--credentials** where that matters.

### `--credentials file`

Names a file of several credential pairs, one *access***:***secret* per line. Blank lines and lines starting with **#** are skipped. The secret is everything after the first colon, so the secret may itself contain a colon. A line **[***id***]** begins a user; that user's settings and keys follow it until the next such line. A file without one has a single owner, as described under **Users**. The path is made absolute against the caller's directory.

The file is read at start. **create** and **start** refuse it if it does not parse or holds nothing. The runtime reads the file again when it changes, checking at most once a second, on the next request:

- A key added to the file works at once.
- A key taken out of the file stops working.
- A file that has gone, is empty or no longer parses leaves the keys in force until it is repaired, and a warning is logged. A half-written edit therefore locks nobody out.

   A user's policy file is watched the same way. A reload does not drop connections. A key given with **--access-key** is part of the same set.

### `--sse-key-file file`

Names the file with the master key that wraps every object's data key under SSE-S3. SSE-S3 is server-side encryption with S3-managed keys. The file holds exactly 32 bytes, or 64 hex digits and an optional newline, and only its owner may read it. A file that the group or others may read, or of any other length, is refused at **create** and **start**. The key is therefore never on a command line or in the state file; only its path is, made absolute against the caller's directory. The file is read at every start.

Without this flag, a request for **AES256** and a bucket default that would need the key are refused with **501 NotImplemented**. SSE-C needs no master key. Keep the file: an object sealed under one key is not opened by another, and a request for it is answered **500 InternalError** saying so. See **Server-side encryption**.

### `--domain name[,name...]`

Sets the domains the endpoint is reached under, such as **s3.example.com**. A request whose **Host** is *bucket***.***domain* (with or without a port) addresses that bucket, and its whole path is the key. A Host equal to one of the domains, an address, or any other name uses path style, as without the flag, so both styles are served at once. Names must be DNS names and are compared without regard to case; anything else is refused at **create**. See **Virtual-hosted-style addressing**.

### `--website-domain name[,name...]`

Sets the domains that buckets' websites are reached under, such as **web.example.com**. A request whose **Host** is *bucket***.***domain* is a browser's request for that bucket's website rather than for the S3 API. It is answered from the bucket's WebsiteConfiguration. Names are checked as for **--domain**, and a Host under both belongs to the website. See **Website hosting**.

### `--fsync always|interval|never`

Sets when a write that a client was answered for is on the disk.

- **always** (the default) syncs the object's file and its directory before answering, so an answered write survives a crash of the machine.
- **interval** answers without those syncs, and syncs the whole filesystem every **--fsync-interval**.
- **never** leaves the syncing to the kernel's own writeback.

   In every mode a crash of the process loses nothing, and a stop syncs everything before it reports that it was clean. See **Durability**.

### `--sync never|active|per-user`

Chooses which **sync** runtimes the storage creates to pull its users' git repositories.

- **never** (the default) creates none.
- **active** creates one for the whole storage.
- **per-user** creates one for each user.

   Each sync runtime is a separate process, which is why none is created unless asked for. The setting is applied by **import**. After a change, the runtimes that the previous setting created are removed at the storage's next start. See **Git repositories** under the storage runtime.

### `--fsync-interval duration`

Sets how often **--fsync interval** syncs the filesystem. The range is 1 second to an hour. Default: **1s**.

### `--notify-targets file`

Names the file of webhooks that buckets' event notifications may be sent to. Each line holds one *name url*. An optional third field **ca=***file* names the CA that an https webhook's certificate is checked against; without it, the system's CAs are used. Blank lines are skipped. A field that begins with **#** is skipped together with the rest of its line:

```
# name   url
audit    http://10.0.0.5:8080/s3-events
thumbs   https://thumbs.internal/hook ca=/etc/ssl/internal-ca.pem
feed     cache://events/stream/s3
live     cache://events/channel/s3
panel    server://dashboard
bus      mqtt://broker/storage/events
oncall   mail://m/ops@example.com,dev@example.com
```

A url may also name another runtime of the daemon:

- **cache://***runtime***/stream/***key* appends each event to that cache's stream, as an entry with one field, **event**.
- **cache://***runtime***/channel/***channel* publishes each event on that channel.
- **server://***runtime* broadcasts each event to the server's clients.
- **mqtt://***runtime***/***topic* publishes each event on that broker's topic at QoS 1. The delivery counts as answered once the broker holds the event.
- **mail://***runtime***/***address*[,*address*...] mails each event to those addresses through that mail runtime, with a subject that says what the event is. The delivery counts as answered once the message is in the spool.

   Such a line takes no **ca=**. An event that a cache refuses, or one for a runtime that is not running, is retried like a webhook that does not answer. A configuration names a target as **arn:socketley:webhook:::***name*.

   **create** and **start** refuse the file if a line does not parse. The file is read at every start. Its host names are resolved off the event loop, and again when a connection is refused. A host that does not resolve is logged, and its events wait until it resolves. Without this flag every destination is refused. See **Event notifications**.

### `--replication-targets file`

Names the file of S3 endpoints that a bucket's replication may write to. Each line holds one *name url region access_key secret*, with an optional sixth field **ca=***file* for an https endpoint. Comments and blank lines work as in **--notify-targets**:

```
# name   url                          region     access key            secret
backup   https://s3.backup.internal   eu-west-1  AKIAREPLICATOR000001  wJal.../replicator
```

A configuration's **Role** names a target by its last path segment, as **arn:aws:iam::***account***:role/***name*. Every copy to that endpoint is signed with the line's key and secret, for the line's region. **create** and **start** refuse the file if a line does not parse, and it is read at every start. **show** and the state file keep its path, and its secrets are never logged. Without this flag every replication configuration is refused. See **Replication**.

### `--acls`

Makes buckets that have no ownership controls accept ACLs. S3 behaved this way before it disabled ACLs by default, and RGW still does. Without the flag, such buckets are BucketOwnerEnforced. See the ACLs under **Supported S3 operations**.

### `--tls-offloaded addresses`

Lists the proxies that terminate TLS in front of the runtime. The entries are comma-separated addresses or blocks (**10.0.0.5**, **10.0.0.0/24**, IPv6 alike). A connection from one of them counts as one made over TLS:

- it may carry SSE-C headers;
- **aws:SecureTransport** is true for it;
- the URLs the runtime answers with are https.

   The client of such a request is the address that the proxy put last in **X-Forwarded-For**. That address is used for **aws:SourceIp**, the access log and the count of failed sign-ins, which would otherwise treat every client behind the proxy as one. **create** refuses an entry that is not an address.

   A proxy that speaks HTTP/2 to clients limits an upload to its flow-control window per round trip, which is 64 KiB unless raised. Behind Apache, **H2WindowSize 524288** in the virtual host raised a browser's upload from 1.2 to 5 MB/s, on a line that carries 6. A far larger window costs the player: the browser sends its requests on the same connection, behind as much of the upload as the window lets it queue. At 16 MiB a request waited 0.5 to 1.1 s, against 0.05 to 0.1 s at 512 KiB.

### `--federation file`

Names the file with the OIDC provider and LDAP directory whose identities STS gives temporary credentials to. The file also names the users those identities sign as. It is read at every start. See **Federated identities**.

### `--tiers file`

Names the file of S3 endpoints that a bucket's lifecycle may move versions to. Each endpoint is a storage class, named by its first field. The format is that of **--replication-targets**. The URL's path names the bucket on the endpoint, optionally followed by a prefix:

```
# name   url                                region     access key            secret
COLD     https://s3.archive.internal/cold/a  eu-west-1  AKIATIER000000000001  wJal.../tier
```

**create** and **start** refuse the file if a line does not parse, and it is read at every start. A tier's path belongs to this runtime alone: anything under it that is not a version here is removed. See **Tiers**.

### `--nodes file`

Makes the runtime a node of a cluster in which every node keeps every bucket and takes writes. The file names three things:

- this node;
- every node, this one included, by the S3 endpoint the other nodes reach it at, with an optional **ca=***file* for an https endpoint;
- the key the nodes sign requests to each other with, which is the same in every node's file.

   Comments and blank lines work as in **--notify-targets**:

   ```
   self  a
   node  a  https://s3-a.internal:9000
   node  b  https://s3-b.internal:9000
   node  c  https://s3-c.internal:9000  ca=/etc/socketley/cluster-ca.pem
   key   AKIACLUSTERNODES0001  wJal.../nodes
   sync  1  5000
   ```

   The **sync** *n* **[ms]** line is optional. With it, a write is answered only once *n* other nodes have it, or once *ms* milliseconds (5000) have passed, whatever the nodes report. After that, the write's copies continue as they would without the line. Without it, a write is answered once it is in this node's outbox. A file whose sync line names more nodes than there are is refused.

   **create** and **start** refuse the file if a line does not parse, if **self** is none of its nodes, or if it names no key. The file is read at every start, so each node picks up a node added to the file when that node next starts. **show** and the state file keep its path, and the key is never logged.

   The cluster's key is accepted beside the runtime's own credentials, but it is not one of them. A request signed with it writes what another node made, is judged by no bucket policy, and cannot be given to a user. See **Cluster**.

### `--anonymous`

Accepts requests that carry no credentials at all. It is required unless credentials are given: a runtime created with neither is refused, so an endpoint is never open by omission. With credentials as well, both kinds of request are served. A request that does carry a signature is always verified; a wrong signature is refused and never taken for an anonymous request.

An anonymous request may send a body in unsigned aws-chunked framing (**STREAMING-UNSIGNED-PAYLOAD-TRAILER**); the body is decoded and its trailing checksum checked. A body signed in chunks (**STREAMING-AWS4-HMAC-SHA256-PAYLOAD**) is refused with **NotImplemented**, because there are no credentials to verify the signatures with. Without **--anonymous**, a request with no credentials is answered **403 AccessDenied** unless its bucket's policy allows it, as described under **Bucket policy**.

### `--idp runtime`

Makes the web interface and WebDAV in a browser use the sign-in of the named **idp** runtime in this daemon. An account signed in there is the user of the same name here, with the rights that user has here and no others. An account that is not a user here is answered **403**. The page offers the provider's sign-in beside its own form, and signing out there also signs out at the provider. The cookie reaches the storage only when the provider's **--cookie-domain** covers the storage's name. The provider can take over the accounts of the storage's own users with **socketley idp-user** *idp* **import** *storage*.

### `--mpu-expire duration`

Aborts a multipart upload that has been open this long (**24h**, **7d**). A bare number is seconds, as for every duration flag. Without this flag, an upload is kept until it is completed or aborted, however old it is. The runtime looks for expired uploads while it runs and once at every start. An upload that outlived the setting while the runtime was stopped is therefore gone when the runtime comes back.

### `--scrub duration`

Reads every object and version back once in this period (**30d**, **7d**) and checks its bytes. The bytes are checked against the MD5 that the header names, so a file the disk changed is found before a client reads it. See **Scrub**. Without this flag, nothing is read in the background.

### `--compress duration`

Compresses each version where it lies once it has gone unwritten this long (**1h**, **7d**). A compressed version takes less of the disk and reads back as it was. See **Compression**. Without this flag, every body is stored as it was sent.

### `--max-bytes size`

Sets a quota on the bytes the runtime holds. It takes the **K**/**M**/**G** suffixes of **--maxmemory**. A put that would exceed the quota is answered **507 StorageFull** and stores nothing. The quota can be changed on a serving runtime with **import**. 0, the default, means no quota.

**edit** does not change these flags; **import** does, as it does for a cache. While the runtime is running, **import** refuses to change **dir**, **anonymous**, **domain**, **fsync**, **fsync_interval**, the access key, the secret key, the credentials file, the SSE key file or the notification targets file. The contents of a credentials file are re-read on their own. The quota and the expiry can change under a serving runtime. **--shards** splits the runtime over several processes on one directory, as described under **Sharding**.

## What it shares with the other runtimes

#### `TLS`

**--tls**, **--cert** and **--key** terminate TLS on the listener, as for a server or a cache. With **--ca**, the runtime also asks every client for a certificate signed by that CA. The runtime reads the certificates when it starts, so **reload** installs a replaced certificate. The runtime sets up a TLS session for every accepted connection before it reads the first byte. A plaintext client therefore meets the handshake and is refused; it is never served in the clear. A peer that stays in the handshake for thirty seconds is dropped. Over TLS, a download is read from the file and encrypted. Only plain TCP downloads are sent with sendfile, so **zero_copy_bytes** stays 0 for TLS downloads. TLS and **--listen unix:** cannot be combined.

#### `The node beside the port`

A runtime with a port also listens on the Unix socket *<daemon\***socket>.rt/***name***.sock** for callers on the same machine. A proxy whose **--backend** is the runtime's *name*, or a group the runtime belongs to, connects to that socket instead of the port. A proxy in front of the runtime carries GETs and PUTs of any size. With **--protocol tcp**, the request reaches the runtime exactly as the client signed it; use this mode once requests are signed. In the default **http** mode, the client's path carries the proxy's own **/***name***/** prefix, and the proxy strips that prefix before it forwards the request.

#### `Limits and timeouts`

**--max-connections** closes any connection beyond the limit. **--idle-timeout** closes a keep-alive connection that stays idle between requests, and counts it in **timeouts**.

#### `--cpus`

The CPU set is checked against the daemon's ring and shown by **stats**, as for every runtime type.

#### `Persistence`

The configuration is saved with the runtime. When the daemon restarts, it starts every runtime that was running, with its objects, TLS settings and limits.

#### `daemon --fast-lo`

The loopback shortcut needs no exception for a storage runtime. The runtime reads every request body with a receive call, and it splices only from a file to a socket, never from a socket. Clients on the shortcut, directly or through a proxy, therefore put and get objects byte for byte.

| GetBucketReplication | GET /bucket?replication | The configuration as it is kept, an ID given to a rule that had none; ReplicationConfigurationNotFoundError (404) when there is none. |
| DeleteBucketReplication | DELETE /bucket?replication | 204 whether or not there was one; versions already queued are still copied. |
| PutBucketQuota | PUT /bucket?quota | socketley's own: a BucketQuota of MaxBytes and MaxObjects, admins only. See **Quotas** below. |
| GetBucketQuota | GET /bucket?quota | The quota as it is kept; NoSuchBucketQuota (404) when there is none. Admins only. |
| DeleteBucketQuota | DELETE /bucket?quota | 204 whether or not there was one. Admins only. |
| PutBucketWebsite | PUT /bucket?website | A WebsiteConfiguration: an IndexDocument, an ErrorDocument and up to 50 RoutingRules, or a RedirectAllRequestsTo alone. See **Website hosting** below. |
| GetBucketWebsite | GET /bucket?website | The configuration as it is kept; NoSuchWebsiteConfiguration (404) when there is none. |
| DeleteBucketWebsite | DELETE /bucket?website | 204 whether or not there was one. |
| GetSessionToken | POST / Action=GetSessionToken | STS's: temporary credentials for the signing user, DurationSeconds 900 to 129600 (43200). See **Temporary credentials** below. |
| AssumeRole | POST / Action=AssumeRole | STS's: the same, DurationSeconds 900 to 43200 (3600), the RoleArn of a role the IAM API made, and a Policy that bounds the session. |
| AssumeRoleWithWebIdentity | POST / Action=AssumeRoleWithWebIdentity | STS's, unsigned: temporary credentials for an OIDC provider's token, as **--federation** maps it. See **Federated identities** below. |
| AssumeRoleWithLDAPIdentity | POST / Action=AssumeRoleWithLDAPIdentity | Unsigned: temporary credentials for a user the LDAP directory binds, as **--federation** maps it. |

A bucket's ownership controls decide whether the bucket takes ACLs. They are managed with PutBucketOwnershipControls, GetBucketOwnershipControls and DeleteBucketOwnershipControls, or with **x-amz-object-ownership** on CreateBucket. BucketOwnerEnforced is every bucket's default, as S3 makes it now, and it disables ACLs. Every bucket and object then has one grant, FULL_CONTROL to the bucket's owner, and GetBucketAcl and GetObjectAcl answer that grant. A write may ask only for that ACL: **bucket-owner-full-control**, or **x-amz-acl: private** from the bucket's owner, which rclone and s3fs send by default. Any other canned ACL or grant is **400 AccessControlListNotSupported** (**InvalidBucketAclWithObjectOwnership** on CreateBucket), and nothing is stored.

ObjectWriter and BucketOwnerPreferred enable ACLs. With **--acls**, every bucket that has no ownership controls takes ACLs too. For such a bucket, GetBucketOwnershipControls answers **404 OwnershipControlsNotFoundError**, as for an RGW bucket. Where ACLs are enabled, these set the ACL of a bucket or of an object:

- the canned ACLs: private, public-read, public-read-write, authenticated-read, bucket-owner-read, bucket-owner-full-control and log-delivery-write;
- the **x-amz-grant-*** headers: id=, uri= of AllUsers, AuthenticatedUsers or LogDelivery, and emailAddress= of a user's **email** setting;
- an AccessControlPolicy document.

A bucket's ACL is kept as a document beside the bucket's policy. An object's ACL is kept in the object's header, together with the object's owner. Under ObjectWriter the owner is the writer. Under BucketOwnerPreferred the owner is the bucket's owner when the write gave that owner full control.

A bucket's grants allow listing (READ), writes and deletes (WRITE), and access to the bucket's ACL (READ_ACP, WRITE_ACP). An object's grants allow reading the object (READ) and access to its ACL. The runtime reads an object's grants when it reads the object, and only after the bucket's grants did not decide the request.

- An explicit Deny in a policy still refuses the request.
- The bucket's owner and an admin are let in, whatever the grants say.
- A public grant is **403 AccessDenied** where the public access block blocks public ACLs. Where the block ignores public ACLs, a public grant counts for nothing.
- A grantee that is not a user is **400 InvalidArgument** (**UnresolvableGrantByEmailAddress** for an email address).
- BucketOwnerEnforced is refused on a bucket whose ACL grants anything more than the owner's full control.

A bucket can have tags of its own, managed with PutBucketTagging, GetBucketTagging and DeleteBucketTagging. A bucket has at most 50 tags, under the same rules as an object's tags. When there are none, the answer is NoSuchTagSet (404). The tags are kept in *dir***/***bucket***/tagging** and carried between shards like the bucket's CORS rules.

The runtime accepts every storage class S3 has, and keeps the bytes the same way as for STANDARD.

- A class whose objects S3 can read at once (REDUCED_REDUNDANCY, STANDARD_IA, ONEZONE_IA, INTELLIGENT_TIERING, GLACIER_IR, EXPRESS_ONEZONE) is kept. HEAD, GET, the listings, GetObjectAttributes, and an upload's ListParts and ListMultipartUploads name it.
- An archive class is named STANDARD, because its own name would tell a client to restore an object that it can read now.
- A copy takes the class it names, or STANDARD when it names none. A copy may name a class to change an object's class in place.
- A version that a lifecycle rule moved to a tier is listed and read with the tier's name as its class.

A class S3 does not have is **400 InvalidStorageClass**. **x-amz-website-redirect-location** is kept and returned like the other stored headers. Any other feature, such as analytics or inventory, is answered **501 NotImplemented** and is never mistaken for the plain operation. A single put is at most 5 GiB, and a key is at most 1024 bytes.

## Uploads by form

A POST to a bucket with a **multipart/form-data** body is S3's POST Object: the upload that a web page makes with an HTML form. It also takes the fields that **generate_presigned_post** and the SDKs' presigned POST write. A form posted to a key instead is **405 MethodNotAllowed**, as is a POST to any key without a subresource.

The fields before the file describe the upload. Together they may hold at most 20 KiB; more is **MaxPostPreDataLengthExceeded**. The fields are:

- **key**; **${filename}** in it is replaced with the file's name;
- the headers a PutObject would carry: Content-Type, Cache-Control, Content-Disposition, Content-Encoding, Expires, x-amz-meta-*, x-amz-checksum-* and x-amz-server-side-encryption*;
- **acl** and **tagging** (a Tagging document);
- **success_action_status** (200, 201 with a PostResponse document, or 204, the default), or **success_action_redirect**, which answers a 303 to that address with the bucket, key and ETag in its query.

The file is streamed into the object like a put's body. Fields after the file are ignored, as on S3.

A form with a **policy** carries its signature in its fields, in one of two forms:

- SigV4: **x-amz-algorithm**, **x-amz-credential**, **x-amz-date** and **x-amz-signature**, an HMAC-SHA256 of the policy;
- the older form that boto3 still writes by default: **AWSAccessKeyId** and **signature**, a base64 HMAC-SHA1 of the policy. This is Signature Version 2, which headers and presigned URLs may also use (see **Authentication**).

The policy is a base64 JSON document with an **expiration** and **conditions**. An expired policy is AccessDenied. The conditions are {"field": "value"}, ["eq", "$field", "value"], ["starts-with", "$field", "prefix"] and ["content-length-range", min, max]. Field names are compared without case. "$bucket" is the bucket posted to, and a field the form leaves out counts as the empty string.

A field that does not meet a condition is **403 AccessDenied** ("Invalid according to Policy: ..."). So is a field that no condition names, except the signature and its key, the policy, the file and the x-ignore-* fields. A file outside the content-length range is **EntityTooLarge** or **EntityTooSmall**. In each case nothing is stored.

A form without a policy is an anonymous PutObject. It is taken by a runtime with **--anonymous**, or where the bucket policy lets anyone put the key. Either way, the bucket policy and a script's on_request see a form upload as PutObject.

## Virtual-hosted-style addressing

Against AWS, S3 clients address a bucket by host name by default (**https://***bucket***.s3.amazonaws.com/***key*). Most clients can be told to do the same against a custom endpoint.

Given **--domain s3.example.com**, a request with **Host: photos.s3.example.com** and path **/2024/a.jpg** names the object **2024/a.jpg** in bucket **photos**. The path-style request **/photos/2024/a.jpg** names the same object, with **Host: s3.example.com** or with any Host that is not a subdomain of a given domain, including an IP address.

Everything before the domain is the bucket name, dots included. With several domains, the longest domain that matches decides. A Host equal to one of the domains is that endpoint itself, so **--domain example.com,s3.example.com** reads **s3.example.com** as the endpoint and not as bucket **s3**.

Signatures need no special handling. SigV4 signs the path as sent and the Host header, so a virtual-hosted request is verified over **/***key* and its own host. A presigned URL in either style verifies as it was written.

The locations the runtime writes back follow the style of the request. This applies to the **Location** of CreateBucket (**/***bucket* in path style, the bucket's URL in virtual-hosted style), the Location of a form upload, and the location in **CompleteMultipartUploadResult**. **x-amz-copy-source** names *bucket***/***key* in both styles, as in S3.

Clients need the bucket host names to resolve to the runtime. Use a wildcard DNS record (*.s3.example.com), or, on one machine, **--domain localhost**: glibc resolves every *name***.localhost** to the loopback address. The usual client settings are:

- boto3's **addressing_style: virtual** (in the AWS CLI's config, **s3 = addressing_style = virtual**);
- rclone's **force_path_style = false**;
- an mc alias set with path lookup **off**.

A bucket whose name is not a single DNS label, such as a name with dots, is still served path style. Over TLS, the clients fall back to path style for such names. With **--tls**, the certificate must cover every bucket's host name. That takes a wildcard certificate for *.*domain* as well as the domain itself. A wildcard matches only one label, so a bucket with dots in its name fails certificate verification in virtual-hosted style and is reached path style.

## Authentication

The runtime verifies requests signed with AWS Signature Version 4, in both forms: the **Authorization** header, and a presigned URL (**X-Amz-Algorithm** and the other parameters in the query, for GET, HEAD, PUT and DELETE).

The runtime also verifies Signature Version 2, which awscli 1.x presigns with and older tools sign with. It takes both forms:

- the header **Authorization: AWS** *key*:*signature*, dated by **Date** or **x-amz-date** within fifteen minutes;
- a URL's **AWSAccessKeyId**, **Expires** and **Signature**. The URL is good until **Expires**, which may be at most a week (604800 seconds) ahead.

For Signature Version 2, the signed resource is the bucket and key as sent, with the subresources S3 signs. No part of the body is signed.

Any region in the credential scope is accepted, including none. Every **x-amz-*** header in a request must be among the signed headers, as S3 requires. The one exception is an **x-amz-content-sha256** header sent with a presigned URL. A request with an unsigned **x-amz-*** header is refused with **403 AccessDenied**.

The runtime honours every **x-amz-content-sha256** mode a client sends:

- A hex hash is checked against the body as the body streams. A body that is not the one signed is **XAmzContentSHA256Mismatch** and is not stored. A presigned URL signs no payload, but when its sender states a hash in the header, the body is checked against that hash all the same. A value there that is not a hash is **400 InvalidArgument**.
- **UNSIGNED-PAYLOAD** has nothing to check.
- aws-chunked bodies are decoded: **STREAMING-AWS4-HMAC-SHA256-PAYLOAD**, its **-TRAILER** variant and **STREAMING-UNSIGNED-PAYLOAD-TRAILER**. Every chunk signature and a signed trailer are verified, even when the aws-chunked body is itself carried in **Transfer-Encoding: chunked**.

No mode holds the body whole: the body goes through the same two staging buffers as an unsigned put.

The error answers are S3's:

- **SignatureDoesNotMatch** (403) for a wrong secret, or for a request changed after signing;
- **InvalidAccessKeyId** (403);
- **RequestTimeTooSkewed** (403) for a request dated more than fifteen minutes from the runtime's clock;
- **AccessDenied** (403) for an expired presigned URL, for a request with no signature where no bucket policy allows it, and for a request a bucket policy denies;
- **AuthorizationHeaderMalformed** (400).

A denied request is answered before its body is read, and the connection is closed.

## Users

A credentials file may name users. Each has an id, a display name, its own keys, optionally an identity policy, and optionally the admin flag:

```
# a key outside any user is the default owner, socketley, an admin
AKIAOPS000000000001:ops-secret

[alice]
name = Alice Example
AKIAALICE0000000001:alice-secret-1
AKIAALICE0000000002:alice-secret-2

[bob]
policy = bob.json
AKIABOB000000000001:bob-secret

[root]
admin = true
AKIAROOT00000000001:root-secret
```

**[***id***]** starts a user. The id is 1 to 128 printable characters, with no spaces and none of **/:*?,=[]"<>&**. The lines after it, up to the next user, hold the user's keys (*access*:*secret*) and settings (*name* = *value*):

- **name** is the display name. Default: the id.
- **admin** is **true** or **false**.
- **policy** is the user's identity policy. A value that begins with **{** is the JSON itself, on that one line. Any other value is a file, relative to the credentials file's directory.
- **max_bytes** is the most that the buckets the user owns may hold together, as a size such as **10G** (see **Quotas**).

In a setting line, the **=** comes before any colon. An access key cannot contain **=**.

A key outside any user, and the pair given with **--access-key**, belong to the default owner, **socketley**, an admin. A file without users describes only that owner: every key may do everything to every bucket, except what a bucket policy denies.

These are errors: a user declared twice, a key given to two users, an unknown setting, and a policy that does not compile. **create** and **start** refuse such a file and name the line. On a reload, such a file leaves the current users in force.

An identity policy uses a bucket policy's grammar (see **Bucket policy**), with the same actions and conditions. It has no **Principal**, because the principal is the user itself. Its resources may be in any bucket: * or **arn:aws:s3:::***pattern***.** A pattern is matched as IAM matches an ARN: against the bucket name for a bucket action, and against *bucket***/***key* for an object action. In a pattern, * also spans **/**. So **arn:aws:s3:::logs-*** names those buckets and every object in them, and **arn:aws:s3:::logs-*/*** names only the objects.

A bucket is owned by the user that made it. The owner is recorded on the second line of *dir***/***bucket***/created***.* There is no such line for the default owner, as for every bucket made before users. Every shard reads the owner when the bucket is made and at every start.

ListBuckets shows a user the buckets it owns, and shows an admin every bucket. When one of the user's policies denies it **s3:ListAllMyBuckets** (on * or **arn:aws:s3:::***), ListBuckets is 403. Every Owner element is the bucket's owner, with the owner's display name. This covers ListBuckets, ListObjects, ListObjectVersions, the uploads and parts listings, GetBucketAcl, and GetObjectAcl on a bucket with ACLs disabled. The reason is that an object of a bucket with ACLs disabled belongs to the bucket's owner. Where ACLs are enabled, GetObjectAcl names the object's own owner, as **Supported S3 operations** describes.

A signed request is decided in this order:

1. A matching **Deny** in the user's identity policy or in the bucket's policy refuses the request with **403 AccessDenied**.
2. An admin and the bucket's owner are let in. So is anybody on a bucket that does not exist; the operation then answers **NoSuchBucket**.
3. A matching **Allow** lets the request in. It may be in the identity policy, or in the bucket's policy naming the user by id, by one of its keys, or by *.
4. Anything else is **403 AccessDenied**.

A request without credentials to a bucket that does not exist is answered **404 NoSuchBucket**, as a signed one is. A request is **403 AccessDenied** before anything is done when its **x-amz-expected-bucket-owner** names a user other than the bucket's owner. The same holds when **x-amz-source-expected-bucket-owner** does so for a copy's source bucket. A copy is also judged as a GetObject of its source in the source bucket.

A user of the credentials file may call CreateBucket unless its identity policy denies **s3:CreateBucket** on the name. A role, or a user that the IAM API made, may call it only where one of its policies allows it, as S3 judges them. The bucket policy's own operations stay open to the owner and admins, whatever the policy says. So do the operations that no action names: ownership controls and the operations answered NotImplemented. Another user needs an Allow for the bucket policy's operations, and is refused the operations that no action names.

## Temporary credentials

A user may ask the endpoint itself for temporary credentials, as from STS, with any STS client pointed at the runtime's URL:

```
POST / HTTP/1.1
Content-Type: application/x-www-form-urlencoded

Action=AssumeRole&Version=2011-06-15&DurationSeconds=3600
    &RoleArn=arn:aws:iam::000000000000:role/reader&RoleSessionName=ci
    &Policy=<an identity policy, URL-encoded>
```

The answer is an access key starting with **ASIA**, a secret and a session token. They sign as the user whose key asked for them. The token goes in **x-amz-security-token**, or in a presigned URL's **X-Amz-Security-Token**.

The token carries the user's key, the expiry and the session policy, sealed with that key's secret. The session's secret is derived from that key's secret too. The runtime keeps nothing, so every shard accepts the token, and so does the runtime after a restart. The token ends at its expiry (**400 ExpiredToken**), or as soon as the key is gone from the credentials file (**400 InvalidToken**).

The request is a form posted to **/**, signed for the service **sts** or **s3**. Temporary credentials cannot ask for more, and a runtime without keys gives none.

AssumeRole of a role that the IAM API made (see **IAM**) is refused unless the role's trust policy names the caller. It is also refused for a duration longer than the role's MaxSessionDuration. The session holds the role's policies, not the caller's. Any other RoleArn is **404 NoSuchEntity** and gives the caller nothing.

The session is bounded by its **Policy**, which uses an identity policy's grammar and is at most 2048 bytes. The Policy only narrows the session: what it does not allow is refused even to an admin or a bucket's owner, including the bucket policy's operations.

GetCallerIdentity names the user or the assumed role that signed. For a user that the IAM API made, it gives the UserId and the path the user was given. A browser's form upload is not signed with temporary credentials.

## Federated identities

With **--federation** *file***,** the endpoint gives temporary credentials, without a signed request, to an identity that an OIDC provider or an LDAP directory vouches for. The file holds one setting per line. Comments and blank lines work as in **--notify-targets**, and relative paths are taken from the file's own directory:

```
oidc issuer https://id.example.org/realms/main
oidc client storage-console
oidc jwks   jwks.json
oidc claim  policy
role arn:aws:iam:::role/ci   builder
ldap url    ldaps://ldap.example.org ca=/etc/ssl/ldap-ca.pem
ldap dn     uid=%s,ou=People,dc=example,dc=org
ldap user   alice  =
ldap user   *      reader
```

**AssumeRoleWithWebIdentity** takes a JWT signed with RS256, RS384, RS512, PS256, ES256 or ES384 by a key of the JWK Set file. The keys may be RSA of 2048 bits and up, or EC P-256 and P-384. The runtime reads the JWK Set file again whenever it changes, and keeps the old keys while a new file does not parse. In the token, **iss** must be the issuer, **aud** must name a client, and **exp**, **nbf** and **iat** must hold within a minute. Otherwise the answer is **400 InvalidIdentityToken**, or **ExpiredTokenException** once the token has run out. A **role** line for the RoleArn names the user the session signs as. Without such a line, the token's claim (by default **policy**) must name exactly one user.

**AssumeRoleWithLDAPIdentity** binds **LDAPUsername** with **LDAPPassword**, using the DN that the **dn** template makes (the name is escaped as a DN value). The connection is ldap:// or ldaps://, checked against **ca=** or the system's CAs. The bind runs on a thread of its own and must finish within five seconds. The answer is **503 ServiceUnavailable** when the directory does not answer, and **403 AccessDenied** when the directory refuses the bind. The user's own **ldap user** line, or else the * line, names the user the session signs as; **=** means the same name. An empty password is refused before anything is sent.

Both kinds of session belong to the mapped user. They are signed under that user's first key and have the user's rights, narrowed by a **Policy** as for AssumeRole. A RoleArn that names a role the IAM API made is assumed when the role's trust policy names the mapped user, as for AssumeRole. A mapping to a user that does not exist, or that has no key, is **403 AccessDenied**. The runtime reads the file at every start. **create** and **start** refuse the file when a line does not parse.

## IAM

The endpoint also answers IAM's API. It answers an admin and a user whose own policies allow the action, and never a session. The actions are:

- CreateUser, GetUser, ListUsers, UpdateUser and DeleteUser;
- CreateAccessKey (at most two per user), ListAccessKeys, UpdateAccessKey and DeleteAccessKey;
- CreateGroup, GetGroup, ListGroups, DeleteGroup, AddUserToGroup, RemoveUserFromGroup and ListGroupsForUser;
- CreateRole, GetRole, ListRoles, UpdateRole and DeleteRole;
- CreateLoginProfile, GetLoginProfile, UpdateLoginProfile, DeleteLoginProfile and ChangePassword;
- TagUser, UntagUser and ListUserTags;
- for users, groups and roles alike: Put, Get, List and Delete of an inline policy, and Attach, Detach and ListAttached of the AWS managed policies AmazonS3FullAccess, AmazonS3ReadOnlyAccess and AdministratorAccess.

A request is a form posted to **/**, as **aws iam** and the SDKs send it, signed for **iam** with or without a region.

What the IAM API makes is kept in *dir***/.iam.json**. The file is written under a lock and renamed over the old one. Every shard reads it beside the credentials file. A change is in force at once on the shard that made it, and within 50 milliseconds on the others. A restart keeps it.

A user's identity policy is the statements of its inline and attached policies and of its groups' policies, taken together. A user with none owns and reaches the buckets it makes, as a credentials-file user without a policy does. A user of the credentials file cannot be made again through the API. Policies put on such a user stand beside the file's own: a Deny in either refuses, and an Allow in either admits. Such a user is not listed.

A user can be deleted once it has no keys, policies, groups or login profile left. A group can be deleted once it has no members or policies, and a role once it has no policies. Policies are checked as identity policies are. A trust policy's statements with a condition let nobody in. ARNs name no account, as RGW writes them: **arn:aws:iam:::user/**name**.** OIDC providers, customer managed policies and permission boundaries are not served.

A login profile is a user's password for the web interface, and for a WebDAV client's Basic credentials. It works the same for a user of the API and a user of the credentials file. A password has at least 8 characters. The runtime keeps it as scrypt (N=2^14, r=8, p=1), never as itself. After a password matches, the runtime does not hash it again for five minutes, so a drive that sends it with every request costs one hash, not one per request. **PasswordResetRequired** makes the page ask for a new password before anything else. ChangePassword takes the old password and changes the caller's own. Sessions opened with a password are sealed under a secret drawn with the profile. A session made before the password was last set is no longer let in.

The runtime itself reads four tags of a user:

- **socketley:display-name** is the name shown;
- **socketley:email**;
- **socketley:max-bytes** is the quota on the bytes of the buckets the user owns, like the credentials file's **max_bytes**;
- **socketley:disabled** set to **true** means that neither the user's password nor its keys sign in. Its buckets keep their owner, and a share can still name the user.

Other keys with that prefix are refused. A member of the group **admins** is an admin, as the credentials file's **admin = true** makes one. An IAM user makes a bucket only where a policy allows it, as S3 judges. The web interface gives the users it makes the inline policy **socketley-libraries** (**s3:CreateBucket** on *), and a user owns what it makes.

A user who is not an admin may call an IAM action that its identity policies allow. The action is written **iam:***Action***,** with * and **?** as wildcards (**iam:List***, **iam:***). A bare **"*"** names only S3's actions, so a policy written before IAM could be delegated gives no IAM action; AdministratorAccess names **iam:*** beside it. The resources are **arn:aws:iam::***account***:user/***path name***,** **group/**... or **role/**... in any account. In them, **${aws:username}** is the caller's user id. ListUsers, ListGroups and ListRoles act on no resource, so only **Resource : *** covers them. A Deny wins, and an action with no Allow is **AccessDenied**.

An access key named by its id alone is judged as its owner's. A rename or a move needs both ARNs. GetUser, CreateAccessKey, ListAccessKeys, GetLoginProfile, ListUserTags and ListGroupsForUser without a UserName act on the caller. Without any policy, a user may do to itself what IAM's console lets every user do. It may read its own user, keys, tags and groups, and make, change and delete its own keys. It may also set a first password and change its password.

An admin keeps every right, whatever its policies say. Only an admin changes an admin or gives an identity IAM rights. Anybody else is refused a policy put or attached whose Allow names an **iam:** action (AdministratorAccess included), a group that has such a policy, the group **admins**, and the **socketley:** tags. IAM actions that this runtime does not answer are accepted in a policy and match nothing.

## CORS

A bucket's CORS rules let a page served from another origin use the bucket from a browser: read objects, and upload with a presigned URL. PutBucketCors sets them as S3's **CORSConfiguration** document, with up to 100 **CORSRule** elements. Each rule holds:

- one or more **AllowedOrigin**. An origin may hold at most one *, which stands for any run of characters; * alone stands for every origin;
- one or more **AllowedMethod** (GET, PUT, HEAD, POST or DELETE);
- any number of **AllowedHeader** (at most one * each, compared without case) and **ExposeHeader**;
- an optional **MaxAgeSeconds**, and an optional **ID** of up to 255 characters.

A document that is not a CORSConfiguration is **400 MalformedXML**. An unknown method, a second wildcard or a 101st rule is **400 InvalidRequest**. A refused document leaves the existing rules in place.

The rules are kept in *dir***/***bucket***/cors***.* A new file is written beside it, synced and renamed over it. The rules therefore survive a restart, and a crash leaves either the old rules or the new ones. The rules are deleted with the bucket, and a bucket made again under the same name has none. With **--shards**, shard 0 writes the rules, whichever shard took the request, as described for the policy under **Bucket policy**. The request is answered once no shard can go on with the old rules. A shard that was not running reads the rules from the file when it starts.

A preflight is an **OPTIONS** request on the bucket or on a key, with **Origin** and **Access-Control-Request-Method**, and with **Access-Control-Request-Headers** when the real request will send other headers. The runtime answers it without authentication, from the first rule whose origin, method and every requested header match. The answer is 200 with:

- **Access-Control-Allow-Origin** (the origin, or * when the rule allows every origin);
- **Access-Control-Allow-Methods**;
- **Access-Control-Allow-Headers** (the headers asked for);
- **Access-Control-Allow-Credentials: true** for a named origin;
- **Access-Control-Expose-Headers** and **Access-Control-Max-Age**, when the rule has them;
- **Vary**.

A preflight to a bucket without rules is **403 AccessForbidden** ("CORSResponse: CORS is not enabled for this bucket."). A preflight that no rule allows gets the same answer with "This CORS request is not allowed". A preflight without **Origin** or with a method S3 does not have is **400 BadRequest**.

Any other request whose **Origin** some rule allows for its method gets the same headers, except **Access-Control-Allow-Headers**. A request that also carries **Access-Control-Request-Method** is judged by that method and the headers it asks for, and gets the headers of that preflight, as S3 answers it. These headers come on every answer, including errors and authentication refusals, so a page can read why it was refused. A request from an origin that no rule allows is served normally, with no CORS headers. When none of a runtime's buckets has rules, the runtime looks nothing up for a request.

## Checksums

The runtime computes a checksum over the body of a PutObject or an UploadPart when the request names one of **x-amz-checksum-crc32**, **-crc32c**, **-crc64nvme**, **-sha1** and **-sha256**. The request names it in that header, in a trailer of an aws-chunked body (**x-amz-trailer**), or with **x-amz-sdk-checksum-algorithm**. The runtime compares the result with the value the client gave. A mismatch is **400 BadDigest** and nothing is stored.

The checksum is kept in the object and echoed in the answer. GetObject and HeadObject return it when the request has **x-amz-checksum-mode: ENABLED**, except on a ranged read, which is not of the whole object. **x-amz-checksum-type** says what the checksum is of.

A multipart object has the checksum of its parts' checksums, followed by **-N** for the number of parts (**COMPOSITE**), as on S3. A part with no checksum of its own still gets one in the upload's algorithm. An upload created with **x-amz-checksum-type: FULL_OBJECT** and a CRC instead has the CRC of all its bytes. So does every CRC64NVME upload, as in S3. The runtime combines that CRC from the parts' CRCs and lengths, without reading the parts again. FULL_OBJECT with SHA-1 or SHA-256, or COMPOSITE with CRC64NVME, is **400 InvalidRequest**. A checksum that a CompleteMultipartUpload carries is compared with the one the parts make. A mismatch is **400 BadDigest** and nothing is stored.

Each part's own checksum is kept with the completed object, beside the part's size (see **Reading by part number**). A GetObject or HeadObject by part number with **x-amz-checksum-mode: ENABLED** therefore answers the part's checksum, with the object's **x-amz-checksum-type**. GetObjectAttributes lists the checksum beside each part. A single-part object answers part 1 with its own checksum. A copy keeps none of its source's part checksums, so it answers part 1 with its own whole checksum. An object completed before part checksums were kept answers its parts without one.

An object that arrives with no checksum gets S3's default: the **CRC64NVME** of its whole bytes, FULL_OBJECT. A PutObject, a POST form upload and an object a script puts compute it in the same pass that computes the ETag's MD5. They answer it as they would a checksum the client named. An upload created with no algorithm keeps a CRC64NVME of each part beside the part, shown to no client. UploadPart, ListParts and GetObjectAttributes answer none, and its parts are read by number without one. Its CompleteMultipartUpload combines these CRCs into the object's default without reading the parts again. An object stored before this, and an upload whose parts were written before it, has none, and is not given one until it is copied.

A CopyObject's checksum is of the copy's own bytes, FULL_OBJECT, as S3 makes it. It is in the algorithm that **x-amz-checksum-algorithm** names, or else in the source's algorithm, under either metadata directive. An algorithm the runtime does not take is **400 InvalidRequest**.

When the source's checksum is already of its whole bytes, the copy takes that value. For a COMPOSITE source, or one in another algorithm, the copy's checksum is computed from the bytes in the copy's one pass through them. The same holds for every copy that is encrypted or decrypted on its way. The CopyObjectResult carries the checksum with its **ChecksumType**. A source with no checksum gives the copy the default, CRC64NVME, unless the request names another algorithm.

A copy onto itself that names **x-amz-checksum-algorithm** is allowed under either directive; S3 documents this for adding or changing an object's checksum. A copy onto itself that names nothing new is still **400 InvalidRequest**. A copy made before this answers with its source's COMPOSITE value, as it was stored. UploadPartCopy computes the upload's algorithm over the bytes it copies, whatever its source's checksum, and answers it in its CopyPartResult.

## Object tags

An object has at most 10 tags. They are set with PutObjectTagging, or with **x-amz-tagging** (a URL-encoded query string, *k1*=*v1*&*k2*=*v2*). That header works on a PutObject, on a CreateMultipartUpload (the tags land on the completed object), and on a CopyObject under **x-amz-tagging-directive: REPLACE**.

A tag key is 1 to 128 characters and a value at most 256, counted as characters and not bytes. They may hold letters, digits, spaces and **+ - = . _ : / @**. Outside ASCII, every character is taken except a control, a format or a private-use character. This is wider than S3, which takes letters, digits and spaces of every script. Keys are unique, and none begins with **aws:**.

Eleven tags are **400 BadRequest**, and any other breach of these rules is **400 InvalidTag**. A Tagging document that is not valid is **MalformedXML**. A repeated key or a broken escape in **x-amz-tagging** is **InvalidArgument**. A refused put stores nothing, and a refused PutObjectTagging leaves the tags that were there. GetObject and HeadObject give the number of an object's tags in **x-amz-tagging-count**.

Tags live in the object's own header, beside its other metadata. The journal record mirrors them like the rest, so tags survive a stop, a crash and a lost journal.

A tag change keeps the object's bytes, ETag and Last-Modified, as on S3, because it does not rewrite the object. The padding of the header's first 4 KiB holds two tag slots of whole 512-byte sectors. A change is written into the slot that the last change did not use, with a sequence number and a CRC32C, and then synced (one write and one **fdatasync**(2)). A crash in the middle leaves a slot whose checksum fails, so the tags are those from before the change, never a torn header. A start after a crash reads the tags from the key's file, which is the truth.

A tag set too big for the room left in the slots is written instead as a new file, with the tags in its header and the bytes copied behind them. The new file is renamed into place like a put. This happens above about 1.5 KiB of tags with little other metadata, or for any change to a header that fills its first 4 KiB. On ext4, a change in place took 2.4 to 2.7 ms whatever the object's size. A rewrite took 12.6 ms for 4 KiB, 102 ms for 64 MiB and 1.07 s for 1 GiB. **stats** counts the two as **tag_writes** and **tag_rewrites**.

A tag change goes to the shard that owns the key, and waits behind the key's other writes in the key's lane. It is answered once the file holds the change and every shard has dropped what it holds of the key. A GET or a GetObjectTagging on any shard therefore sees the change at once.

## Multipart uploads

An upload is a directory, *dir***/***bucket***/mpu/***id***.** It holds a **meta** file, with the object the upload will become in an object header, and one file per part. Each part file is an object header followed by the part's bytes, so the runtime finds uploads again after a stop or a crash.

A part is written like a put (streamed, hashed and synced) and then renamed to its number, so it is either whole or not there. An upload is created, and its directory synced, before its id is given out. A part still arriving when the worker is killed leaves nothing behind. The upload id is 32 hex digits.

Most clients cut an object into parts of one size. When a part's place in the object is known as the part starts, the runtime writes the part at that place. For this, the upload also holds a **data** file, with room for the object's header at the front. The first part of at least 5 MiB fixes the part size. Part *n* of that size, or a smaller last part, goes into **data** at its offset. Its numbered file then holds only a header that names the place. The shard that owns the upload hands out each place once. A part sent again, a part of another size and a part sent by UploadPartCopy therefore get files of their own, as described above.

CompleteMultipartUpload checks the list against what was uploaded. The listed parts may be exactly 1 to N, all in place, and all of the fixed size except the last. In that case the runtime writes the object's header in front of them, syncs **data**, and commits it as the object itself, so the bytes are written to the disk only once.

Otherwise the runtime writes the header and copies the parts into a temporary file, a megabyte at a time on the ring, reading the placed parts from **data**. It then syncs that file and commits it. An upload that was open across a restart, or whose copy-free completion failed, always copies. Either way, the commit is a put's commit: a rename and a directory sync, with the journal record after the answer. A crash during completion therefore leaves the upload intact and no object. Only after the commit are the parts removed. The ETag is the md5 of the parts' md5s followed by **-N**, as on S3.

A copy passes the bytes through the process, because io_uring has no copy between two files. The loop never blocks on the disk, and the worker holds two one-megabyte buffers for the copy, whatever the object's size. warp, the AWS CLI and boto3 upload anything above 8 to 16 MiB as a multipart upload, so this is the path of every large upload. On a 4-vCPU VM, removing the copy took 64 MiB puts at four connections from 3.2 to 6.5 per second, and 256 MiB puts at two connections from 0.90 to 1.81.

An upload is kept until it is completed or aborted, unless **--mpu-expire** is set. Its parts count against **--max-bytes** while they are held. Deleting a bucket that holds nothing but open uploads aborts those uploads, as on S3. A part sent again needs room for both copies until the new one lands.

## Reading by part number

**GET /bucket/key?partNumber=N** (and HEAD) answers part *N* of the object, as on S3. The AWS CRT, the Java transfer manager and several Go clients use this to download a multipart object in parallel. The answer is a **206** of the part's bytes, with **Content-Range: bytes** *first***-***last***/***size***,** the part's Content-Length, the whole object's ETag and **x-amz-mp-parts-count**.

Parts are numbered from 1 to the part count, in the order the completion listed them. A single-part object (a put, or any copy) is its own part 1, answered the same way but without the parts count. An empty object answers a 200 with no body. A number past the part count is **416 InvalidPartNumber**, and a number outside 1 to 10000 is **400 InvalidArgument**. A Range header together with a part number is **400 InvalidRequest**. The conditional headers apply as on a plain GET, before the part is looked at.

CompleteMultipartUpload records the part sizes in the object's header, as **x-socketley-part-sizes**, which is never sent to a client. The header holds one size when every part except the last has that size, as in every in-place completion. Otherwise it holds the list of sizes, up to 4 KiB of it. An upload with a checksum algorithm also records its parts' checksums, in base64, up to 4 KiB of them (**x-socketley-part-checksums**). The journal carries these headers as it carries the rest of the header.

A longer list, which any upload S3 takes may need, follows the object's body in the file instead. It takes 20 bytes plus 12 per part. When it holds checksums, it takes 24 bytes plus 12 and the checksum's width per part. The header names where the list begins and its SHA-256 (**x-socketley-part-layout**). A read by part number of such an object first reads the list from the file. A list that does not match its digest is **500 InternalError**. An in-place completion whose checksums do not fit the room its header was given writes them after the last part in the same way, and still copies nothing.

A multipart object completed before part sizes were recorded answers any part number within its count with **501 NotImplemented** rather than a guess. A plain GET or a Range reads it as before.

CopyObject makes a single-part object, as on S3. The runtime hashes a multipart source's bytes on the way through, and the copy's ETag is their md5, with no **-N**. When the copy's checksum must be computed, it is computed in that same pass.

## Versioning

**PutBucketVersioning** with **Enabled** makes every PUT, CopyObject and CompleteMultipartUpload in the bucket a new version of its key. Each version has an id of its own (32 hex digits), answered in **x-amz-version-id**. The earlier versions stay. GET, HEAD, DeleteObject and the tagging operations take **?versionId=***ID* to name one version. A GET without a version id reads the latest version.

A DELETE without a version id puts a delete marker in front of the key. The answer is 204 with **x-amz-delete-marker: true** and the marker's id. After that, a GET or HEAD of the key is **404 NoSuchKey** with **x-amz-delete-marker: true**, and a GET of the marker by its id is **405 MethodNotAllowed**. A listing leaves the key out.

A DELETE with a version id removes that version for good. Removing the marker undeletes the key. Removing the latest version makes the version behind it the latest.

An object written before versioning was enabled is the **null** version. A GET, HEAD or GetObjectTagging of it names it with **x-amz-version-id: null**. **Suspended** keeps the existing versions and writes the **null** version, which the next write or delete marker replaces. As in S3, a bucket never becomes unversioned again. **GetBucketVersioning** of a bucket that was never versioned answers an empty configuration. MFA delete is refused with **501 NotImplemented**. A version id that could not be one is **400 InvalidArgument**, and a version id that the key has no version of is **404 NoSuchVersion**.

The latest version of a key is its file at the usual path. A read without a version id, on any shard, is therefore the same read as in an unversioned bucket. When a new latest version replaces a version, the runtime first links the replaced version to *dir***/***bucket***/versions/***ab***/***sha256(key)***.***id* and syncs that directory. Only then does it rename the new file over the old one. The 256 directories of **versions/** are made together with the configuration. Shard 0 changes the configuration like the CORS and lifecycle documents (see **Bucket policy**). While the owner of a key is unsure of the configuration, it writes nothing to the key, and a write through another shard is answered 503.

Each version's header carries its id and its order among the key's versions. The shard that a body lands on writes them into the header before the body is synced. The key's owner keeps these values unless a newer version of the key, or a change of the bucket's versioning, came first. That includes a change the owner learns of only by reading the configuration again before the write. In that case the owner writes the header again with its own values.

A versioned put takes a file of the pool, as an unversioned put does. It is answered at its rename, once the link of the version it replaces and that link's directory are synced. The syncs of its own directory and of **pool/** follow the answer. A crash that takes the rename leaves the put whole in **pool/**. The next start then links the version the put would have replaced before it moves the put into place. This also happens when the bucket was versioned only after the put was answered. A versioned put therefore waits for one sync more than an unversioned put when it replaces a version, and for none more when its key is new. A version removed for good is unlinked. When it is the latest, the version behind it is renamed over it instead.

The journal records each key's other versions and delete markers beside its latest object. A start after a clean stop therefore reads a versioned bucket from its journal, like any other bucket. A journal written before the journal recorded versions is read from the files once and written again. Any other start reads **versions/** in the same parallel walk as **data/**. The headers give each key's versions in order, and its delete markers. A version left under both its names by a crash between the link and the rename is kept once, as the latest. A key whose latest file is gone gets its newest version back.

With a warm cache on four CPUs, 100,000 keys of three versions each start in 0.19 s after a clean stop and in 0.86 s after a kill. Both took 1.3 s when every start read the files.

With **--shards**, all versions of a key belong to the key's owner. A shard that does not own the key reads a version by its id from the file where it is. If a rename moved the file meanwhile, the shard looks in the other place once. Before a new version, a marker or a removal that changes the latest is answered, every shard drops its held copy of the latest. **ListObjectVersions** asks every shard and merges their pages.

## Object lock

A bucket created with **x-amz-bucket-object-lock-enabled: true** is versioned and locked from the start. **PutObjectLockConfiguration** also locks an existing bucket, as S3 now allows, but only when its versioning is **Enabled**; otherwise the request fails with 409 **InvalidBucketState**. Once a bucket is locked, its versioning cannot be suspended (409 **InvalidBucketState**) and its lock cannot be removed. A configuration without a **Rule** only removes the default retention. The default retention is **GOVERNANCE** or **COMPLIANCE** for a number of **Days** or calendar **Years**. Every new version that names no retention of its own gets the default, counted from the moment the version is written.

To set a version's retention, send **x-amz-object-lock-mode** and **x-amz-object-lock-retain-until-date** on PutObject, CopyObject or CreateMultipartUpload, or call PutObjectRetention. For CreateMultipartUpload, the completed object gets the retention. To set a legal hold, send **x-amz-object-lock-legal-hold** or call PutObjectLegalHold. GET and HEAD return all three headers. A copy never inherits its source's lock; it gets only what its own request or its bucket gives it. Asking for a lock in a bucket without object lock fails with **400 InvalidRequest**. A retain-until date that is not in the future fails with **400 InvalidArgument**.

PutObjectLockConfiguration, PutObjectRetention and PutObjectLegalHold must prove the integrity of their body, and so must a PutObject that names a retention or a legal hold. The runtime accepts and checks either of these:

- **Content-MD5** or an **x-amz-checksum-*** header of the body, as S3 requires.
- A SigV4 signature over the body's SHA-256, that is, an **x-amz-content-sha256** that is a hash. This is all that an SDK from before checksums sends.

A PutObject that only receives the bucket's default retention needs neither.

A version cannot be removed while its legal hold is ON, or while its retention date is still ahead of the server's clock (UTC). A DELETE or DeleteObjects entry that names such a version fails with **403 AccessDenied**. A DELETE without a version id still places a delete marker in front of it.

**COMPLIANCE** retention cannot be overridden by anyone; it can only be lengthened. **GOVERNANCE** retention can be lengthened by anyone. Only a request with **x-amz-bypass-governance-retention: true** can shorten or remove it, change it to COMPLIANCE, or delete the version it protects, and the caller must have **s3:BypassGovernanceRetention**. Every key of the runtime has that permission unless the bucket's policy denies it. An anonymous caller has it only when the policy allows it. No bypass overrides a legal hold.

A lifecycle rule never expires a locked version. The expiry of a current version may still place a delete marker in front of it. DeleteBucket refuses a bucket that still holds versions.

The retention and the legal hold are entries in the version's header, so the journal and the index carry them too. The shard that owns the key makes each change under the key's lane. It writes the change in place into the header's tag slots, which is crash-safe in the same way as a tag change. Once a version has a lock, its slot holds its tags, retention and hold together, so a torn write leaves the previous slot intact. When the header has no room, the runtime writes the whole header again. A version that never had a lock keeps the slot format that an older binary reads.

With **--shards**, a change or removal that arrives on a shard that does not own the key is decided by the shard that owns it, and the bypass travels with the request. Shard 0 decides the bucket's configuration, as it does for versioning, in the order of the bucket's changes.

## Event notifications

A bucket's **NotificationConfiguration** (PutBucketNotificationConfiguration, GetBucketNotificationConfiguration) sends S3's event records to webhooks. Its **QueueConfiguration**, **TopicConfiguration** and **CloudFunctionConfiguration** entries are all treated the same way. Each entry has:

- an **Id**;
- a destination **arn:socketley:webhook:::***name*, where *name* is a line of **--notify-targets**;
- one or more **Event** elements;
- an optional **Filter** with an **S3Key** prefix rule and suffix rule.

The runtime emits the following events. An entry names each one by its full name or with *.

- **s3:ObjectCreated:Put**, **:Post** (a form upload), **:Copy** and **:CompleteMultipartUpload**.
- **s3:ObjectRemoved:Delete** (a key deleted, or a version removed by its id) and **:DeleteMarkerCreated** (a delete in a versioned bucket).
- **s3:LifecycleExpiration:Delete** and **:DeleteMarkerCreated** (a lifecycle rule's expiry, which sends no ObjectRemoved event).
- **s3:ObjectTagging:Put** and **:Delete**.

The other event names S3 has (ObjectRestore, Replication, ...) are accepted and send nothing.

A destination that is not a webhook's ARN, or that names a webhook the targets file does not list, fails with **400 InvalidArgument** ("Unable to validate the following destination configurations", with the ARN as **ArgumentName**). The request can skip this check by sending **x-amz-skip-destination-validation: true**. These are also refused with **400 InvalidArgument**:

- an unknown event;
- a filter rule other than one prefix and one suffix;
- two configurations with the same Id;
- two configurations that share an event on overlapping keys;
- **EventBridgeConfiguration**, which this endpoint cannot reach.

A document that is not a configuration fails with **400 MalformedXML**. An empty **NotificationConfiguration** removes the configuration. The configuration is kept in *dir***/***bucket***/notification**, and shard 0 changes it like the bucket's other configuration documents.

The runtime POSTs each event to its webhook as S3's message, with one record in a **Records** array. The request carries **Content-Type: application/json**, **Connection: keep-alive** and **X-Socketley-Event-Id**. **X-Socketley-Event-Id** is a number that a receiver can use to deduplicate events:

```
{"Records":[{"eventVersion":"2.1","eventSource":"aws:s3",
  "awsRegion":"us-east-1","eventTime":"2026-10-02T12:00:00.123Z",
  "eventName":"ObjectCreated:Put",
  "userIdentity":{"principalId":"socketley"}, ...,
  "s3":{"s3SchemaVersion":"1.0","configurationId":"thumbs",
    "bucket":{"name":"photos","ownerIdentity":{...},
              "arn":"arn:aws:s3:::photos"},
    "object":{"key":"2026/a+b.jpg","size":5821,
      "eTag":"9b2cf535f27731c974343645a3985328",
      "versionId":"...","sequencer":"00063F7A2B1C0D9E"}}}]}
```

In the record:

- The key is form-encoded as S3 encodes it: a space becomes **+**, **/** is kept, and other bytes become **%***XX*.
- A removal's record has no size or eTag.
- versionId is present in a versioned bucket.
- The sequencer is sixteen hex digits. It grows with every event of the shard that owns the key, so sorting by it puts a key's events in order.
- **userIdentity.principalId** is the requester. For a signed request it is the id of the user who owns the request's key, or **socketley** for a key that belongs to no user. For a request without credentials, let in by **--anonymous** or by a bucket policy, it is **anonymous**.
- **requestParameters.sourceIPAddress** is the client's address. An IPv4 client on a dual-stack socket appears by its IPv4 address. A client on a unix socket has no address.

A lifecycle expiry names **s3.amazonaws.com** as the requester and gives no address. A change that a script makes through **socketley.storage** names neither a requester nor an address. With **--shards**, both travel with the change to the shard that owns the key.

When a webhook is named by a host name, the runtime resolves it on a separate thread. The event loop reads the answer from an eventfd through its ring, so no delivery and no request waits on the resolver. The host is resolved:

- once at start;
- again after every one of its addresses has refused a connection, at most once a second;
- every minute while events are being delivered to it.

A host with several addresses is tried address by address before it is resolved again. Stopping the runtime waits for a resolve in progress; the system resolver's own timeout bounds that wait. **SOCKETLEY_STORAGE_NOTIFY_HOSTS** names a file of *name address* lines, one per line, that the runtime consults before the system resolver. It is a test aid.

The shard that owns a key emits the key's events, whichever shard took the request, so each change produces one event. The shard appends the event's record to *dir***/.notify/outbox.***shard* when the change starts. It syncs the record alongside the change's own syncs, together with every other record waiting at that moment. The change is answered only once both are durable. An answered change's event therefore survives a crash, and the request's path pays no second sync.

The event is sent only after the change is durable and after a second record saying the change was made. That record is synced before the next change of the key may start. At start, the runtime keeps an event that has no such record only when the object files show the change. For a write, they must show its ETag, size, time and version; for a removal, the key or version must be gone. A crash therefore never sends an event for a change that was not made.

A webhook receives up to four events at once, each on its own connection. The events of one object are sent one at a time and in the order they happened, so a removal never overtakes the write before it. An event that concerns no object waits for the previous event of the same kind. A 2xx answer delivers the event. Anything else is a failure, including a refused or failed connection and no answer within 10 seconds. A failed event is tried again after 0.25 s, with the delay doubling up to 8 s.

When an event is delivered, the runtime appends a record saying so. It writes that record at once, but syncs it with the next event's record rather than on its own. At start, the runtime sends again every event that has no such record. An event is therefore delivered at least once. It is delivered more than once only when a crash, or a 2xx answer lost on the way, leaves its delivery unrecorded.

At every start, the outbox is written again with only the undelivered events. It is also emptied once it has grown past a megabyte with nothing left to send. At most 10000 events wait per shard. Past that, a new event is dropped and counted in **notify_dropped**, and its change is answered all the same.

**stats** shows these counters per shard:

- **notify_sent**;
- **notify_failed**: failed attempts;
- **notify_queued**: events waiting now;
- **notify_dropped**;
- **notify_resolves**: host names resolved;
- **notify_connects** and **notify_reuses**: deliveries that went on a connection kept from the previous delivery.

The runtime keeps a webhook's connection open for the next event, as a proxy does with its backends. It does so when the answer is HTTP/1.1, does not say **Connection: close**, and ends where its framing says. The connection is closed:

- after 4 seconds with nothing on it;
- after a minute, so that a host name that moved is followed;
- whenever the webhook has closed it. The runtime checks for this before it uses the connection.

Over https, this saves a handshake per event: 3,000 events to a local https webhook took 4.5 seconds with a connection each and 0.6 seconds on one kept connection.

## Replication

A bucket's **ReplicationConfiguration** (PutBucketReplication, GetBucketReplication, DeleteBucketReplication) copies the bucket's new versions, and the delete markers its clients make, to buckets of another S3 endpoint — another storage runtime, or any S3. The configuration is S3's document: a **Role** and one or more **Rule**s. Each rule has:

- an **ID**;
- a **Priority**;
- a **Status** of Enabled or Disabled;
- the keys it covers: a rule-level **Prefix** in the first schema, or in the second schema a **Filter** of a **Prefix**, a **Tag** or an **And** of both;
- a **Destination** with the **Bucket** as **arn:aws:s3:::***bucket*, and optionally an **Account**, a **StorageClass** (sent as the replica's **x-amz-storage-class**) and an **AccessControlTranslation** to Destination;
- **DeleteMarkerReplication**.

The last path segment of the Role names a target of **--replication-targets**. Every rule of the configuration writes with that target's endpoint and credentials:

```
<ReplicationConfiguration>
  <Role>arn:aws:iam::123456789012:role/backup</Role>
  <Rule><ID>docs</ID><Priority>1</Priority><Status>Enabled</Status>
    <Filter><Prefix>docs/</Prefix></Filter>
    <Destination><Bucket>arn:aws:s3:::docs-copy</Bucket></Destination>
    <DeleteMarkerReplication><Status>Enabled</Status></DeleteMarkerReplication>
  </Rule>
</ReplicationConfiguration>
```

As in S3, a bucket whose versioning is not Enabled cannot be given a replication configuration (**400 InvalidRequest**). While a bucket has one, its versioning cannot be suspended (**409 InvalidBucketState**). These configurations are also refused, each with **400** InvalidRequest or InvalidArgument:

- a second-schema rule without DeleteMarkerReplication;
- delete marker replication with a tag filter;
- rules of both schemas;
- two rules with the same ID or the same priority;
- overlapping first-schema prefixes.

A Role that names no target fails with **400 InvalidArgument**. A document that is not a replication configuration fails with **400 MalformedXML**. **ExistingObjectReplication** Enabled, ReplicaModifications Enabled, a **ReplicaKmsKeyID**, and replication time control or metrics fail with **501 NotImplemented**, rather than being accepted and not honoured. The runtime does not check the destination bucket when the configuration is put. The document is kept in *dir***/***bucket***/replication**, and shard 0 changes it like the bucket's other configuration documents.

For each destination bucket, the matching enabled rule with the highest priority decides. A version is copied when such a rule exists. A delete marker is copied when that rule replicates delete markers. A rule with a tag filter never matches a delete marker, and the first schema always replicates them.

A version that is to be copied is written with **x-amz-replication-status: PENDING** in its header, and GET and HEAD return that header. The status becomes **COMPLETED** once every destination has the version, or **FAILED** once one destination has refused it. A FAILED status stays FAILED. The status is written in place into the header's slot, which then carries it together with the tags, the retention and the hold.

The rules a version is copied by are decided when its metadata is made, which happens on:

- a PutObject or POST;
- a CopyObject (the source's status is never copied);
- a CreateMultipartUpload, for the object that its completion makes;
- a script's put.

A later tag change or tag removal of a COMPLETED or PENDING version is copied too, to the same version id at the destination, as in S3. It has no status of its own. If the destination refuses it, the runtime logs it and gives up. As in S3, these are not copied:

- a version removed by its id;
- a delete marker that a lifecycle rule made;
- a version written before the configuration;
- an SSE-C version, which has no status.

The runtime copies a version with a signed PutObject streamed from the version's file. The request carries the version's Content-Type, Cache-Control, Content-Disposition, Content-Encoding, Content-Language, Expires, website redirect, user metadata and tags. It also carries the version's MD5 as Content-MD5 and its full-object checksum, and the destination checks the bytes against them. A multipart version is copied by a multipart upload with the same parts and part numbers, so the replica has the same ETag and composite checksum.

An SSE-S3 version is read in the clear, and sent over the target's https when the target's URL is https. It is written with **x-amz-server-side-encryption: AES256**, which a destination without a master key refuses. A delete marker is copied as a signed DeleteObject of the key. A tag change is copied as a signed PutObjectTagging or DeleteObjectTagging of the version. Every request carries **x-amz-replication-status: REPLICA**.

A storage runtime that is the destination judges such a write as **s3:ReplicateObject**, such a delete as **s3:ReplicateDelete** and such a tag change as **s3:ReplicateTags** (see **Bucket policy**). It honours the header only for a user whom the policies allow that action and do not deny the write it stands for. From anyone else, the request is the plain write it is. The destination marks the version REPLICA. It never copies a replica, or a replica's delete marker, any further, so two buckets that replicate to each other copy each change once.

The request also names the source's version id in **x-socketley-replica-version-id**. A storage runtime that is the destination gives that id to the replica or its delete marker, as S3 does. It does so only while the id is still newer than every version the key has there and is dated no more than fifteen minutes past the destination's clock. Otherwise the replica gets an id of its own. Another S3 stores the replication header as S3 does and ignores the other header, so there a replica's version id is its own. A replica's time and owner are always the destination's own.

The shard that owns a key queues the key's copies in *dir***/.replicate/outbox.***shard*, one entry per destination bucket. As with events (see **Event notifications**), the entries are synced alongside the change itself and before the change is answered, so a crash never copies a change that was not made.

Each target has up to 16 copies in flight, each on its own connection. A key's copies go one at a time, in the order they were made. An unencrypted body of 64 KiB or more goes to an http target straight from its file by splice, without passing through the runtime.

These failures are tried again after 0.25 s, with the delay doubling up to 8 s:

- a refused connection;
- a stall of 10 seconds;
- no answer within 120 seconds for the whole request;
- an answer of 408, 409, 429, or a 5xx other than 501.

The runtime logs the first failure of a run of retries. Any other answer, or a version whose bytes cannot be read, makes the version FAILED and is logged with the destination's error code.

An entry is retired after the version's status is written. A crash between the two copies the version again, which is harmless. At start, the runtime queues the outbox again, and also every version that its index still marks PENDING but that has no entry. An answered version is therefore copied even if its entry was lost. A target's host name is resolved off the event loop, as a webhook's is. **SOCKETLEY_STORAGE_REPLICATION_HOSTS** is the test aid that points a host name elsewhere.

**stats** shows these counters per shard:

- **replication_pending**: entries waiting now;
- **replication_completed** and **replication_failed**: versions and delete markers;
- **replication_retries**;
- **replication_bytes**: body bytes a destination accepted;
- **replication_connects** and **replication_reuses**: requests that went on a connection kept from the previous request, as for a webhook.

## Cluster

Each node of a cluster (**--nodes**) keeps every bucket, and every node takes reads and writes, so a client or a load balancer may use any of them. A node sends each change it makes to every other node. It sends from its replication outbox, in the way a bucket's replication sends a version (see **Replication**). The change is in that outbox, synced, before the client is told it was made. These changes are sent:

- a version or an object, as a PutObject or as a multipart upload in the same parts, so its ETag is the same everywhere;
- a delete marker, a tag change, a removal, and a version removed by its id;
- a version's retention or legal hold;
- a bucket created with its owner, a bucket removed, and a configuration document given to a bucket or removed from it (versioning, object lock, policy, lifecycle, CORS, encryption, tags, website, logging, quota, public access block, notification, replication);
- the IAM API's users, groups and roles;
- share links with their downloads.

A node does not send on what another node sent it. Each node runs a bucket's lifecycle rules itself, so expiries are each node's own. So are a bucket's event notifications, which only the node where the change was made sends. So is the bucket's replication to another endpoint, which only that node copies.

Every node ends with the same state, whatever order the changes reach it in:

- A version keeps the id, the time and the lock that its node gave it. A version older than the key's latest goes behind the latest rather than in front of it. A node that has not yet heard of the bucket's versioning answers such a version **503 SlowDown** until it has.
- In a bucket that keeps no versions, the object is the write made last. The time it was written on its node decides, and then the larger ETag.
- A removal is stamped with its time as well. A node keeps a record of what it removed for 24 hours, across a restart, in *dir***/.removed.***shard*. An older write that crosses the removal on its way is therefore not made. A node sends a removal even if it did not have the key yet.
- The IAM document is the one changed last on any node. If two admins change IAM on two nodes at the same moment, only the later change is kept.
- Each node counts a share link's downloads, and the counts are added up. The link's limit holds across the nodes once their counts have met.

A node that is sent a write it already has, or one older than what it has, answers **412 PreconditionFailed** to the node that sent it. That node takes the answer as delivered.

A node that was stopped is sent what it missed once it is back, as a replication target is. A change for a bucket that another lane is still creating or emptying waits for that lane for up to 15 minutes, and is then given up and logged. When a node falls more than 100000 changes behind a shard, the shard drops its queue for that node, which bounds the memory a long absence takes. Once the node answers again, the shard sends it everything instead, as described next.

A node whose data is new to another node — one that joined the cluster, or started again with an empty **--dir** — is sent everything the other node holds. Every node keeps a random id of its data in *dir***/.cluster-id**. It asks every other node for its id at start and every 30 seconds. When an id is new, the node sends:

- the IAM document;
- the share links;
- every bucket with its documents;
- every version, delete marker and object it holds, 500 keys at a time, asking first whether the other node already has each one;
- last, what it removed in the last 24 hours.

The node notes how far it got in *dir***/.replicate/seed.***shard***.***node* so a restart continues from there.

All nodes need the same credentials and the same **--sse-key-file**. An SSE-S3 object is sent in the clear over the node's endpoint and encrypted again there, so use https between nodes that are not on one host. The nodes' clocks must be within a second of one another, since the time a write was made decides between two writes of one key. An SSE-C object is not sent, because its key belongs to its client.

**stats** shows these counters per shard:

- **cluster_pending**: changes waiting for another node;
- **cluster_sent** and **cluster_failed**: changes the other nodes accepted, and changes given up;
- **cluster_in**: bucket, IAM and share records another node sent here;
- **cluster_seeds**: nodes this shard began to send everything to;
- **cluster_seeded**: versions and objects it queued for them;
- **cluster_seeding**: nodes it has not yet queued everything for, or not yet asked;
- **cluster_overflows**: queues dropped;
- **cluster_synced** and **cluster_sync_timeouts**: writes answered once the number of nodes that **sync** names had them, and writes answered once the wait was over.

Three nodes on one host, 4 KiB PutObject from 16 clients for 15 seconds: the two other nodes keep up as the writes come. When the clients stop, 4 changes are waiting, and none 0.4 seconds later. On a 4-vCPU VPS with the two other nodes on tmpfs, a node takes 1800 PutObject a second, against 2660 alone. Its own work per write grows from 450 to 557 microseconds of CPU, which is the write read back and sent twice. With 1 MiB PutObject from 8 clients, a node takes 200 a second against 415 alone, at 5.7 against 4.4 milliseconds of CPU each, with the two other nodes taking every megabyte on the same four CPUs.

## Scrub

With **--scrub**, every shard reads back each version it holds from its file, one key at a time in order. It paces the reads so that one pass over the shard's bytes takes the given period, but reads at least a megabyte a second. A pass begins one period after the previous pass began. Every 30 seconds the shard notes how far the pass got in *dir***/.scrub.***shard*, so a restart continues from there.

The bytes are checked against the MD5 that the object's header names:

- A whole object is checked against its MD5.
- A multipart object is checked part by part against the ETag its parts make.
- An SSE-S3 or SSE-KMS object is checked in its plaintext. A chunk whose tag fails also makes the object corrupt.

An SSE-C object, whose key only its client has, and an object whose parts are not recorded, are passed over and counted as skipped.

A copy whose bytes differ is logged as an error once, however many passes find it. On a runtime that is not a node of a cluster, the copy stays as it is, to be restored from a copy elsewhere. On a node of a cluster (**--nodes**), the runtime asks the other nodes in turn for the version, named by its id, or for the object of a bucket that keeps no versions. It asks with a HEAD that must answer the same ETag. The first node that holds the copy whole is asked to send it again.

Before that, the runtime takes the corrupt copy away, but only while it is still the copy the scrub read. Taking it away sends no event, sends no copy to the other nodes and records no removal. The node's copy comes back under its own id, and behind the latest version when it was behind it before. Until it is back, a read of it on this node finds nothing.

**stats** shows these counters per shard:

- **scrub_objects** and **scrub_bytes**: read;
- **scrub_corrupt**: found, each counted once;
- **scrub_skipped**;
- **scrub_passes** and **scrub_last_pass_ms**: how long the last whole pass took;
- **scrub_heals**: corrupt copies another node was asked to send again;
- **scrub_unhealed**: corrupt copies that no other node held whole.

## Compression

With **--compress**, every shard looks, one key at a time, at the versions written since its last pass that have now gone unwritten for the given duration. It compresses each such version that is stored in the clear, has one part and holds at least 4 KiB:

- The shard cuts the version's bytes into chunks of 64 KiB and compresses each chunk as an LZ4 block. A chunk that compression does not make shorter is kept as it is.
- It writes the chunks beside the version, with a table of where each chunk lies.
- It puts the result in the version's place under the key's lane, but only while the version is still the one it read.

A version is left as it was when its first megabyte, or its whole body, does not get an eighth shorter. A pass begins once a quarter of the duration, and at least a second, has passed since the previous pass's window. What each pass covered is noted in *dir***/.compact.***shard***,** so each version is looked at once. The reads go at most 64 MiB a second.

Compression changes nothing a client sees:

- The ETag, the checksums, the size and the time stay the version's own.
- A range opens only the chunks it touches.
- A copy is made of the bytes, not of the chunks.
- Replication, the scrub, media and WebDAV read a compressed version as they read any other.

A version under SSE, a multipart object and an object under 4 KiB are never compressed.

**stats** shows these counters per shard:

- **compressed_objects**: versions compressed;
- **compressed_skipped**: versions read and left, as no shorter or changed meanwhile;
- **compressed_failed**;
- **compressed_bytes_in** and **compressed_bytes_out**: the bytes of the compressed versions, and what they take on disk now;
- **compressed_passes**;
- **compressed_gets**: GETs whose chunks were opened from the file rather than from memory.

## S3 Select

SelectObjectContent runs one SQL expression over an object, with an optional ScanRange. The object may be stored as:

- CSV, with FileHeaderInfo USE, IGNORE or NONE, any field and record delimiter, quotes and comments;
- JSON, as DOCUMENT or LINES.

The answer is AWS's event stream, sent as HTTP chunks while the object is read. It holds Records events as they come, a Progress event when the request asks for one, then Stats (the bytes scanned, processed and returned) and End. When the object cannot be read after the 200 has been sent, the stream carries an error event instead.

The expression supports:

- **SELECT** * or a list of expressions with **AS**;
- **FROM S3Object** with an alias and a JSON path (**S3Object[*].items[*]**);
- **WHERE** and **LIMIT**;
- columns by position (**_1**), by header name or by JSON path (**s.a.b[0]**);
- the comparisons, **AND**, **OR**, **NOT**, **LIKE**, **BETWEEN**, **IN**, **IS NULL**, arithmetic and **||**;
- **CAST**, **LOWER**, **UPPER**, **TRIM**, **CHAR_LENGTH**, **SUBSTRING**, **COALESCE** and **NULLIF**;
- the aggregates **COUNT**, **SUM**, **AVG**, **MIN** and **MAX**.

A record over 1 MiB fails with **OverMaxRecordSize**. GZIP, BZIP2 and Parquet input fail with **501 NotImplemented**. The object is read the way a GET reads it, whether it is sealed, compressed or at a tier. The request needs everything a GetObject of the object needs, SSE-C headers included. **stats** counts **selects** and **select_scanned** (the bytes their scans read).

## Tiers

A lifecycle rule's **Transition** or **NoncurrentVersionTransition** names a tier of **--tiers** as its **StorageClass**. When a version comes due, the shard that owns its key reads it and writes it to the tier with one signed PUT. For a version of one part, the PUT's Content-MD5 is the version's own. The object is stored under *prefix***bucket***/***mtime***-***md5***-***version***/***key** in the tier's bucket, so the same version from every node of a cluster is one object there. Once the tier has it, the version's file here is reduced to its header alone. The shard puts that header in place under the key's lane, but only while the version is still the one that was read. These versions stay here:

- a version under SSE;
- a version larger than 5 GiB;
- a multipart object whose part list follows its bytes.

Listings, GET and HEAD show a moved version with the tier's name as its **x-amz-storage-class**. A GET, a range or a part of a moved version is read from the tier half a megabyte at a time, two windows ahead. It keeps the size, ETag, time and checksums it always had. CopyObject and UploadPartCopy from a moved version fail with **403 InvalidObjectState**, as S3 answers for an archived object. The scrub, replication and a cluster's seeding pass it over.

A quarter day after the previous walk, each shard walks every tier's listing. It removes from the tier whatever is no longer a version of a key the shard owns, but no sooner than an hour after the tier took it. A version deleted, expired or written over here is therefore gone from the tier within six hours.

**stats** shows:

- **tier_moved** and **tier_moved_bytes**: versions moved and their bytes;
- **tier_failed**;
- **tier_moving**: versions waiting and in flight;
- **tier_reads** and **tier_read_failures**: windows read back;
- **tier_swept**: objects removed at a tier;
- **tier_gets**: GETs read from a tier.

## Server-side encryption

**x-amz-server-side-encryption: AES256** on PutObject, CreateMultipartUpload or CopyObject selects SSE-S3. The runtime stores the object encrypted under a key of its own, and wraps that key with the runtime's master key (**--sse-key-file**). Every answer about the object says so with the same header: the PUT, the upload's steps, GET, HEAD and the copy. A GET needs nothing extra. It returns the plaintext, and its ETag is the MD5 of the plaintext, as for any object. Ranges, partNumber and conditions work as they do for unencrypted objects.

**aws:kms** (SSE-KMS) works the same way, except that the object's key is wrapped by a key derived from the master key and a KMS key id. The KMS key id is the one the request names in **x-amz-server-side-encryption-aws-kms-key-id**, or else the bucket default's, or else **arn:aws:kms:us-east-1:000000000000:alias/aws/s3** when neither names one. Any key id is accepted, and no key is kept except the master key. Every answer names the key id as the write gave it. An encryption context is accepted and not kept.

These requests fail:

- **aws:kms:dsse**: **501 NotImplemented**;
- any other value: **400 InvalidArgument**;
- a KMS key or context without **aws:kms**: **400 InvalidArgument**;
- the header on a GET or HEAD: **400 InvalidArgument**, since only a request that writes an object chooses its encryption.

**PutBucketEncryption** sets a default for every new object of the bucket whose request asks for nothing else. An **AES256** rule makes such objects SSE-S3, and an **aws:kms** rule makes them SSE-KMS under the rule's KMSMasterKeyID. The default covers puts, copies into the bucket, uploads begun in it and a script's **socketley.storage.put**. A bucket's rule is a document like its CORS rules. Shard 0 changes it after telling every shard first (see **Bucket policy**). It is kept in *dir***/***bucket***/encryption** and read at every start. A rule that no longer parses still encrypts, and the log shows an error. **DeleteBucketEncryption** stops the default for new objects and leaves the objects it encrypted as they are.

With SSE-C, the client supplies its own key with every request that touches the object, as boto3 and the AWS CLI send it. The key travels in three headers: **x-amz-server-side-encryption-customer-algorithm: AES256**, **-customer-key** (the 32 bytes in base64) and **-customer-key-MD5**. The runtime accepts SSE-C over TLS only: its own TLS, or that of a proxy that **--tls-offloaded** names. The headers over plain HTTP from anywhere else, or over a unix node, fail with **400 InvalidRequest**, and nothing is written.

The key is never stored. The object's data key is wrapped under the client's key, and only that key opens it. A GET or HEAD without the headers therefore fails with **400 InvalidRequest**. With another key it fails with **403 AccessDenied**, and with a key-MD5 that does not match the key it fails with **400 InvalidArgument**. CopyObject and UploadPartCopy open an SSE-C source with the **x-amz-copy-source-server-side-encryption-customer-*** headers. The parts of an SSE-C upload carry the upload's key. As in S3, the ETag of an SSE-C object or part is not the MD5 of its bytes; it is derived from that MD5 under the data key. Nothing of an SSE-C object is kept in memory between requests. A script's **socketley.storage.get** of an SSE-C object is refused, since the script has no key to give.

When an SSE-C upload completes, its part list is bound to its key, so a header rewritten to drop trailing parts cannot be read. S3 does not ask CompleteMultipartUpload for the customer key, but boto3 and the AWS CLI can send the three headers with it. When they do, the key must be the upload's (**403 AccessDenied** otherwise), and the data key is wrapped again with the digest of the part list, as for SSE-S3.

A completion without the headers is bound instead by an HMAC-SHA256 of the object's encryption record and its part list. The HMAC's key is derived (HKDF) from the **--sse-key-file** master key. The HMAC is recorded in the header as **x-socketley-sse-parts** and checked before every read, so every read then needs that master key too. With neither the headers nor a master key, the completion fails with **400 InvalidRequest**, naming both ways out, and the upload stays open to be completed again.

An upload begun before this binding existed completes only with the headers, since its object could not be told apart from an older one whose HMAC was removed. Without the headers, its completion fails with **400 InvalidRequest** saying so. An object of an upload begun since then is never read with its part list unbound: a missing or wrong HMAC gives **500 InternalError**. An object completed without the key before this binding existed is read as it was, unless it carries an HMAC that does not hold.

On disk, an encrypted object is its header followed by its sealed body. The header records the scheme (**x-socketley-sse**: format, SSE-S3 or SSE-C, the chunk size, whether the body is one stream or one per part, the master key's id and the wrapped data key). The body is the plaintext in chunks of 64 KiB. Each chunk is sealed on its own with AES-256-GCM and stored as a random 12-byte nonce, the ciphertext and a 16-byte tag. That adds 28 bytes per 64 KiB.

Every new object and upload is written in format 2. In format 2, each chunk is sealed together with three values. They are the part number its stream was uploaded as (0 for an object that is one stream), the chunk's index in that stream, and whether it ends the stream. Every stream ends in a chunk shorter than 64 KiB, which is empty when the stream's length is a whole number of chunks. A completed upload's data key is wrapped again with the digest of its part list, sizes and numbers. As a result, each of the following fails to open rather than read as a shorter or mixed object:

- a header cut back to a chunk boundary;
- chunks moved to another place, or swapped between two parts of one upload;
- a header that names fewer parts, or other ones.

A range or a part reads and opens only the chunks it touches. When the range reaches the end of a stream, it also opens the empty chunk that ends the stream. A chunk that does not open ends the response at that point, with a line in the log. Some objects are answered **500 InternalError** before anything else is sent: an object small enough to be read whole with its header, or one whose data key does not unwrap. Objects written in format 1, which bound a chunk to its index alone, are read as they were, and so are the parts of an upload begun under format 1.

Each part of a multipart upload is a stream of its own. It is written where the object needs it, as unencrypted parts are. It is found again by the part sizes and numbers the object records (see **Reading by part number**). A copy of an encrypted object, or into an encrypted one, is opened and sealed again on its way through, under a key of its own. A tag change, a new version and the assembly of an upload move the sealed bytes as they are.

For bodies and windows of more than 64 KiB, the chunks are sealed and opened on the hashing threads (**SOCKETLEY_STORAGE_HASH_THREADS**). Smaller ones are handled in line. A GET of an encrypted object cannot be spliced from the file. Instead, the runtime reads it a megabyte at a time, opens it and writes it from memory, reading the next megabyte while it sends the current one. An SSE-S3 object of up to 60000 bytes is kept opened in memory like any other object.

Not supported: bucket keys, and changing the master key. A rule's BucketKeyEnabled is kept and given back, and changes nothing. An object opens only under the key that wrapped its data key.

## Bucket lifecycle

A bucket's lifecycle configuration is S3's **LifecycleConfiguration** document, with at most 1000 rules. Each rule has:

- an **ID**: at most 255 bytes, unique, and generated when left out;
- a **Status**: **Enabled** or **Disabled**;
- a **Filter** that selects the objects it covers. An empty Filter covers the whole bucket. Otherwise it holds one of these: a **Prefix**; a **Tag** (a **Key** and a **Value** the object's tags must have); **ObjectSizeGreaterThan** or **ObjectSizeLessThan** (each in bytes and exclusive); or an **And** of a prefix, any number of tags and the two sizes, all of which must hold. The older form, a **Prefix** of the rule's own, is also accepted.
- at least one action.

The actions are:

- **Expiration** by **Days** or by **Date** (midnight UTC);
- **AbortIncompleteMultipartUpload** by **DaysAfterInitiation**;
- **ExpiredObjectDeleteMarker** (**true**, in an **Expiration** of its own);
- **NoncurrentVersionExpiration** by **NoncurrentDays**. With **NewerNoncurrentVersions** (1 to 100), it expires only a version that that many noncurrent versions of its key are newer than.
- **Transition** by **Days** (zero included) or by **Date**;
- **NoncurrentVersionTransition** by **NoncurrentDays**, which takes **NewerNoncurrentVersions** as well.

Each transition goes to a **StorageClass** that names a tier of **--tiers** (any other is **400 InvalidStorageClass**; see **Tiers**). A second transition of either kind in one rule is refused with **501 NotImplemented**, and the configuration that was there stays. Other errors:

- A document that is not a lifecycle configuration is **MalformedXML**.
- A value S3 would not accept is **InvalidArgument**: Days of zero outside a transition, a Date that is not midnight, a repeated ID, 1001 rules, an ObjectSizeLessThan of 0, or a NewerNoncurrentVersions of 0 or over 100.
- A tag key or value that an object could not have is **InvalidTag**.
- What S3 refuses as **InvalidRequest** is refused the same way. That is one tag key twice in an **And**, or sizes with nothing between them. It is also a tag or size filter on a rule that aborts uploads (an upload has neither yet) or on a rule with **ExpiredObjectDeleteMarker**.

The rules are synced into *dir***/***bucket***/lifecycle** before the answer, so they survive a stop or a crash. They are deleted with the bucket. With **--shards**, a change is answered once no shard can go on with the old rules. A shard that is unsure of the rules expires nothing in the bucket until it has read them (see **Bucket policy**).

Each shard carries out the rules with a sweep over the keys and uploads it owns. An object expires **Days** days after its last write, rounded up to the next midnight UTC as S3 does. For example, an object written on the 1st at 10:30 with Days 1 goes at the midnight that begins the 3rd. With a **Date**, every object under the rule goes from that midnight on, including objects written later. The sweep removes an object exactly as a DeleteObject removes it — the unlink synced, then the journal record — and a script's **on_delete** is told.

An object written again or given other tags after the sweep found it is judged as it is then. A configuration changed or removed meanwhile is obeyed. The tags and size that a filter checks come from the index in memory, so a filter on them costs the walk no reads. An upload is aborted **DaysAfterInitiation** days after it began, rounded the same way. In a versioned bucket:

- An expiring latest version is covered by a delete marker rather than removed, as S3 does.
- A noncurrent version is removed for good **NoncurrentDays** days after the version that replaced it was written. This is rounded the same way and filtered by the version's own tags and size.
- With **ExpiredObjectDeleteMarker**, a delete marker that is its key's only remaining version is removed.

A pass runs at each start, within a second of a change to the rules, and then hourly. It walks the index a page at a time, with at most eight removals in flight and a pause between steps. A bucket with a great many expiring keys is therefore worked through without holding up other requests. **stats** counts what the sweep did in **lifecycle_expired** and **lifecycle_aborted**, and each pass that removed anything says so in the log.

When a rule will expire an object, the answer to a PutObject, and to a GetObject or HeadObject of the latest version, carries **x-amz-expiration** (**expiry-date="***date***", rule-id="***id***"**). As in S3, the header names the rule that expires the object first.

**SOCKETLEY_STORAGE_LIFECYCLE_DAY_SECS** is a test aid that only the sweep reads. It makes a lifecycle day last that many seconds (at most 86400), so a rule can be watched taking effect, with passes as often as every second. It is never meant for a runtime holding data anyone wants.

## Bucket policy

A bucket's policy is S3's JSON document. It can make a bucket, or part of one, readable by anyone, for static assets or downloads, while every other request to the runtime still has to be signed. It can also refuse a signed key what the key would otherwise be allowed to do. For example, this policy lets anyone read the objects under **public/**:

```
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicRead",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::media/public/*"
  }]
}
```

The runtime accepts the part of S3's grammar that it can honour exactly. A document that asks for anything else is refused with **400 MalformedPolicy**, naming what the runtime could not accept. A policy is never accepted to do less than it says.

#### `Version`

The version must be 2012-10-17 or 2008-10-17, or left out. The **Id** may be any string.

#### `Statement`

The policy holds one statement or a list of them. Each statement has an optional **Sid** (unique), an **Effect** (**Allow** or **Deny**), a **Principal**, an **Action**, a **Resource** and an optional **Condition**. **NotPrincipal**, **NotAction** and **NotResource** are refused.

#### `Principal`

This element names the requesters that the statement applies to. * or **{"AWS": * }** means everyone, signed or not. **{"AWS": [...]}** names this runtime's users and access keys. Each entry is the access key itself, or **arn:aws:iam::***account***:user/***name* (where the name is a user's id or an access key), or **arn:aws:iam::***account***:root** for every key.

A **{"Service": ...}** principal is accepted but names no requester here. A statement that names only services therefore matches nothing, whatever its conditions, and those conditions are not checked. This way the policy that S3 documents for a log target, which lets **logging.s3.amazonaws.com** write, is accepted as it is written. Federated and canonical-user principals and roles are refused.

#### `Action`

This element names the operations the statement covers, as one **s3:***Name* or a list of them, or * alone. Names take * and **?** wildcards and are compared without case. A name must be one of S3's. Names that this runtime does not implement (s3:RestoreObject, s3:GetBucketAnalyticsConfiguration, ...) are accepted and match nothing.

Some actions cover more than one operation. GetObject covers GetObject and HeadObject, by part too. PutObject covers PutObject, CopyObject, CreateMultipartUpload, UploadPart, UploadPartCopy and CompleteMultipartUpload. DeleteObject covers DeleteObject and DeleteObjects. ListBucket covers ListObjects, ListObjectsV2 and HeadBucket. PutBucketCORS, PutLifecycleConfiguration and PutEncryptionConfiguration also cover the deletes of those configurations. GetEncryptionConfiguration covers GetBucketEncryption. The rest are named as S3 names them (GetObjectTagging, AbortMultipartUpload, ListMultipartUploadParts, ListBucketMultipartUploads, GetBucketLocation, CreateBucket, DeleteBucket, GetBucketVersioning, PutBucketVersioning, ...).

As in S3, a request that names a version with ?versionId= is judged as the version's action. GET and HEAD of a version are GetObjectVersion, and so is a copy whose source is named key?versionId=. DELETE of a version is DeleteObjectVersion, and so is each DeleteObjects entry with a VersionId. Those entries are judged one by one, and a refused entry is answered AccessDenied in the result. The tagging operations on a version are GetObjectVersionTagging, PutObjectVersionTagging and DeleteObjectVersionTagging. ListBucketVersions covers ListObjectVersions.

Object lock has GetBucketObjectLockConfiguration and PutBucketObjectLockConfiguration. It also has GetObjectRetention and PutObjectRetention, which also covers a write that names a retention. It has GetObjectLegalHold and PutObjectLegalHold, which also covers a write that names a hold. Last, it has BypassGovernanceRetention, which is checked beside the action of a request that sends the bypass header. GetBucketNotification and PutBucketNotification cover the two notification configuration operations. GetReplicationConfiguration and PutReplicationConfiguration cover the three replication ones.

A write that sends **x-amz-replication-status: REPLICA** is judged as a replication action. PutObject and the steps of a multipart upload are then ReplicateObject instead of PutObject. Such a DeleteObject is ReplicateDelete, and such a PutObjectTagging or DeleteObjectTagging is ReplicateTags. A user allowed those three actions and nothing else can therefore be the destination's replication user. The header counts only for a user allowed the replication action, and a Deny of the write it stands for still refuses the request. Anyone else's request is the plain write, and its header is ignored.

#### `Resource`

This element names what the statement covers, as one ARN or a list of them. **arn:aws:s3:::***bucket* is the bucket itself, and **arn:aws:s3:::***bucket***/***pattern* is its objects. In a pattern, * matches any run of characters and **?** matches one. The bucket must be this one, or a pattern that covers it, as **arn:aws:s3:::*** does. Because IAM's * spans a slash, that pattern, which ends in *, also covers the bucket's objects. A statement must have an action that applies to one of its resources: an object action to a key pattern, or a bucket action to the bucket. Policy variables are refused.

#### `Condition`

This element sets conditions that a request must meet for the statement to apply; every condition of a statement must hold. **IpAddress** and **NotIpAddress** test **aws:SourceIp** against addresses and CIDR ranges, IPv4 and IPv6. An IPv4 address mapped into IPv6 counts as the IPv4 address. **Bool** on **aws:SecureTransport** tests whether the connection is TLS. **StringEquals**, **StringNotEquals** and **Null** test **s3:x-amz-server-side-encryption**, which is the request's **x-amz-server-side-encryption** header, compared as given. A request that does not send the header equals no value. So **StringNotEquals** holds for it, and **Null** **"true"** holds for it alone.

PutObject, CopyObject and CreateMultipartUpload carry the header. UploadPart, UploadPartCopy and CompleteMultipartUpload take the encryption that their upload's creation chose and was judged on. So no statement with a condition on the header applies to them, whether Allow or Deny. A bucket's default encryption is not the header. S3's two statements that deny a PutObject without **AES256** therefore refuse a put that leaves encryption to the default. A client on a unix socket has no address, so it is in no range: an **IpAddress** never holds for it and a **NotIpAddress** always does.

Beyond those, IAM's operator families work on the keys that a request here carries. The operators are **String**(Not)**Equals**(IgnoreCase), **String**(Not)**Like** with * and **?**, **Arn**(Not)**Equals** and **Arn**(Not)**Like** as their string forms, **Numeric**... and **Date**... (an epoch second or an ISO 8601 time), **Bool**, **Null** and the IP pair. Each takes **IfExists** and the **ForAnyValue:** and **ForAllValues:** qualifiers.

The global keys are **aws:Referer**, **aws:UserAgent**, **aws:SourceIp**, **aws:SecureTransport**, **aws:CurrentTime**, **aws:EpochTime**, **aws:username**, **aws:userid** (the user's id, absent for a request without credentials) and **aws:PrincipalType**. The listing keys are **s3:prefix**, **s3:delimiter** and **s3:max-keys** (a listing's query). The other S3 keys are **s3:versionid**, the **s3:x-amz-**... and **s3:object-lock-**... keys (the request's headers of those names), **s3:RequestObjectTag/***key* and **s3:RequestObjectTagKeys** (the request's **x-amz-tagging** header), **s3:signatureversion**, **s3:authType** and **s3:TlsVersion**.

A key the request does not carry fails its condition, except under **IfExists**, a negated operator or **ForAllValues**, as in IAM. **s3:ExistingObjectTag/***key* is refused, since the object's tags are not read before the request is judged. Any other key or operator is refused too.

A request to a bucket with a policy is authenticated as usual and then judged. A statement applies when its action, principal and resource match the request and its conditions hold. An applying **Deny** refuses the request with **403 AccessDenied**, whatever else applies. An applying **Allow** lets in a request that carries no credentials, on a runtime without **--anonymous**. It also lets in a signed request from a user who does not own the bucket (see **Users**).

A request whose signature is wrong is refused as usual, and is never taken for an anonymous request. A presigned URL is a signed request. On a runtime with **--anonymous**, every request without credentials is already let in, but a **Deny** for * still refuses it.

A copy is also judged as a GetObject of its source, by the source bucket's policy, so an anonymous copy needs both. DeleteObjects names its keys in the body, so it is judged against every key of the bucket. A **Deny** on any key refuses it, and only an **Allow** on **arn:aws:s3:::***bucket***/*** lets an anonymous one in. A request that a policy refuses is answered before its body is read.

The policy's own four operations are decided by ownership alone, for the bucket's owner and an admin. A policy therefore can neither let an anonymous request read or change it, nor lock the owner out of removing it. The Lua **on_request** hook can still refuse a request that a policy let in (see **Lua**). The hook never sees a request that the policy refused.

The runtime compiles the document when it is set, and again when a shard starts, so each request is judged against compiled statements. As a result:

- If none of the runtime's buckets has a policy, nothing is looked up.
- A signed request to a bucket whose policy has no **Deny** looks up the bucket and nothing more.
- Only a statement that compares **aws:SourceIp** asks the kernel for the client's address, once per connection.
- The other keys are read from the request only when a statement that names them applies.

As in S3, a request that a policy lets in learns that a key is missing only if it may list the bucket the key would be in. A GET, HEAD or other object request for a missing key gets **404 NoSuchKey** when **s3:ListBucket** on the bucket applies to the requester. For an anonymous request, that takes an **Allow**. For a signed request, or on a runtime with **--anonymous**, it takes no **Deny**. When it does not apply, the request gets **403 AccessDenied**. For a copy, the bucket is the source's.

The policy is kept in *dir***/***bucket***/policy***.* A new policy is written beside the file, synced and renamed over it, so it survives a restart, and a crash leaves either the old one or the new one. The policy is deleted with the bucket.

A stored policy may fail to compile when a shard starts, because the file was edited or because this version refuses what an older one accepted. Such a policy is not skipped. The bucket then refuses every request with **403 AccessDenied**, naming why, and the log has an error saying so. The exceptions are PutBucketPolicy, GetBucketPolicy, DeleteBucketPolicy and GetBucketPolicyStatus by the runtime's keys, so the policy can be read back and replaced or removed.

With **--shards**, shard 0 makes every change to a bucket's policy and to its CORS, lifecycle and versioning configuration, whichever shard took the request. It makes them one at a time per bucket, and answers a change only once no running shard can go on with the old document. The steps are:

- Shard 0 writes the new document beside the file as *kind***.new** (empty for a removal).
- It asks every other shard to stop serving the bucket until that shard learns how the change ended.
- Only when all of them have promised, it renames the new document over the file (or removes the file), tells the shards the new document and answers.

If shard 0 cannot reach a shard, because it is stopped, starting, wedged or cut off, the change fails with **503 ServiceUnavailable**. Nothing changes anywhere: shard 0 removes the new file and releases the shards that promised.

A shard that promised and is never told the outcome serves nothing of that bucket until it reads the outcome from the files. Until then it answers 503 ServiceUnavailable, which clients retry. While *kind***.new** exists, the change is undecided; once it is gone, the file is the document. A shard reads the files again at its next request to the bucket and at its periodic sweep. A lost message therefore delays a shard but never leaves it with the old document. Between a shard's promise and the rename, a request on another shard can be answered 503 in the same way. A shard that starts while a change is undecided, or that takes a bucket up later than the others, reads the bucket's documents the same way before serving it. A runtime with no change in flight pays one counter load per request for this.

## Server access logging

For a logged bucket, the runtime writes every answer as a line in S3's server access log format, and delivers the lines as objects to the bucket's target bucket:

```
PUT /photos?logging
<BucketLoggingStatus>
  <LoggingEnabled>
    <TargetBucket>logs</TargetBucket>
    <TargetPrefix>photos/</TargetPrefix>
  </LoggingEnabled>
</BucketLoggingStatus>
```

Each line holds these fields:

- the bucket's owner and the bucket;
- the time;
- the client's address;
- the requester's access key (- for none);
- the request id;
- the operation (**REST.GET.OBJECT**, **REST.PUT.PART**, **REST.PUT.VERSIONING**, **WEBSITE.GET.OBJECT** and so on). A DeleteObjects writes a **REST.POST.MULTI_OBJECT_DELETE** line and a **BATCH.DELETE.OBJECT** line for each key.
- the key and the request line;
- the status and the error code;
- the bytes of body sent, and a put's size;
- the milliseconds from the request's start to its answer;
- the referer and user agent;
- the signature version and how it was given;
- the TLS cipher, the Host header and the TLS version.

A field this runtime does not know is -, as S3 writes a field it has nothing for. A line is written when the answer starts, so a download that is cut off is logged as sent.

Each shard holds its lines for each target. It delivers them as one object once it holds a minute's worth or 1 MiB. The object is named *prefix***YYYY-MM-DD-hh-mm-ss-***unique,* or, with a PartitionedPrefix, *prefix***owner***/us-east-1/***bucket***/***YYYY***/***MM***/***DD***/***YYYY-MM-DD-hh-mm-ss-***unique* by the delivery's date. The object is put as a client's object would be. It is encrypted when the target encrypts, and replicated and notified when the target is. An object that cannot be put, because the target was deleted or has gone past its quota, is dropped with a warning in the log. Lines still held when the runtime stops are lost, which is at most a minute of them. The target must be a bucket with the same owner as the logged one. It may be the logged bucket itself, and the deliveries are not logged. The configuration is kept in *dir***/***bucket***/logging** and changed by shard 0 like the bucket's other documents.

## Public access block

A bucket's public access block keeps it from being opened to everyone by mistake:

```
PUT /photos?publicAccessBlock
<PublicAccessBlockConfiguration>
  <BlockPublicPolicy>true</BlockPublicPolicy>
  <RestrictPublicBuckets>true</RestrictPublicBuckets>
</PublicAccessBlockConfiguration>
```

**BlockPublicPolicy** makes the runtime refuse a PutBucketPolicy whose policy is public with **403 AccessDenied**. A policy is public when GetBucketPolicyStatus reports it as public. A public policy that is already in place stays. **RestrictPublicBuckets** stops a public policy from admitting any request without credentials, including requests to the bucket's website. The runtime's users keep the access that the policy and their credentials give them, because they all belong to one account. **BlockPublicAcls** and **IgnorePublicAcls** are stored and read back but have no effect, because the runtime refuses a public ACL regardless of these settings. The block is stored in *dir***/***bucket***/public-access-block** and is changed by shard 0, like the bucket's other documents. A runtime started with **--anonymous** admits everyone regardless of a bucket's block, just as it ignores the bucket's policy.

## How objects are stored

Each object is one file at *dir***/***bucket***/data/***ab***/***sha256(key)***.** The file starts with a checksummed header that holds the key, size, ETag, content type, user metadata, tags and time. The file therefore describes itself, and any byte sequence is a valid key. The 256 directories **ab** (the first two hex digits of the hash) are created and synced together with the bucket, so a put never has to create one. Each bucket also keeps an append-only journal of puts and deletes: **index.0**, or **index.***shard* for a sharded runtime. The journal is CRC32C-framed and is rewritten when its garbage outgrows the live objects. The runtime answers listings from memory, using the journal.

A put writes a temporary file, syncs it, renames it into place and syncs the directory, and only then answers 200. A delete removes the file and syncs the directory.

A small put takes a faster path. This applies to a put of up to 1 MiB whose length is known and that carries no condition (no **If-None-Match**, not a part). The bucket keeps a few empty files ready in **pool/**, and their names are synced before any put takes one. The put writes into one of these files, syncs it and renames it into place, and is then answered. The syncs of **pool/** and of the object's directory happen after the answer. The next put or delete of the same key waits for them.

Either way, the answered object is on disk. If a crash comes before the rename is durable, the object is still whole in **pool/**, and the next start moves it into place. A file in **pool/** counts as whole only when its length and MD5 match the ones its header names. For an encrypted body this is the MD5 of the sealed bytes, kept in the header as **x-socketley-stored-md5**, because a start holds no key that could open the body.

For both kinds of put, the journal record is appended after the answer. The journal is synced once a megabyte of records has gathered, before a compaction and at a stop. It is never synced merely because the queue drained, because that sync would delay the next put's own sync. The object files are the truth and the journal is only their index, so an answer never waits for the journal. A crash at any point leaves either the old object or the new one, never a torn one, and nothing that was answered is undone.

A start after a clean stop trusts the journals, because a clean stop writes and syncs them last. Any other start removes temporary files and reads every object header to reconcile the journals with the files. A journal that is lost, damaged or missing its last records is therefore rebuilt from the objects. A delete whose record was lost does not bring the object back, because its file is gone. This reading happens before the listener opens and takes time in proportion to the object count. It is the only place where the event loop blocks on the disk: every request is served on the runtime's io_uring.

A stop first closes the listener and the connections. It then lets journal writes, directory syncs and compaction that have already begun finish, for at most a second. If they cannot finish in that time, the next start treats the stop as a crash. Each shard holds a lock on **.lock.***n* in the directory until its stop is done. A start waits up to a second and a half in total for other processes to let go. These are the process it replaces on its shard, and every process still holding a shard under another **--shards** value, whose files the start takes over. The start fails if they do not let go. This is a safety net, because the daemon forks a runtime's new workers only once the previous ones have exited (see **restart**). When a stop comes, a request that a shard has sent to a sibling and that has not been answered is answered as failed, so it does not hold up the stop.

The start after a crash reads every header, even for a file that the journal lists with the same size. An overwrite whose record was lost can leave exactly that situation, and only the header tells the two versions apart. The start is fast because it does many reads at once. The 256 directories of every bucket are shared out among threads, one per CPU the runtime may run on, at most 16 (**SOCKETLEY_STORAGE_RECOVERY_THREADS**). These threads have all finished before the listener opens. Each thread reads its directories with 128 KiB **getdents64**(2) calls, and keeps 32 opens and header reads in flight on an io_uring of its own (**SOCKETLEY_STORAGE_RECOVERY_DEPTH**; 0 reads one file at a time without a ring). All of this stays within half of the descriptors that **RLIMIT_NOFILE** leaves. Only a file at the one path its key gives, *ab***/***sha256(key)*, is read. This lets a bucket whose files match its journal one for one skip the search for records whose file is gone. If a directory cannot be read whole, or the descriptor table runs out during the scan, the start fails with the reason rather than dropping the objects it did not see.

Measured with 1 KiB objects on an ext4 virtio disk and four CPUs: 100,000 objects take 0.24 s with a warm cache (0.8 s before this was parallel) and about 1 s from a cold cache (11 to 33 s before). For 1,000,000 objects a start takes 2.3 s warm (9.8 s before) and 19 s cold (344 s before). A start after a clean stop reads only the journals: 0.07 s for 100,000 objects and 0.66 s for 1,000,000.

A body is never held in memory whole. It streams from the socket into a one-megabyte staging buffer and is hashed as it passes. From 256 KiB up, the hashing runs on helper threads, so the event loop's one core does not hash every upload. The body is written to disk while the next bytes arrive, so a gigabyte upload costs a few megabytes of memory.

A GET of 64 KiB or more is sent by **sendfile**(2) from the file to the socket without passing through the process. The event loop sends it a burst at a time; a stretch that is not in the page cache is read through the ring instead. The bytes sent this way are counted as **zero_copy_bytes** in **stats**. Smaller objects are read once, together with their header, and sent from memory with the response headers in one write.

After an object of up to 60000 bytes is first read, every shard that reads it keeps a copy in memory. Each shard keeps up to 32 MiB of copies (**SOCKETLEY_STORAGE_HOT_BYTES**) and evicts the least recently read first. Later GETs on that shard are answered from the copy without opening the file. On the shard that owns the key, a copy is used only while it is the version the index names.

With **--shards**, a shard that does not own the key has no index entry to compare with. The keys are spread over 16384 slots. The first copy such a shard keeps of a key in a slot must be one that the key's owner has confirmed is the indexed version. From then on, the owner tells that shard to drop its copy of any key in that slot. The owner does this after it commits or deletes the key and before it answers the client. This costs one round trip to those siblings, in parallel, against the milliseconds of the syncs. It costs nothing for a key whose slot no sibling has read from. A read during which a drop of its key arrived is not kept. As a result, after a PUT, copy, multipart completion or DELETE has been answered, no GET on any shard returns the bytes it replaced. The owner does not wait for a sibling that is down, and that sibling holds no copies when it starts again. A shard that starts tells the others to drop every copy of its keys, because it may have died between renaming a new version into place and telling them.

Measured with a 4 KiB GET at 32 connections on four shards, keeping the copy on every shard lowered worker CPU (summed over the shards) from 45 us to 30 us per request. Throughput rose from about 50 thousand to about 56 thousand requests per second. At one connection, CPU fell from 30 to 20 us and throughput rose from 7100 to 8100 requests per second. A 4 KiB PUT into memory-backed storage takes about 14 us longer for the round trip. Once a copy has answered a plain GET, it also keeps that GET's response headers, so a shard spends the same on a GET whether or not it owns the key. In a later measurement on four CPUs with another client, four shards took about 26 us per 4 KiB GET at 32 connections, against about 17 us for one shard. The difference is four half-idle loops that each sleep and wake every few requests, not work that only a shard does.

## Performance

The first set of measurements used warp and boto3 over plain HTTP with SigV4 on one 16-core VM with an ext4 virtio disk. The comparison was MinIO as a single node with a single drive on the same filesystem. Each test ran three alternating passes, with the box quiet before each pass.

Reads are faster than MinIO's, each at a tenth or less of MinIO's CPU:

- A 4 KiB GET at one connection is about 4x as fast (8200 against 1900 per second). At 32 connections it is 1.7x with one shard and 3.6x with four shards.
- A 1 MiB GET is 2x with one shard and 4x with four.
- A 64 MiB GET is 1.4x with one shard and 3.8x with four.

A 64 MiB put is 1.3x at one connection and 1.1x at 32 connections. That is about 600 MiB/s, which is the most this disk takes. Mixed 64 MiB loads are level with MinIO.

The second machine was a 4-vCPU VM (AMD EPYC, Debian 12, kernel 7.2). The client, warp 1.3.1, ran on the same four CPUs against one shard, in three alternating passes, and was compared with the same MinIO:

- 4 KiB GET: 3.0x at one connection and 3.9x at 32.
- HEAD 3.9x, 1 MiB GET 2.5x, 64 MiB GET 1.8x, listing 3.1x, multi-object delete 2.7x.
- 4 KiB put: 1.7x at one connection and 2.5x at 32 (about 900 and 3000 per second; this disk's sync is fast).
- 1 MiB put 1.2x; 64 MiB put level (6.5 against 6.6 per second); mixed 1 MiB loads 1.6x.

Every row used less CPU per request than MinIO: about nine tenths of MinIO's for large puts, a third to a half for small puts, and a seventeenth for reads. On this machine four shards are slower than one, because the client shares the four CPUs. Shards are for a machine with cores to spare.

From a client 31 ms away over the internet (k6, 32 connections), both servers run 4 KiB GETs and puts as fast as the round trip allows, about 800 to 880 per second. At p99, socketley takes 45 to 47 ms against MinIO's 48 to 147 ms, and it uses about 2.6x less CPU per put.

Small puts wait for the disk and for little else, so their speed follows the disk. A put of up to 1 MiB now waits for one sync, of its pooled file, instead of two (the file and then its directory). No put waits behind a sync of the journal. Previously the journal record was synced after each answer, and the next put's own sync queued behind it. Measured with warp 1.3.1, three alternating passes each:

- Dropping the journal sync raised 4 KiB puts at one connection from 77 to 104 per second.
- The pooled file raised 4 KiB puts at one connection from 107 to 118 per second in a fast phase of the disk, and left them level (35 and 34) in a slow phase.
- In the slow phase, the pooled file raised 4 KiB puts at 32 connections from about 430 to 600 per second, and 1 MiB puts at one connection from 22 to 28.
- boto3's p50 for a 4 KiB put went from 13.0 ms to 11.3 ms and then to 7.6 ms. MinIO's was 8.5 to 17 ms on the same disk, minutes apart.

Against MinIO, a 4 KiB put at one connection is level in the disk's fast phases (about 120 per second each) and 0.6x in its slow phases (33 against 54). At 32 connections it is 1.2x or more. MinIO syncs its file once and never syncs its directory, so a power cut can lose a put that MinIO has answered. Here, an answered put survives a power cut. The disk's sync latency drifts by a factor of two to three within an hour, so these rows name the phase they were measured in.

No answer waits for the journal. A stop syncs it, and a start after any other kind of stop reads every object header. That takes about a quarter of a second per 100,000 objects with a warm cache, and about a second from a cold cache, on four CPUs (see How objects are stored). Uploads of 256 KiB or more are hashed on helper threads (**SOCKETLEY_STORAGE_HASH_THREADS**). This lets a 64 MiB put at 32 connections be limited by the disk rather than by one core.

A slow body gets special handling. This applies to a body of known length that arrives slower than 4 MB/s, judged over 10 ms. The runtime lets it gather in the socket and reads it once per 10 ms tick, a tick shared by every such connection. The last 64 KiB of the body is excepted. Each tick reads everything that has gathered, even over TLS, where one receive brings 16 KiB. A body that began slowly and then speeds up is therefore read at the speed it arrives. A slow upload thus does not cost a receive and a wakeup per TCP segment. Its digests are handed to the hashing threads 64 KiB at a time. In a test, a 1 MiB put was sent in 1448-byte segments at 0.8 MB/s, eight at once. It took about 35 to 60 ms of worker CPU per MiB before this change and about 6 to 9 ms after. The same put sent at loopback speed takes about 3 to 5 ms.

## HTTP/2

A storage runtime speaks HTTP/2 (RFC 9113) as well as HTTP/1.1. It uses HTTP/2 in two cases:

- over **--tls**, with a client that offers **h2** by ALPN, as every browser does;
- in the clear, with a client that opens with HTTP/2's preface (prior knowledge). The curl tool does this when told to, and so does a proxy's h2c backend.

Each request is a stream on the one connection and runs exactly as it does over HTTP/1.1. This holds for S3, WebDAV, the web interface, share links and media alike. A browser's uploads, its player's segments and its pictures therefore no longer wait for one of the six connections a browser opens to an HTTP/1.1 server.

The runtime gives back a stream's window only as it consumes the stream's body. A disk that cannot keep up therefore holds back the client, just as a full socket does. For outgoing data, the runtime sends one frame of each stream in turn, as the client's windows allow. A stream is told that its bytes have left once they reach the connection's queue, which is kept under 1 MiB. The next piece of a file is therefore read while the previous one is being written.

The runtime's receiving limits are:

- a window of 4 MiB per stream and 32 MiB per connection;
- 128 streams open at once (the next one is refused with REFUSED_STREAM);
- header lists of up to 64 KiB, and frames of 16 KiB.

The runtime sends GOAWAY with ENHANCE_YOUR_CALM to a peer that, within ten seconds, resets more than 400 streams, or sends more than 200 PINGs or SETTINGS or 1000 empty DATA frames. It does the same for a header block larger than 80 KiB or longer than 64 CONTINUATIONs. This follows RFC 9113 and the rapid-reset advisory (CVE-2023-44487).

Over HTTP/2 a stream's file is read through the process rather than spliced, as over TLS. A connection with no open stream is closed with GOAWAY after the idle timeout. At a stop, every connection is closed with GOAWAY. **stats** counts **h2_conns**, **h2_streams**, **h2_refused**, **h2_resets_in**, **h2_resets_out** and **h2_goaways**. **SOCKETLEY_STORAGE_HTTP2=0** turns HTTP/2 off, so every client speaks HTTP/1.1.

## HTTP/3

With **--tls** a storage runtime also speaks HTTP/3 (RFC 9114) over QUIC (RFC 9000), on the same port number over UDP. This requires a build with HTTP/3, which **stats** shows as **h3:1**. **bin/build-thirdparty.sh http3** builds the static OpenSSL 3.5, ngtcp2 and nghttp3 that HTTP/3 needs, and the install script runs it.

Every answer over TCP carries **Alt-Svc: h3=":PORT"**. A browser then tries QUIC on its next request, and stays on TCP if UDP does not get through. Each request is a stream and runs exactly as over HTTP/1.1 and HTTP/2. A connection survives a client's change of address or network, and a lost packet holds up only its own stream. These are the reasons to use HTTP/3 on mobile and lossy links; on a clean wire, HTTP/2 costs less CPU per byte.

With **--shards**, the shards share the UDP port, and the kernel picks a shard by the client's address. A client that changed address may therefore reach a different shard. Every connection ID names its shard, and a shard hands a packet for another shard's connection to that shard, which answers from the same port.

The limits are:

- A stream's window starts at 1 MiB and a connection's at 4 MiB; they grow to 16 MiB and 64 MiB.
- 128 streams are open at once.
- A handshake not done in 10 seconds is dropped.
- A connection is closed after 30 seconds without a packet.

The runtime paces what it sends with BBR. BBR follows the path's measured rate and round trip rather than backing off at each lost packet. Over a 50 ms path that loses one packet in a hundred, as Wi-Fi and mobile links do, a download ran ten to twenty times faster than with CUBIC. On a clean path it was as fast. **SOCKETLEY_STORAGE_HTTP3_CC=cubic** (or **reno**) chooses another congestion control. AES-128-GCM is offered first, because every packet is sealed on its own and AES-128-GCM costs a quarter less than AES-256.

While more than **SOCKETLEY_STORAGE_HTTP3_RETRY_AFTER** handshakes are under way (default 64; 0 means always), a new client is sent a Retry. The client must prove its address before the runtime keeps any state for it (RFC 9000 8.1.2), so datagrams with forged sources cannot fill the table. QUIC uses the same TLS setup as TCP: a certificate renewed on disk is picked up the same way, and **--ca** asks for a client certificate here too.

A reverse proxy forwards only TCP, and it passes the Alt-Svc header on unchanged, still naming the runtime's port. To use HTTP/3 behind such a proxy:

- forward UDP from the port browsers reach (usually 443, which the proxy does not take for UDP) to the runtime's port;
- give the runtime the certificate browsers expect;
- set **SOCKETLEY_STORAGE_HTTP3_ADVERTISE** to the port browsers reach, or to 0 to advertise none.

**stats** counts **h3_conns**, **h3_streams**, **h3_retries** and **h3_forwarded** (packets handed to another shard), and shows the connections open now as **h3_open**. **SOCKETLEY_STORAGE_HTTP3=0** turns HTTP/3 off.

## Quotas

A bucket's quota limits how many bytes its objects and versions hold, and how many of them there are. The quota is socketley's own document; S3 has no counterpart:

```
PUT /photos?quota
<BucketQuota>
  <MaxBytes>10737418240</MaxBytes>
  <MaxObjects>100000</MaxObjects>
</BucketQuota>
```

Either element may be left out, and 0 means no limit. Only an admin, the runtime's own key, or anyone on an **--anonymous** runtime may set, read or delete a quota, because a quota limits what the bucket's owner may store. The quota is stored in *dir***/***bucket***/quota** and is changed by shard 0, like a bucket's other configuration documents. It survives a restart. A user's **max_bytes** (see **Users**) limits the total that all the buckets owned by that user hold together.

A write that would take a bucket or its owner past a quota is answered **403 QuotaExceeded** and stores nothing. This applies alike to a PUT, a POST, a copy and the completion of a multipart upload. An overwrite counts only the bytes it adds beyond the object it replaces, and does not add to the object count. In a versioned bucket every version counts, including delete markers.

The shard that owns the key checks the quota at the commit, one write at a time, so writes racing each other cannot pass it together. That shard also refuses a body of known length before reading it. Under **--shards**, each shard holds its share of a quota, as it does of **--max-bytes**. A bucket whose keys are spread unevenly over the shards is therefore refused somewhat before the whole quota is reached. The parts of a multipart upload are not counted until the upload is completed.

## Website hosting

A bucket with a website configuration is served to browsers under **--website-domain**, in the way S3's website endpoints serve a bucket:

```
socketley create storage media -p 9000 --dir /srv/objects \
    --credentials /etc/socketley/s3.keys --website-domain web.example.com -s
```

Any S3 client then puts the site's configuration on its bucket and uploads its files:

```
PUT /docs?website
<WebsiteConfiguration>
  <IndexDocument><Suffix>index.html</Suffix></IndexDocument>
  <ErrorDocument><Key>404.html</Key></ErrorDocument>
</WebsiteConfiguration>
```

After that, **http://docs.web.example.com:9000/** serves the bucket's **index.html**.

A website request is never treated as signed. The runtime judges it as a request with no credentials, whatever it carries. A page is therefore served only when the bucket's policy lets anyone read it (**Principal "*"**, **s3:GetObject**). On an **--anonymous** runtime every page is served. Only GET and HEAD are served, the query is ignored, and the page is the latest version of the key.

A key that is empty or ends in **/** gets the index document's suffix appended, so **/guide/** serves **guide/index.html**. A key without the trailing slash, whose folder has an index document, is answered **302** to the folder, so that the page's relative links resolve. An object stored with **x-amz-website-redirect-location** is answered **301** to that location.

Routing rules redirect requests:

- A rule whose only condition is KeyPrefixEquals redirects before the object is looked up.
- A rule with HttpErrorCodeReturnedEquals redirects a failure with that status.
- A rule's Redirect may replace the key or its prefix, and may name a host, a protocol and a 3xx code. The defaults are the request's own host and protocol, and 301.
- RedirectAllRequestsTo sends every request to its host, keeping the key.

A failure that no rule redirects is answered with the ErrorDocument and the failure's status, if the policy lets anyone read the ErrorDocument. Otherwise it is answered with an HTML page that names the error's code, message and request id, and with an **x-amz-error-code** header. As on S3, a missing key is **403 AccessDenied** rather than **404 NoSuchKey** when the policy lets anyone read the bucket's keys but not list them. The S3 API is still served on the same port, so a site can be uploaded and read over both.

## Drive, links, media and the web interface

Paths that begin with **~**, which no bucket name can, are the runtime's own applications. They are served on the S3 port and use the S3 runtime's users, policies and versioning:

#### `/~dav/`

A WebDAV drive (classes 1 and 2) for Windows, macOS, Linux file managers, rclone and phones. It signs in with HTTP Basic: the access key is the user name and its secret is the password. A runtime without credentials asks for none.

The drive's root lists every bucket the user owns or that a bucket policy lets the user list; an admin sees every bucket. A bucket's keys appear as files, and the slashes in a key are folders. A file's GET, PUT, DELETE, COPY and MOVE are the S3 operations, judged by the same policies. MKCOL at the root creates a bucket. Inside a bucket, MKCOL creates an empty *folder/* marker object, as S3 browsers do.

A folder's COPY, MOVE and DELETE apply to every key under the folder. A copy reads each object whole, so an object larger than 256 MiB, or one stored under a client's own key, is not copied, and the answer is **500**. A COPY or MOVE with **Overwrite: F** is answered **412** when its Destination holds a file, or, for a folder, any object under it. Otherwise the COPY or MOVE replaces the destination. Locks are granted but not enforced, and properties are not kept.

Failed sign-ins are rate-limited per address. The count covers Basic sign-ins here, at **/~ui/** and at **/~media/**, and passwords of share links. After ten failures within a quarter hour, the address is answered **429** with a **Retry-After** until that quarter hour ends, even when it then sends the right secret. Sessions already signed in from the address go on working. An IPv6 address is counted by its /64. Each shard counts on its own, so an address has ten tries per shard. Behind a proxy every client has the proxy's address, so one client guessing there also keeps the others from signing in.

A file may also be uploaded in parallel parts, using S3's multipart upload under the drive's sign-in. Each step is judged as the S3 operation it is. **POST ?uploads** on the file begins an upload and answers its UploadId. **PUT ?partNumber=***n***&uploadId=***id* streams a part and answers its ETag. **POST ?uploadId=***id* with S3's CompleteMultipartUpload body assembles the file from the parts. **DELETE ?uploadId=***id* abandons the upload. **GET ?uploadId=***id* lists the parts that have arrived, with **max-parts** and **part-number-marker** for the next page. An interrupted upload can therefore resume where it stopped. A file's other PUTs ignore their query.

```
[drive]                      # rclone.conf, then: rclone copy ~/photos drive:holiday
type = webdav
url = http://host:9000/~dav/
user = AKIA...
pass = <the secret, as rclone obscure prints it>
```

**GET /~dav/***bucket***/***folder***/?zip** downloads the folder as one ZIP, saved as *folder*.zip. **?zip&n=***name***&n=***name* includes only the named files and folders of it. A bucket's root accepts these queries too. The ZIP is streamed as it is read, and each file is stored without compression. Its Content-Length is therefore known before the first byte, and a browser shows the download's progress. Each entry's CRC-32 is computed as its bytes pass and follows them in a data descriptor. A file or an offset past 4 GiB uses ZIP64.

An entry's name is its key relative to the folder, with empty, “.” and “..” segments removed. “\” and control characters become “_”. Where another entry already has the name, “ (2)”, “ (3)” and so on is added before the extension. No key can therefore unpack outside the folder or over another file. The ZIP holds only what the user may read, and leaves out objects that only their client's key opens. If an object changes while the ZIP is being sent, the connection ends, because the length was already promised.

In a versioned bucket a deleted file becomes a delete marker, and its versions stay. **GET /~dav/***bucket***/***folder***/?trash** lists, as JSON, the files under the folder whose latest version is a marker. Each entry has the key, the time of the deletion and the size of the version behind the marker. **POST /~dav/***bucket***/***key***?restore** removes the marker and brings that version back. A lifecycle rule's NoncurrentVersionExpiration empties the trash.

**GET /~dav/***bucket***/***folder***/?list** returns a folder's listing in the form the web interface reads. It is JSON with the subfolders' names and the files' names, sizes, times in milliseconds and types (**{"d":[...],"f":[[name,size,mtime,type],...]}**). It is about a tenth of the size of a PROPFIND answer, and has an ETag of its own. A repeated request with **If-None-Match** that finds nothing changed is answered **304** with no body. A folder of 20,000 files took 9.9 MB and 44 ms as a PROPFIND, and takes 1.0 MB and 9 ms this way; a browser read it in 40 ms rather than 400.

**POST /~dav/***bucket***/***key***?unzip** unpacks a ZIP object on the server into a folder beside it. The folder is named after the archive without its extension, numbered (*name* (2)) when that name is taken. Nothing is overwritten, and none of the archive's data crosses the client's line. Each file is read from the archive, inflated if it is deflated, and checked against its CRC-32 and size. It is then written as an object of its own, four at a time, in the same way as the drive's other writes: encrypted when the bucket encrypts, and typed by its extension. An empty folder in the archive becomes that folder's marker object. ZIP64 archives are read. Names in UTF-8 are kept, and older names are read as code page 437.

The unpacking skips a file that is encrypted, packed other than stored or deflated, or named outside the folder (**..**, a control character). It also skips macOS's **__MACOSX** tree, **.DS_Store** and **Thumbs.db**, without reporting them. Unpacking needs GET on the archive and PUT under the folder. Once every file is written, the answer is JSON that names the folder. It counts the files, folders and bytes written and the files skipped and failed, with up to 20 names of each. The status is 201 when none failed and 500 when any did. An archive whose directory is over 64 MiB, or that holds more than 100,000 entries, is refused. The job runs to its end even if its request is abandoned. In a test, 549 MiB unpacked from a 312 MiB archive of 502 files in 2.1 s, on four CPUs with two shards; other requests were answered meanwhile in under 35 ms.

#### `/~share/`

Share links to an object or a folder, which anyone holding a link can read without credentials. **POST /~share** with a JSON body creates a link; the request is signed with SigV4 or Basic, as above:

```
{"bucket": "holiday", "key": "2026/", "expires_in": 604800,
 "password": "...", "max_downloads": 0, "upload": false, "note": "..."}
```

A key that ends in **/**, or no key at all, makes a folder link. A folder link is read as a page, as JSON with **?format=json**, and file by file under it. **upload** lets a visitor PUT files into the folder. The maker must be able to read what the link names, and, for an upload link, to write there.

A link acts as its maker: each request is judged as the maker's own request would be. Reading a file through the link is the maker's GetObject of that key. A folder's page, list and ZIP are the maker's ListBucket, and the ZIP leaves out each file the maker may not read. An upload is the maker's PutObject. A link that its maker may no longer use is answered **403**. A link is answered **410** when its maker is no longer a user of the runtime or is disabled, or when its bucket was removed and created again under the same name.

A link's password is asked for with Basic, with any user name, and is stored salted and hashed. **max_downloads** counts each read from the start of a file, and not a player's later range requests. **?download** asks a browser to save the file. A folder link read with **?zip** returns the folder, or the part of it that the path names, as one ZIP, as the drive gives it. This counts as one download, and the folder's page offers it. An expired link is answered **410** and is removed at the next listing. **GET /~share** lists the caller's links, or every link for an admin. **DELETE /~share/***id* revokes a link.

**"burn": true** makes a link that removes what it names when the link ends, like a file sent once. The link ends at its expiry, at its revocation, or ten minutes after the last download its limit allows (so a browser resuming that download still finds it). A burning link needs **expires_in** or **max_downloads**, cannot be an upload link, and can be made only by a user who may also delete there. A cluster does not make burning links. A burning link to a file opens on a page that describes the file. This page counts no download, so a chat's preview of the link costs nothing. The file itself is read with **?download**.

The runtime's sweep checks the links every five seconds. It renames a link that has ended to *id*.burning, which no reader opens, stamped with the time, and then removes what the link names. The shard that renamed the link does the removal. If a stop left a link stamped more than a minute ago, the first shard to see it takes over the removal. In a versioned bucket the removal is a delete marker, and the versions stay.

**"notify": "https://..."** gives a link a webhook. The runtime POSTs a JSON object to it at each download the link counts, and when a burning link's target is removed. The object has these fields: **content** and **text** (a sentence, as Discord and Slack show it), **event** (**downloaded** or **deleted**), **bucket**, **key**, **downloads**, **max_downloads** and **expires**. A notification the hook does not accept is posted again, in the same way as a bucket's webhook events. It is kept across a restart in **.share-notify** under the runtime's directory.

Because the runtime makes the request on behalf of the link's maker, the URL must begin with one of the comma-separated prefixes in **SOCKETLEY_SHARE_NOTIFY_ALLOW**. By default these are the webhooks of Discord (**https://discord.com/api/webhooks/**, **https://discordapp.com/api/webhooks/**), Slack (**https://hooks.slack.com/**) and **https://ntfy.sh/**. Any other URL is answered 400. A webhook gets up to four requests at once, at most 16 wait, and requests about one file are sent one at a time.

Links are files in *dir*/.shares/, and every shard reads them. Each link has a mark under *.shares/owner/* by its maker and, for a burning link, a mark under *.shares/burn/*. A user's list and the search for burning links therefore read only those marks. A link with no marks, as an older build made them, is read once at a start.

#### `/~media/variant/bucket/key`

Media that ffmpeg makes from an object, kept for later requests.

**thumb-***width* (64, 128, 256, 320, 480, 640, 960, 1280 or 1920) is a JPEG still of a picture, or of a film a few seconds in.

**info** describes the object as JSON. It gives the length, picture size, frame rate and codecs, and whether the object is HDR. It gives the MIME type with codecs, which the interface uses to ask a browser whether it plays the file itself. It lists the codecs of the copied stream, the renditions and the text subtitles. It lists every sound track with its codec, channels, language, title and whether it is the default. It lists the chapters with their start, end and title. For a song it gives the tags (title, artist, album, album artist, track, disc, date, genre). These come from the container or, for a file without a picture, from the sound stream, as Ogg keeps them.

**trick** is a film's stills for a seek bar: one JPEG of 160x90 tiles, ten per row. There is one still every two seconds, or every 1/200 of the film if that is longer. The **trick** field of info gives the seconds between stills, their count and their layout. The stills are taken from the keyframes alone, or from every frame when the keyframes give none. They are made in a place of their own beside the thumbnails, one job at a time per shard.

**sub-***stream***/subs.vtt** is a text subtitle stream (SubRip, ASS, mov_text, WebVTT) converted to WebVTT, on the film's clock. **sub-***stream***/index.m3u8** is its HLS playlist. Subtitles that are pictures are not offered.

**hls/***bucket***/***key***/master.m3u8** is an HLS master playlist of the renditions, with their size, peak bitrate and codecs. A player switches between them as its bandwidth allows. The master names one rendition for every rung of 2160, 1440, 1080, 720, 480, 360 and 240 that the picture fills in at least one dimension. Each rendition is fitted into its rung's 16:9 box and never enlarged, and 720 is listed first. The master also names the source's own picture, copied, when it is H.264 or HEVC (HEVC is tagged hvc1), and the text subtitles as a SUBTITLES group. BANDWIDTH is the most a segment can carry, a quarter over the rung's cap. The levels are 4.2 up to 1080 and 5.2 above. The URLs a master names carry the object's version, so their answers can be cached for good. Every medium's answers carry an ETag that a client can revalidate with (answered 304), and accept a Range.

**hls-***height***/index.m3u8** is one rendition: H.264 held to its rung's bitrate, with AAC sound, in CMAF segments of four seconds. Its playlist is complete from the start, written from the film's length, so a player can seek anywhere at once. The segments are made as they are requested. A request for a segment at or a little past the point where a job is working waits for that job. A request elsewhere starts a new job at that point. Jobs work on the film's own clock, so the segments of every job join up, and every job's init segment is the same bytes. A length over 99,999 segments (about 111 hours), or a length that is not a number, is treated as no length. The info variant then gives 0, and a rendition is answered 415, as for a film with no length.

A request for an init segment with no job running starts a job at the beginning at once. A seek that follows releases that job, and the job is paused after two seconds if no segment of it is requested.

Several jobs can run over one film for viewers at different places. A job ends when it reaches segments that were already made. A job is paused when it is fifteen segments ahead of every player that requests from it, or two ahead when nobody has requested from it for ten seconds. It resumes when a player comes within eight segments. A job ends when nobody requests from it for a minute while it is paused, or for ten minutes while it runs. A paused job with no requests gives its place to a new job when the shard has eight jobs. Where renditions are made on a GPU, the limit is 24 jobs shared among the shards, and never fewer than eight.

What the jobs make is kept, so a film watched once streams from the cache afterwards. HDR (PQ or HLG) is tone-mapped to SDR for these renditions. Where a GPU with VAAPI is present, a rendition is decoded, scaled, tone-mapped and encoded on it, as **SOCKETLEY_MEDIA_HWACCEL** describes. An HDR film without the mastering display metadata that the GPU tone-maps from is made with x264 instead. Where the copied stream has not yet been remuxed up to the current position, the interface plays that part from a rendition until the copy catches up.

A variant with **-a***n* appended, such as **hls-a1**, **hls-720-a1** and **hls-copy-a1**, carries the film's sound track *n* instead of the first. Tracks are counted from 0 among the sound tracks, as info lists them. The track is made or copied with its own codec and channels. Its master names its streams with the same suffix. Each stream is made and kept as a stream of its own, so the picture is made again for the other track. **hls-copy** streams the source's own picture without transcoding. It copies the sound when the sound is AAC in two channels or fewer, and converts it to AAC otherwise. Renditions always convert the sound to AAC, because a copy begun at a seek would start at the keyframe before the seek point.

The object is read as a GET of it would be: by its user or, under **/~media/***variant***/~share/***id*[**/***path*], through a share link. ffmpeg, and the ffprobe beside it, read an unencrypted object's file directly; the shard keeps that file open for a minute. They read any other object over the runtime's own listener, at an address signed for that version of the object by a key in *dir*/.media/key*.* They read it with a single-file demuxer, never with one that opens URLs that the object names (HLS, DASH, concat). What they make is stored in *dir*/.media/ under the variant, the object's key and its ETag. A new version is therefore made anew, and every shard serves what any shard made. A thumbnail is made only once, however many requests ask for it at the same time.

A shard runs as many thumbnails and probes at once as it has cores of the host's share, and at least two. Each runs ffmpeg with one thread: a 1600x1200 JPEG's thumbnail took 166 ms with ffmpeg's threads and 72 ms without. A shard also runs up to eight streams at once. The ring polls a pidfd for each job, so the result is served as soon as ffmpeg exits, not at the next check. A request waits up to a minute for its medium. An object ffmpeg cannot read is answered **415** for two minutes. An ffmpeg that a dying worker left behind is found by its pid and ended. See **SOCKETLEY_FFMPEG** and **SOCKETLEY_MEDIA_CACHE_MB**.

#### `/~ui/`

A web interface: one page, served from the binary. A browser that asks for the runtime's root is redirected here when the request has no query and no signature and its **Accept** header includes **text/html**. The host's name alone therefore reaches the interface. An S3 client sends none of that, so **GET /** is still ListBuckets for it.

The interface signs in with an access key and its secret. It sends them once, to get the session cookie described below, and stores them nowhere. It browses libraries (buckets) as a media library. Films, pictures, music and documents appear in their own rows, with thumbnails, lengths, and what the user left half watched on any device. Films named S01E02 or 1x02 are grouped by season, in order, and play on into the next episode. A folder's or library's card shows a picture in it called folder, cover or poster, or else its first picture or film. More than twelve pictures are grouped by the month of their date: the camera's date (see **/~ui/taken**), or else the object's. Pictures play as a slideshow. A ZIP's menu unpacks the archive beside itself on the server (**?unzip** above).

The interface uploads several files at once, through the drive's multipart upload above. A file of 48 MiB or more is sent in parts of at least 16 MiB. Four requests run side by side, shared among up to three files, and each request goes to the file with the fewest requests under way. Over HTTP/1.1, while a film or a song plays in any of the browser's tabs, uploads use only one request, because a browser opens at most six connections to such a server. The tabs tell each other on a BroadcastChannel. Uploads take four requests again once the player is closed. Over HTTP/2 (see above), uploads keep all four requests beside the player. Each file shows its percentage, rate, time left and start. Folders can be uploaded too, by dropping them or choosing one.

A file in parts whose connection is lost is paused, and resumes when the connection is back. A file left by a closed or reloaded page is shown again with how far it came. It resumes from the parts the server lists once the user chooses the file again: the same name and size, and the same modification time or a confirmation. Each part, and each file sent whole, carries its CRC-32 in **x-amz-checksum-crc32**, which the server checks against what arrived. A part refused as **BadDigest** is read and sent again.

The interface can select several items to download or delete, rename, share, restore from the trash and show pictures one after another. It opens text in an editor that highlights code, finds and replaces, previews Markdown and saves with Ctrl+S, and it makes new text files. Its search box filters the open folder and searches every library. Items dragged onto a folder, a library or a breadcrumb are moved there. The page requests the open folder again every five seconds while the page is visible (every thirty seconds past 2000 entries), so changes from another device show within seconds. A download is the object byte for byte: the drive's GET with **?download**. A browser resuming an interrupted download sends that request again with the cookie. The owner of a library shares it from the page with other users, to view or to edit, through **/~ui/access** below.

Send a file sends files the way wormhole does. The files are uploaded into the user's library for temporary files, **tmp-***user***.** This is the user's id in lowercase; the library is made when first needed and is shown as Temporary files. Each sending goes into a folder of its own, behind a burning link (see **/~share/** above). It is deleted after a chosen time or number of downloads (for several files, that number for each file). It can have a password and a webhook that is told of each download. Once a picture or a film is uploaded, the page requests its thumbnails and facts. For a film this browser would not play itself, it also requests the start of its stream. The server therefore makes these before anyone waits for them. Five colour themes can be chosen from the sidebar, and the choice is kept in the browser.

The interface signs in with **POST /~ui/session** and Basic credentials. These are either a user's name and the password of its login profile (see IAM above), or an access key and its secret. The answer sets the cookie **skl_ui** (HttpOnly, SameSite=Strict, Secure over TLS). The cookie holds the access key (or **~***user* for a password), the time it was made, an expiry, and an HMAC-SHA256 of these under the key's own secret. Every shard and node therefore checks it the same way. When a key's secret changes or the key is removed, its sessions end. A session lasts twelve hours and the browser's session, or thirty days with **?remember**. **GET /~ui/session** says who is signed in, and **DELETE /~ui/session** signs out.

**POST /~ui/session?everywhere** ends every session of the user made before it, in each browser. It does this by storing its time in *dir*/.ui/sessions/. The other shards follow within a second. A sign-in with Basic credentials is not a session and keeps working.

/~dav/, /~media/ and the management of /~share/ accept the cookie as they accept Basic credentials, so the page's script never holds the secret. A change made with only the cookie (any method but GET, HEAD, OPTIONS and PROPFIND) must carry the header **X-Socketley-UI**, which no other site's page can add. Without it, the change is answered 403. A session never creates a new session. A file's **GET /~dav/***bucket***/***key***?download** is saved under the file's name.

The page's Account section sets and changes the user's password. It also creates, deactivates and deletes the user's access keys; a new secret is shown once. An admin's Users section lists every user with how the user signs in. There an admin can create a user with a password (optionally to be changed at the first sign-in). The admin can set a user's password, display name, email, quota, admin status and whether the user makes libraries of its own, and can disable and delete users.

An admin can also invite people. An invitation is a link, **/~ui/#invite=***token***,** that lets one person choose a user name and password of their own, once. It is valid for one to thirty days, and makes the user an admin or gives a quota if it says so. Only the SHA-256 of its token is stored, in *dir*/.iam.json beside the users. Sharing a library offers the users by name.

**POST /~ui/iam** with **{"Action":** *action***,** *its fields***}** runs an IAM action as the signed-in user, judged and answered as IAM's own. **GET /~ui/users** lists the users. Any user sees each user's id and name; an admin sees all fields, and the open invitations. **GET /~ui/invite?token=** says whether an invitation is valid. **POST /~ui/invite** with **{"token", user , password , name , email }** accepts it without a session. A token that is not valid counts as a failed sign-in.

**GET /~ui/progress** lists the films the signed-in user has partly watched, most recent first, with the position, the length, the size and the type. It lists only films the user may still read, in the version watched. A film replaced or removed since, or one whose access was taken away, is left out. **POST /~ui/progress** with **{"bucket", key , t , d }** stores where the user left a film; a t below 0 forgets the position. Each user's positions are a file of their own in *dir*/.ui/progress/. The file is changed entry by entry under a lock, so two devices watching different films both keep their positions. The latest 200 are kept. Nodes of a cluster keep their own positions.

**GET /~ui/search?q=***text*[**&bucket=***name*] lists the files and folders whose own name contains the text, matching ASCII letters in any case. It searches every library the user lists, or only the one named. It returns folders first, at most 200 results, with **more** set to true when there were more or a library was too large to list whole. A file is listed only where the user may read it. Each library is listed whole for the search.

**GET /~ui/taken?bucket=***name***&prefix=***folder/* says when and where the photos directly in a folder were taken, from their EXIF data. It covers each JPEG, TIFF or HEIF (HEIC) the user may read. For each it gives the key, the **taken** time as the camera's clock wrote it ("2021-07-14T18:03:22", with "+02:00" where the camera wrote its offset), and the **lat** and **lon**. The runtime reads the first 64 KiB of each file, and a HEIF's Exif item where it lies further in. What was read is kept in the shard's memory, keyed by the object's ETag. An object stored encrypted, compressed or in a tier is left out. So is everything past the folder's first thousand keys (**more**). The page groups a folder's pictures by the month they were taken, and shows the time in the viewer. It links to the place on openstreetmap.org, which the page never loads itself. It shows a HEIF as its thumbnail, which ffmpeg makes from version 7.1 on.

**GET /~ui/usage** lists every library the user lists. For each it gives the owner, whether the library is shared with the user, and its bytes and objects. These are summed from the library's listing, which holds every shard's keys, and kept for a minute. **partial** is set when the library was too large to list whole. The library's quota is also given. Besides the libraries, the answer gives the user's own quota over the libraries it owns, and whether the user is an admin. **POST /~ui/usage** with **{"bucket", max_bytes , max_objects }** sets a library's quota as **?quota** does; 0 means no limit. Like **?quota**, it is for admins only. The page's Storage section shows these figures as bars.

**GET /~ui/access?bucket=***name* says who else a library is shared with. **POST /~ui/access** with **{"bucket", user , access }** shares it, by id, with a user of the credentials or the IAM API. The access is **read** (list and read), **write** (also write, delete, and restore from the trash) or **none** (take the access back). Each share is a statement in the bucket's policy, named by its Sid **socketley-ui-***access***:***user*. Only those statements are read or changed: the rest of the policy is kept, and a Deny in it still holds. Both requests are for whoever may read or write the bucket's policy: its owner and an admin. The drive's root lists the buckets a user owns and also every bucket whose policy lets the user list it.

A film's share link is a page that plays the film. A chat embeds the page as a player once the film's web copy, **/~media/web/***bucket***/***key*, is made. The web copy is H.264 in an MP4 of at most 46 MiB and 1440 lines. It is made when a link asks for it, or when the film is put into a library tagged **socketley:web-copies=on**. **GET /~ui/library?bucket=***name* says whether a library has that tag. **POST /~ui/library** with **{"bucket", "web_copies"}** sets or removes the tag, for whoever may change the bucket's tags.

The interface plays films and music, with their subtitles. Where the browser plays the file itself, it plays the file, which costs the server nothing. Otherwise it plays the master playlist's streams through Media Source Extensions. It uses the copied stream where the browser supports its codec and the connection can carry it, and otherwise renditions chosen by measured bandwidth. Where the browser has no Media Source at all, it uses the browser's own HLS. The player's quality menu offers Original (the file, or the copied stream where the browser does not play the file), Auto and each rendition. A change of quality is made on the same media source. It keeps the next six seconds already buffered while the new stream's first segment is made.

## Git repositories

The page's Sync section keeps git repositories in a library. Each repository is pulled when it is added, whenever its user asks, and on its own schedule, as its Pull every setting says. The schedule is every day, week or month from 3:00 local time, or never (the default). When any ref has moved since the last run, the run writes the branch's files under *name***/** in the library. It writes what changed, or the whole tree the first time, and leaves nothing else beside the files. It also writes a git bundle of the branch and the tags (or of every branch, with *) under **_backups/***name***/***date***_***time***_***commit***.bundle***.*

**git clone file .bundle** makes the repository from a bundle, with its branch checked out. A run with nothing new writes nothing. Every bundle of the last day is kept. Before that, the newest bundle of each of the last 14 days, 8 weeks and 12 months is kept, and the rest are deleted. Symbolic links and submodules are not files and are left out.

**--sync** chooses which runtimes do the runs. With **never** (the default), the storage makes no sync runtime, and the page says that an added repository would not run. With **active**, the runtime's first shard makes one **sync** runtime for the whole storage, *storage***-sync***.* It pulls every user's repositories, each with that user's own credentials. With **per-user**, the storage makes a separate **sync** runtime for each of its users, *storage***-sync-***user***.**

Either kind of sync runtime is owned by the storage. It stops when the storage stops and comes back when the storage starts. **socketley ls** and the dashboard list it with its **runs**, **failures**, **running** and **last_error**.

A sync runtime runs **socketley git-sync** for that user's repositories alone, one at a time. It uses temporary credentials of the user, which the storage hands it in *dir*/.ui/sync/ with mode 0600. The credentials last twelve hours and are renewed when three hours are left. It works through the runtime's own S3 API on its port. It therefore cannot write what the user may not write, quotas and versioning apply, and a missing library is created as the user.

A failed scheduled run is retried an hour later. A run the user asks for is the file *dir*/.ui/git/*id*/asked, and the user's sync runtime starts it within a second. Each repository's bare clone, the state of its last run and its log are under *dir*/.ui/git/*id*/. The list of repositories is *dir*/.ui/git.json*.* Git must be installed. A runtime on a unix socket has none of these features.

A repository is fetched over https://, http:// or git://, never with credentials in its URL. A private repository is read with the GitHub token the user keeps in the page. The token is passed as git's http.extraHeader through git's environment, so it appears on no command line. It is stored in *dir*/.ui/git-tokens/, sealed with AES-256-GCM under a key that only the user's own secret derives. It is never shown again.

**GET /~ui/git** lists the repositories the user keeps (for an admin, all of them). Each entry has the state its last run ended in, and the answer says whether the user has a token. **POST /~ui/git** takes one of these bodies. **{"action":"add", url , branch , bucket , name , private , every }** adds a repository and starts its first run. The defaults are branch **main**, the user's own library **git-***user***,** every **never**, and the name taken from the URL's last part. **{"action":"every","id","every"}** sets the schedule: **never**, **day**, **week** or **month**. **{"action":"sync","id"}** starts a run. **{"action":"remove","id"}** removes a repository; its files and bundles stay. **{"action":"token","token"}** sets the user's token, and an empty token removes it. A user can add a repository only into a library the user may write.

Earlier, all users shared one library, **git**. A repository still in that library moves to its owner's own library at the next start. It runs there until its tree is complete and **git-sync --move-from git** has taken over its backups and removed its files from the old library. The old library is removed once it is empty. *dir*/.ui/git/*id*/moved-from keeps track of the move across restarts.

## Durability

**--fsync** decides when a write that a client was answered for is on the disk, like a cache's journal and Redis's appendfsync. In every mode, a crash of the process loses no answered write, because the page cache outlives the process. Every mode syncs the whole filesystem at a stop, before it writes the clean marker.

#### `always`

Each write is synced before it is answered; this is the default. A put is answered once its file, its name and its directory are synced. A put of up to 1 MiB with no condition waits for one sync instead: its pooled file is synced and renamed, and its directory is synced after the answer (see **How objects are stored**). A delete is answered once its directory is synced. The same holds for versions, tags, uploads and parts, and for the event-notification and replication entries written beside them. An answered write survives a crash of the machine. A small put spends most of its time waiting for its one sync. On one shard of the measuring box this gives about 1,500 4 KiB puts a second, or about 700 into a versioned bucket.

#### `interval`

The per-write syncs are skipped, and a thread syncs the filesystem periodically. The thread calls **syncfs** every **--fsync-interval** (default 1 second). Under **--shards** the thread runs in shard 0 alone, since one call covers the files of every shard. A crash of the machine loses at most the writes of the last interval. The same box handles about 18,000 puts a second, or about 9,600 into a versioned bucket.

#### `never`

The syncs are skipped; only the kernel's own writeback and a stop put the writes on disk. The kernel's writeback typically happens within 30 seconds. This mode is for data that can be made again, such as caches and build artefacts.

Under **interval** and **never**, what a crash of the machine leaves behind depends on the filesystem. ext4 in its default data=ordered mode leaves an object either as it was or as it was written, never partly written. A start that finds a file whose header does not check out leaves the file unserved. On other filesystems, a file written in the last interval may hold zeros where its data was not yet written. Bucket creation and removal and the configuration documents are synced in every mode. Backups, and anything else that deletes its own copy once a put is answered, should use **always**.

The cost of **always** depends on the disk. A drive with power-loss protection (most enterprise NVMe and SATA SSDs) answers a sync from its protected cache in microseconds, so the mode costs little there. A consumer or virtual disk answers a sync only once the data is on the medium. XFS writes less per sync than ext4. ext4's **fast_commit** feature (**tune2fs -O fast_commit**) shortens a sync after a small change. Concurrent puts already share the filesystem's journal commits, so **always** gains throughput with concurrency. Three alternatives were measured against it: one sync of the whole filesystem shared by every waiting put, files written ahead of time and overwritten, and **O_DSYNC** writes. None did better under a sustained load of small puts. **stats** counts the syncs that ran in **fsyncs**, those a mode skipped in **fsyncs_skipped**, and the filesystem syncs of **interval** in **syncfs_rounds** and **syncfs_failed** (counted by shard 0); a stop after a failed round is not a clean one.

## Sharding

**--shards** *N* runs N worker processes on one port (**SO_REUSEPORT**), all on the same **--dir**. With **--listen**, each worker is a node of its own instead (*name#i*.sock, as for a cache). Clients see one runtime. Every shard serves a GET or HEAD itself by opening the object's file, whose header describes the object, so object bytes never move between shards.

**One shard is the default, and on a machine of a few cores it is the right one.** One shard answered 95,000 signed GETs of 4 KiB a second on one core, about 3 Gbit/s of payload. A runtime behind a 1 or 10 Gbit link therefore runs out of network before it runs out of its core. Shards help only where small reads saturate that core, and they cost CPU wherever a request crosses shards. The table below was measured on one box, with the runtime confined by **taskset** and a **wrk** client, on cores of its own, replaying signed GETs of 64 keys:

| CPUs | shards | GET 4 KiB |
|---|---|---|
| 2 | 1 | 96,000 req/s |
| 2 | 2 | 185,000 req/s |
| 2 | 4 | 177,000 req/s |
| 4 | 2 | 187,000 req/s |
| 4 | 4 | 253,000 req/s |
| 4 | 8 | 218,000 req/s |
| 8 | 4 | 258,000 req/s |
| 8 | 8 | 359,000 req/s |

The last row is limited by the client's six threads. More shards than CPUs is slower, never faster.

Shards have a price, measured on the same box:

- A ListObjectsV2 page of 1000 keys took 2.1x the CPU at two shards and 2.4 to 2.5x at four, because every shard walks up to a page and one shard merges them.
- A 4 KiB PUT took 1.2 to 1.3x the CPU at two shards and 1.4 to 1.6x at four. At four shards, three keys in four are committed by a shard other than the one the body landed on.

Large objects move at the same rate at any shard count: a 64 MiB GET was limited by the client and a 64 MiB PUT by the disk.

A key's *owner* is the shard that commits its changes. The slot is the CRC16/XMODEM of the string *bucket***/***key* masked to 16384 slots, exactly the function of a cache's key slots. The owner is shard *slot* * *N* / 16384. A client can therefore compute the owner and send a request to the owner's node, so that nothing crosses shards.

A put streams into a temporary file on whichever shard took the connection. That shard then sends the owner the file's name and the object's metadata over the shard link. The owner renames the file into place, syncs the directory and answers. After the answer, the owner appends to its own journal (**index.***i*, written by shard *i* alone). A delete, the target of a copy and a create-only put (**If-None-Match: ***) go the same way. This keeps the changes to a key in one order, and ensures that one of two racing creators is refused. A listing is requested from every shard and the pages are merged, so the result is the listing a single shard would give. If a shard cannot be reached, the listing fails with a 500 rather than coming back incomplete.

Shard 0 creates and drops buckets, and tells the other shards before it answers. A bucket is dropped only when every shard agrees that it holds nothing and is idle. Shard 0 also changes a bucket's CORS, lifecycle and versioning configurations and its policy, whichever shard took the request. It makes one change per bucket at a time. It answers only once no shard can go on using the old document. A change that a running shard cannot be told of is refused with 503 and changes nothing (see **Bucket policy**).

Each shard sweeps the keys it owns. Temporary files are named for the shard that wrote them, so a shard that the supervisor restarts removes only its own. A shard killed between a rename and its journal record leaves the object in the directory. When the shard restarts, it adopts the object from its header. From then on, either every shard serves the object or none does. A put that was in flight through the killed shard is answered with an error.

A start with a different **--shards** on a directory written with another shard count is not refused, unlike a cache with a missing dump. The object files are the record. Each shard sees that its journal was written for another shard count, and rebuilds its keys from the object headers, keeping those it owns. Shard 0 removes the journals of shards that no longer exist. Such a start reads every header once per shard, so its time grows with the object count.

**--max-bytes** is split into equal shares per shard. The shard that took the put checks it against its own bytes, and the owner checks it again. The limit is therefore approximate when keys are unevenly sized. **stats** gives a section per shard with **shard_commits_sent**, **shard_commits_served**, **shard_deletes_sent**, **shard_deletes_served**, **shard_list_fanouts**, **shard_list_pages_served**, **shard_bucket_ops**, **shard_mpu_sent**, **shard_mpu_served** (multipart steps), **shard_hot_drops_sent** and **shard_hot_drops_served** (a sibling told to drop its copy of a key, once per sibling), **shard_hot_holds_sent** and **shard_hot_holds_served** (a sibling asking the owner to keep a copy) and **shard_peer_failures**; at one shard nothing is sent and they read zero.

A multipart upload lives on the shard that owns its key. Every step that names the upload (create, part, complete, abort, ListParts) is handled by that shard, and ListMultipartUploads asks every shard. A part's body is written on the shard where the connection landed, and only its name crosses to the shard that keeps the upload. CompleteMultipartUpload works in three steps:

- the shard that keeps the upload checks the part list and seals the upload;
- the shard the request landed on assembles the object from the parts on the shared disk, and commits it through the key's owner;
- the owner removes the upload.

No long task is therefore asked of a sibling over the link. An upload whose assembler never reports back is opened again after six hours. After a restart with another **--shards**, the shard that owns an upload's key finds the upload again. A bucket with an open upload on any shard is not dropped.

TLS, credentials, the credentials file, scripts and the metrics are each shard's own, or their sum:

- every shard terminates TLS and re-reads the credentials file;
- a script's hooks run on the shard that took the request;
- a script's **socketley.storage** call is answered by whichever shard the daemon relays it to, and reaches the other shards as any request does;
- the **socketley_storage_** series add the shards together (a bucket that every shard holds is counted once).

**stats** reports these fields. For contents and traffic: **buckets**, **objects**, **bytes**, **requests**, **gets**, **heads**, **puts**, **deletes**, **copies**, **lists**, **client_errors** and **server_errors**. For reads and the journal: **zero_copy_gets**, **copied_gets**, **hot_gets** (the copied GETs answered from the hot copy), **hot_bytes** (what the hot copies hold), **zero_copy_bytes**, **journal_records** and **journal_compactions**. For syncs and starts: **fsyncs** (of files and directories alike, that ran), **fsyncs_skipped** (those **--fsync interval** or **never** skipped), **syncfs_rounds** and **syncfs_failed** (the filesystem syncs of **--fsync interval**), **start_files_read** (object and version files whose headers the last start read: 0 when every journal was trusted), **pool_ready** (empty files the buckets' pools hold durable for small puts, 0 after a start until the first put). For uploads, lifecycle and connections: **multipart_uploads**, **multipart_parts**, **multipart_bytes**, **multipart_created**, **multipart_completed**, **multipart_aborted**, **lifecycle_expired**, **lifecycle_aborted**, **timeouts**, **tls** (1 when the listener is TLS), **tls_handshakes**, **tls_failures**, **body_recvs** (receives that brought bytes of an upload's body) and **hash_handoffs** (pieces of digest work handed to the hashing threads). For encryption and media: **sse** (1 when the runtime has a master key), **sse_puts** and **sse_gets** (bodies written encrypted, and GETs answered by opening an object's chunks), **media_made**, **media_failed** and **media_served** (thumbnails and streams ffmpeg made and failed to make, and the answers served from them), **media_direct** (ffmpeg jobs that read the object's file rather than through the listener), **media_hw** (rendition jobs encoded on the GPU). There is also one line **error_***Code* for every S3 error code the runtime has answered, such as **error_NoSuchKey**. Bytes in and out and **total_messages** (requests) are the common fields. The runtime closes a connection whose request head is unfinished after ten seconds, or whose body has not moved for a minute, and removes its temporary file.

## Metrics

With the metrics endpoint on, each running storage runtime adds these series, all labelled **name**: **socketley_storage_buckets**, **socketley_storage_objects**, **socketley_storage_bytes_stored**, **socketley_storage_bytes_received_total**, **socketley_storage_bytes_sent_total**, **socketley_storage_zero_copy_bytes_total**, **socketley_storage_tls_handshakes_total** and **socketley_storage_tls_failures_total**. It also adds **socketley_storage_requests_total** (label **op** = get, head, put, delete, list, copy) and **socketley_storage_errors_total** (label **code** = the S3 error code).

The subsystems have families of their own when a runtime runs them: event notifications (**socketley_storage_notify_***), replication (**socketley_storage_replication_***), a cluster (**socketley_storage_cluster_***), the scrub (**socketley_storage_scrub_***), compression (**socketley_storage_compressed_***), tiers (**socketley_storage_tier_***), and lifecycle, multipart, media and fsyncs. Every other **stats** figure is exported as **socketley_storage_stat** with its name as the label **stat**, so nothing a runtime counts is missing from a scrape.

A mail runtime's figures are **socketley_mail_received_total**, **_delivered_total**, **_deferred_total**, **_bounced_total**, **_stored_total**, **_quarantined_total**, **_auth_failed_total** and the gauges **socketley_mail_queued** and **_queued_bytes**. Its other figures are **socketley_mail_stat** by name. A tunnel's gauges are **socketley_tunnel_links**, **_agents**, **_shares** and **_flows** (UDP visitors). Its counters are **socketley_tunnel_streams_total**, **_refused_total**, **_visitors_refused_total** (requests a protected service's auth refused), **_bytes_in_total**, **_bytes_out_total**, **_datagrams_total** and **_datagrams_dropped_total**.

## Lua

A script attached with **--lua** may define three hooks on a storage runtime.

#### `on_request(req) -> nil | true | false | string | table`

Called for every request after authentication and the bucket policy, before anything is done. The hook therefore sees only requests that both let through. It can refuse any of them, but cannot let in a request that they refused. It runs on a coroutine, so it may wait for another runtime (see **socketley.storage** below). The connection is not read from until the hook answers. A refused upload is therefore answered before its body is read, and its connection is closed.

*req* has **method**, **operation** (the name S3 gives it: GetObject, PutObject, DeleteObjects, ListObjectsV2, CreateMultipartUpload, UploadPart, UploadPartCopy, CompleteMultipartUpload, AbortMultipartUpload, ListParts, ListMultipartUploads, PutBucketLifecycleConfiguration, ...), **bucket**, **key**, **path** and **query** (as sent), **host**, **request_id**, **principal** (the access key, empty for a request with no credentials), **tls** (boolean), **client** (**ip:port**, or **unix**), **content_length** (absent for a chunked body) and **headers** (lowercase names).

Returning nothing or **true** lets the request go on. **false** refuses it as AccessDenied (403). A string refuses it as that S3 error code, with the status S3 gives that code (403 for a code the runtime does not know). A table **{deny="Code", message="...", status=403}** sets all three. An error raised in the hook, or a return value of any other type, refuses the request with 500 InternalError and is logged. This is deliberate: a hook whose failure let requests through would protect nothing.

#### `on_put(bucket, key, meta)`

Called after an object is committed. It is called for a put, for the destination of a copy, for an object a script put with **socketley.storage.put**, and for a completed multipart upload (once, at completion, and never for its parts). It is never called for a write that was refused. *meta* has **size**, **etag**, **content_type**, **mtime_ms** and **metadata** (the user metadata, without its prefix). The hook is called after the client's answer is on its way.

#### `on_delete(bucket, key)`

Called after an existing object is removed by DeleteObject, DeleteObjects or **socketley.storage.delete**. It is not called for a key that did not exist.

When a script writes an object in **on_put**, its **on_put** is called again for that object.

## socketley.storage

Any runtime's script may use a storage runtime by name, in this daemon or in another process. The daemon does not stop while the script waits:

```
socketley.storage.put(runtime, bucket, key, data [, {content_type=, metadata={}}] [, callback])
socketley.storage.get(runtime, bucket, key [, callback])
socketley.storage.head(runtime, bucket, key [, callback])
socketley.storage.delete(runtime, bucket, key [, callback])
socketley.storage.list(runtime, bucket [, prefix] [, {delimiter=, max_keys=, start_after=}] [, callback])
```

Some callbacks can pause: **on_message**, **on_client_message** and the storage hooks above. In these, a call without a callback waits and returns the answer. The connection that a server handler is answering is kept open while it waits, as it is for a linked cache. Anywhere else (an **on_tick**, a cache's **on_write**, a proxy's filter), pass a function as the last argument. The call then returns **true** at once, and the function is called with the answer on a later turn. A call that must wait, made where waiting is not possible and without a function, returns **nil** and a message saying so.

The answers are:

- **put** and **head** return a table with **size**, **etag**, **content_type**, **mtime_ms** and **metadata**.
- **get** returns the data and that table.
- **delete** returns **true**, also for a key that was not there, as S3 does.
- **list** returns a table with **objects** (each with **key**, **size**, **etag**, **content_type**, **mtime_ms**), **prefixes**, **truncated** and, when truncated, **next** (pass it as **start_after** for the following page).

A failure returns **nil** and the S3 error code and message (**NoSuchKey**, **NoSuchBucket**, **InvalidBucketName**, **EntityTooLarge**). When the request did not reach the runtime, the call returns **nil** and a reason (**no such runtime**, the request channel is full). Metadata names are lowercased and stored as **x-amz-meta-***. Buckets are created with the S3 API. An object moves whole in memory, and the request crosses a process boundary in a frame that waits in a 4 MiB queue. A script may therefore put or get at most 1 MiB per call, and at most 1024 calls may be waiting on one runtime. Use the S3 port for larger objects.
