# Concepts

The daemon, its runtimes and the few rules every one of them follows.

The rules every runtime follows, whatever its type. For what happens behind a command, step by step, see [How it works](how.txt).

## A runtime

A runtime is one network service. It has a **type**, which decides what it speaks (a server, a proxy, a cache, …; see [registered types](man-registered-types.txt)), and a **name**, unique on its daemon, by which commands and other runtimes refer to it.

| Command | What it does to a runtime |
|---|---|
| `create type name [flags]` | Checks the flags and saves the runtime. With `-s` it also starts it. |
| `start` / `stop` | Starts its worker process / ends it. The runtime itself is kept. |
| `edit name [flags]` | Changes flags. Without flags it opens the runtime's JSON in your editor. |
| `reload-lua name` | Loads the changed script without dropping connections. |
| `remove` | Stops it and deletes it. |

A runtime is always in one of four states: `created` (saved, never started), `running`, `stopped`, or `failed` (it could not start; `ls` shows why).

## State that survives

Each runtime is saved as a JSON file in the daemon's state directory. When the daemon starts, it brings every runtime back and starts the ones that were running before. Runtimes survive restarts and reboots without any setup.

| Command | Use it to |
|---|---|
| `show name` / `import name` | Print a runtime's configuration as JSON / replace it from JSON, so `show a \| import b` copies one. |
| `export dir` | Write the daemon's whole setup as Lua files into a directory. |
| `export --full file` | Archive setup and data together, for a backup; `restore` puts it back. |

### State persistence

The daemon persists runtime configurations as JSON files. When a runtime is created, its configuration is saved. When the daemon starts, it restores all persisted runtimes. Runtimes that were running when the daemon stopped are started again automatically.

Runtimes therefore survive daemon restarts and system reboots, like Docker containers with the restart-always policy.

State is saved after the create, start, stop, remove and edit commands. The **was_running** field records whether a runtime should be started automatically when the daemon starts.

## Names, ports and addresses

- **Runtimes find each other by name.** `--backend api` or `--cache store` names a runtime, not a port, so the link holds when its port changes.
- **Public names go through the entrance.** A runtime's `--domain` names are served by the entrance, the one proxy on ports 80 and 443, which also gets their certificates.
- **A port can be kept local.** `--bind 127.0.0.1` binds it to one address; `--listen unix:/path` uses a unix socket instead of a port.
- **One address, one runtime.** Two runtimes on the same port and address are refused, so a typo cannot silently split traffic.

### The node beside the port

A **server** or an unsharded **cache** that listens on a TCP port also listens on an AF_UNIX node. The daemon creates the node in a directory named after its own socket, *<socket>*.rt/, and names the node after the runtime. The directory is named after the socket rather than placed beside it, because the default socket is */tmp/socketley.sock*, and every user on the machine shares that directory. Nothing needs to be configured, and nothing about the port changes: a runtime created with **-p 9000** is reached on 9000 from anywhere, as before. The node is an addition, never a replacement, and nothing outside this machine can reach it.

The node exists for one caller: another runtime on this machine. A proxy whose backend is written as a *runtime name* uses it. A proxy whose backend is written as an *address* uses it too, but only while a running runtime publishes exactly that host and port. A name asks for the runtime, and the proxy may choose how to reach it. An address asks for the address, so the substitution holds only while the two are the same thing. If the runtime moves to another port, the address means what it says again.

Measured on Linux 7.2.2, with the same proxy in front of the same server and only the backend leg differing, a request falls from 25.33 to 22.68 microseconds. The whole process tree spends 4.0 microseconds less CPU on each one. This held in 12 of 12 interleaved passes (median of the per-pass differences). The CPU saving is larger than the latency saving, which is what a saving under load looks like. A serial round trip waits on wakeups, and the freed CPU has no use until a second request needs it.

**The node is 0600 in a directory the daemon creates 0700.** Only the user the daemon runs as can reach it. Measured: another local user reaches the port but is refused on the node with **EACCES**, and cannot list the directory or create a node in it either. None of this narrows the port, which is exactly as open as it was. But the leg between two runtimes no longer travels over something every local user could also connect to.

The daemon checks the directory, not only creates it. A **mkdir**(2) that answers **EEXIST** says a directory is there but not who owns it, so the daemon stats it. If it is not a directory the daemon owns with no group or other access, companion nodes are turned off for the whole daemon, and the log says so once. Without that check, another user could create the directory first and hold a live node at a path the daemon was about to publish. The bind refuses to take over a live node, so the path would stay published and be served by that other user.

The node takes away two things, both worth knowing before relying on it:

- **A firewall rule on loopback does not apply.** nftables and iptables see packets, and an AF_UNIX socket produces none. A rule that drops traffic to a runtime's port does not stop another runtime from reaching it over the node.
- **tcpdump -i lo shows nothing.** At start, the proxy writes one line per backend to the daemon log, naming the path it will use. That line is the only evidence that the node was used.

A runtime gets no node in these cases:

- It is neither a server nor a cache.
- It has no port. A runtime already on **--listen unix:** has nothing to add.
- It uses **--udp**.
- Its listener is TLS. A cleartext node beside an encrypted port would undo what the port was configured to give.

A proxy keeps only its port, and so does a cache with **--shards**. A path is one node, and N processes would unlink each other's; that is why **--listen** gives each shard a node of its own. One rule decides both what the daemon publishes and what a runtime binds. So a type that is not wired to a listener is never advertised as having one, because a path published with nothing behind it is a backend that is simply down. For the same reason, a proxy configured with backend TLS keeps TCP rather than silently dropping the encryption it was asked for.

### Between runtimes on one machine

Requests from one runtime to another include **socketley.send**, **self.route**, and a server's **--cache** *name***.** The daemon carries the first such request between two runtimes, up one control socket and down the other. It then introduces the two processes to each other with a new socket pair, and later requests go straight across.

There is nothing to configure and nothing to see from outside. The pair has no path in the filesystem, so nobody can connect to it or squat on it; only the two processes that were handed the ends can use it. The daemon logs one line naming the pair when it introduces them. **socketley stats** *name* reports **peer_links**, **peer_direct** and **peer_relayed**, which tell a request that went through the daemon from one that went straight across.

Measured with a server posting every cache command to a cache runtime, the two arms differing only in whether they were introduced, a round trip falls from 31.60 to 21.14 microseconds. The process tree spends 10.75 microseconds less CPU per command. This held in 12 of 12 interleaved passes (median of the per-pass differences). A third of the round trip was the daemon.

A request falls back to the daemon whenever the link is not usable, so nothing depends on the link. If a link never forms, or its peer has gone, the only cost is the speed it would have saved. A routed connection is pinned to the path it opened on for its whole life, because a message that changed route mid-stream could arrive ahead of one sent before it.

### Which port a runtime is on

**ls**, **ps**, **stats** and the metrics endpoint report the port a runtime *binds*, which is not always the port it was configured with. A runtime created without **-p** takes its type's default: 8000 for a server, 8080 for a proxy, 9000 for a cache. The **PORT** column, **ps --json** and **stats** show that port, not the configured 0, so an operator can see which port the runtime is actually answering on.

**show** is deliberately not in that list. Its output is the state document, which goes back in through **import**. Writing the default into it would pin a runtime that had been left to take whatever default its type has.

A runtime that binds no port at all reports **0**. That is a client, a **--listen** *unix:* listener, a process registered with **attach**, or a server reachable only through its owner.

### One address, one runtime

A runtime's start is refused when another runtime on this daemon is already serving the address it would bind: a TCP port, a UDP port, or a **--listen** *unix:* path. The refusal names both runtimes and reaches the terminal. During the restore at boot, it names both in the daemon log.

The kernel would not refuse it. Every listener is opened with **SO_REUSEPORT**, because that is the whole mechanism behind **--shards**: N worker processes of *one* runtime bind one port, and the kernel hands each connection to one of them. A second *runtime* claiming the same port looks the same as a second shard, so the bind succeeds and the connections split between the two at random. Measured without this check, with two servers created on one port: both started, both listened, nothing was logged, and twenty messages arrived split nine and eleven.

These are still accepted, because they are not the same address:

- **--udp beside TCP**. UDP and TCP are separate namespaces in the kernel, so a datagram server and a stream server on the same number are two listeners that never meet.
- **A restart**. It passes through **stopped** and takes back its own port, because the rule reads state, not configuration.
- **--shards**. Its workers are one runtime.
- A runtime that binds nothing at all: a client, a process registered with **attach**, or a server reachable only through its owner.

A clustered cache holds more than one address: the configured port, and *base+1*..*base+N* for the shards, which is the formula **CLUSTER SLOTS** publishes. A runtime that took one of those ports would be sent keys it does not hold.

The refused runtime stays in the state it was in, **created** or **stopped**, not **failed**, because nothing was built and nothing broke. To resolve it, stop the runtime named in the refusal, or give one of the two an address of its own.

## TLS

A server, cache, proxy or mqtt broker encrypts its own port with `--tls --cert file --key file`. Add `--ca file` to require client certificates. `--acme name` gets a Let's Encrypt certificate and renews it.

When socketley connects out (a client runtime, a proxy's `https://` backend), it always verifies the server's certificate; that check cannot be turned off. What is not supported is listed under [TLS limitations](man-limitations.txt).

## Several cores

A runtime's worker uses one core. `--shards N` runs N workers that share the port, and `--cpus` chooses the cores they may run on. On a cache, each key belongs to one shard. More shards do not always mean more speed: read [sharding](man-server-flags.txt) before choosing N.

## Scripts

Most types take `--lua file`: a script whose callbacks (`on_client_message`, `on_http_request`, …) answer instead of the built-in behaviour. It is loaded when the runtime starts and replaced with `reload-lua`. A callback that never returns is ended by its [deadline](man-lua-configuration.txt). See [Lua scripting](lua.txt).

## More than one machine

Daemons that share a cluster directory see each other's runtimes, and a proxy's `@group` backend reaches group members on every machine. See [Cluster](cluster.txt).

## Watching it

`socketley ls` lists runtimes and their states; `socketley stats name` and `socketley daemon stats` print live counters. The daemon also serves a web [dashboard](man-dashboard.txt) and Prometheus `/metrics`. A [metrics](rt-metrics.txt) runtime keeps the history and sends alerts.

### Dashboard

When **daemon.metrics_port** is set in the daemon configuration file, the metrics endpoint serves the following routes:

##### `GET /`

Serves the web dashboard, which has the storage interface's look and takes its stylesheet and helpers from the same binary. The overview shows the daemon's runtimes, connections, messages, bytes in and out, CPU and resident memory, each with a line graph of its last three minutes. The runtime list shows each runtime with its state and the same figures, and can be filtered by type and name. Each runtime also has a page with its configuration and its **stats**.

A signed-in user can start, stop, restart and remove a runtime, and reload its Lua. The user can also edit a runtime, either in a form for its type, filled in with what **show** prints, or as the JSON that **import** takes. To create a runtime, the user picks the type and then fills in a form of every flag that **create** takes for that type, grouped by section. The page shows the command it will send while the form is filled in.

If **daemon.dashboard_idp** names an **idp** runtime, the page offers sign-in through it. An account of the group **admins** that is signed in at that idp is signed in to the dashboard too. Signing out of the dashboard also signs out at the provider.

Otherwise, signing in takes the access key and secret of an admin in the credentials file that **daemon.dashboard_credentials** names. The file has a storage runtime's format, and the dashboard checks the key and secret the same way a proxy's **--auth basic:** does. An address that fails five times in fifteen minutes is refused with 429, even with the right secret. Behind a proxy on this machine, the address counted is the one in X-Forwarded-For.

The session is a cookie sealed with a key that the daemon generates at start. The cookie is HttpOnly and SameSite=Strict, and also Secure behind HTTPS. It is valid for twelve hours. The daemon ends a session when the user signs out, when the user's key is removed from the file, or when that key is given another secret. Each command also carries the page's own header, which a request from another site cannot carry. The command goes over the daemon's control socket, as a CLI command does, and is logged with who sent it. The page sends only **create**, **edit**, **import**, **start**, **stop**, **remove**, **reload**, **reload-lua**, **show**, **stats**, **ls** and **ps**, and never a word that contains a space.

When credentials are configured, every route except the page and the sign-in needs a session. **/metrics** needs a session too, except for a scraper on this machine that connects without a proxy in between. Without credentials, the page shows the figures but changes nothing. The log and a zone's text always need a session, whatever is configured.

The dashboard's history and alerts come from a **metrics** runtime (see **METRICS FLAGS**). The daemon creates one named **metrics** the first time it starts with the dashboard on and a way to sign in to it (**daemon.dashboard_credentials** or **daemon.dashboard_idp**), or with any of **daemon.alert_webhook**, **daemon.alert_mail** and **daemon.events** set. The metrics runtime listens on 127.0.0.1:9090, or on the next free port above it. The daemon creates it only once, so a metrics runtime that was removed stays removed. With no metrics runtime running, the page shows the current figures and no history. With several, the page reads the one named **metrics**, or else any running one that collects this daemon's series.

The graphs cover a chosen range: the last fifteen minutes, hour, six hours, day, week, month or year. The value and time under the pointer are shown. For each runtime and for the daemon, connections and memory are drawn as they are, and messages, bytes and CPU as rates per second. The figures are read from the metrics runtime's store, which keeps them as long as its **--keep** and **--downsample** allow. **GET /api/history?runtime=**name**&range=**seconds**&points=**n returns the history of one runtime, or of all runtimes together when no name is given, as *n* points. A point with no data is null. The answer is an object with **from** (in seconds since 1970), **step** (the seconds per point) and the arrays **conn**, **msg**, **in**, **out**, **cpu** (percent of one CPU) and **rss**. The range is held between a minute and a year, and the number of points between 10 and 1440.

The Alerts view shows the metrics runtime's rules. These are the built-in rules below, unless its **--rules** file changes them. A runtime failed, or was started again three times within the hour. A sync runtime cannot carry what it owes. A certificate that a runtime serves expires within two weeks; the alert is critical within three days, or once the certificate has expired. The disk under a storage runtime or under the state directory, or the host's memory, is at 90% (critical at 95%). A storage runtime is at 90% of its **--max-bytes**, or a cache that refuses writes is at 90% of its **--maxmemory**. A git repository's last pull failed. A mail runtime has a hundred messages waiting (critical at a thousand), or its own address is listed by a blocklist that its **--dnsbl** names. A scraped target does not answer for two minutes. A tunnel edge is missing an agent that joined it, or drops more than 1% of its datagrams. An idp runtime barred more than twenty sign-ins in ten minutes.

A critical alert silences the warning on the same thing. Each alert is logged, listed on the page with the recent notifications, and shown on the overview. When **daemon.alert_webhook** is set to an http or https URL, each alert is also posted to it as JSON. The **content** and **text** fields carry the message; these are the fields Discord, Slack and Telegram's sendMessage read. The **state** (**firing**, **resolved**) and **alert** fields carry the rest. If the hook does not accept a message with a 2xx status, the daemon posts it again after a pause that doubles each time, up to eight seconds. A message the hook has not accepted is kept in **.notify** in the state directory and posted after a restart.

When **daemon.alert_mail** is set to **mail://***runtime***/***address*[,*address*...] that mail runtime mails each alert, as well as or instead of the webhook. The subject is the alert's first line. Mail is held the same way until the mail runtime runs. The metrics runtime keeps its alerts' state in its directory, so a metrics runtime that is started again does not report the same alerts a second time. **GET /api/alerts** lists the alerts, and **POST /api/alerts/test** sent with the page's header posts a test through the hook.

When **daemon.events** names an mqtt runtime, the daemon publishes the state of each runtime on it, at QoS 1 and retained. It publishes on **socketley/runtimes/***name***/state** as JSON with the runtime's **name**, **type**, **state** and **port**. It publishes at every change, and clears the topic when the runtime is removed. The daemon also publishes each alert while it holds, on **socketley/alerts/***id* as the JSON that the **alert** field above carries, and clears it when the alert clears. A subscriber to **socketley/#** receives the current state as soon as it subscribes, and every change after that. The broker may be created after the daemon starts. Until it runs, the messages owed to it wait in **.notify** in the state directory, as the webhook's do.

The Logs view follows the daemon's recent log live, and filters it by runtime, by level and by text. Each runtime's page shows that runtime's own log. A failed runtime shows the last warning or error it wrote, both in the list and on its page, next to how often it was started again. Each worker writes its stderr into its own pipe, which the daemon reads. The daemon passes every line on unchanged to its own stderr, so the journal gets every line. It also keeps the last 10,000 lines in memory, its own and the workers', each tagged with the runtime's name: **GET /api/logs?since=**seq**&max=**n**&runtime=**name**&level=**warn**.**

The Domains view shows three things. The first is every certificate that a runtime serves: its names, its issuer, how long it has left, whether it is self-issued, whether a wildcard is waiting for its zone's delegation, and the last line of a failed issuance. The second is each entrance's routes, each mapping a name to the runtime it goes to. The third is the zones of the dns runtimes, whose records the page can edit. Before an edited zone is written, its text is checked the way the dns runtime reads a zone file. If the serial was left as it was, the dashboard raises it, so secondaries take the change. The view uses **GET /api/edge**, and **GET** and **PUT /api/zone** for a file a dns runtime serves and no other.

The endpoint listens on 127.0.0.1 only. To reach it on a server, open an SSH tunnel with **ssh -L 9100:127.0.0.1:9100** *host*, and then open **http://localhost:9100/**. On an installed system the port is set in **/etc/socketley/config.lua**, as **daemon = { metrics_port = 9100 }**, and is read when the service starts.

##### `GET /metrics`

Serves the daemon's metrics in Prometheus exposition format. It is suitable for scraping by Prometheus, Grafana Agent, or similar monitoring stacks.

##### `GET /api/overview`

Returns a JSON object with high-level daemon statistics:

```
{
    "version": "1.1.0",
    "uptime_seconds": 86400,
    "runtimes_total": 5,
    "runtimes_running": 4,
    "connections_total": 18230,
    "connections_active": 142,
    "messages_total": 9120044,
    "bytes_in": 12345678,
    "bytes_out": 9876543,
    "cpu_seconds": 812.40,
    "rss_bytes": 163577856,
    "memory_bytes": 94371840,
    "processes": 5,
    "cpus": 4
}
```

**cpu_seconds** is the user and system CPU time of the daemon and of every process its runtimes run in, read from **/proc**. The change between two readings, over the time between them, is the CPU used. **rss_bytes** is the sum of their resident memory, which counts a page shared between shards once per shard. **memory_bytes** is what they cost the machine: each shared page is counted by the share of it that each process holds (the kernel's Pss). So the runtimes' figures add up to the memory they hold between them. **processes** is how many processes there are, and **cpus** is the number of CPUs online.

##### `GET /api/runtimes`

Returns a JSON array of all runtimes with name, type, port, state, connections and message/byte counters. Each entry also has **cpu_seconds**, **rss_bytes**, **memory_bytes** and **processes** for the runtime's own processes: one per shard, and none while it is stopped.

##### `GET /api/runtime/name`

Returns a JSON object for the single runtime named *name*. Returns 404 if the runtime does not exist.

The **dashboard** CLI command prints the dashboard URL:

```
$ socketley dashboard
Dashboard: http://localhost:9100/
```
